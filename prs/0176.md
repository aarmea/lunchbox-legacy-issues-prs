## Description

Closes [#170](https://github.com/aarmea/lunchbox/issues/170). Split out of [#155](https://github.com/aarmea/lunchbox/issues/155), where it was found and agreed as a real defect
but explicitly out of scope.

Usage is written **once**, at session end, and `end_current_session` charged it
to `now.date_naive()`. A session from 23:50 to 00:10 therefore put all twenty
minutes on the *second* day — out of a quota the child had not touched yet. An
activity run right up to bedtime ate into the next morning, and the child woke
up already behind.

```rust
let billed_day = session.started_at.date_naive();
```

`ActiveSession::started_at` is the wall clock at launch approval and is never
mutated afterwards, so it is exactly the ledger key wanted. Splitting a session
across the two days it spans stays out of scope: the whole session lands on its
start day.

## Why the start of the session, not the start of billing

Billing runs from `window_ready_at_mono` — [#135](https://github.com/aarmea/lunchbox/issues/135), the child is not charged for
the spinner — which is monotonic and has no wall-clock twin. Deriving one would
reintroduce exactly the drift [#155](https://github.com/aarmea/lunchbox/issues/155) was about. The two differ by the launch
latency, which can only matter for a session approved in the last few seconds of
a day, and "the day the child started playing" is the honest answer there
anyway.

## Tokens, which [#155](https://github.com/aarmea/lunchbox/issues/155) said this would have to decide

That same date was passed down through `settle_session_end` into
`settle_tokens`, so token settlement and the force-enable lookup landed on the
same wrong day. They do not have the same answer, and the reason is that **token
balances are not a ledger.**

Each gate is a single row in `token_balances` with one `updated_day` stamp, and
a gate without `carry_over` resets *lazily* when that stamp goes stale rather
than by a sweep job. So once midnight has passed there is no "yesterday's
balance" left to settle against — it is gone by construction.

Passing the billed day straight through to the store would have been actively
harmful. `adjust_token_balance` reads the row, resets it if the stamp does not
match, and writes the requested day back:

> A caregiver grants ten minutes at 00:05, while a session started at 23:50 is
> still running. The session ends at 00:10, settles against `2026-04-27`, finds
> a row stamped `2026-04-28`, treats it as stale, and writes the spend over the
> top. The grant is silently zeroed.

So `settle_tokens` now takes both dates, and they differ only for a session that
crossed midnight:

| | means | who is told |
|---|---|---|
| `billed_day` | the day the session belongs to | the **ledger** questions: which day's force-enable granted it, and whether the balance it drew on still exists |
| `today` | the day the live balances belong to | the **store**, always — so the stamp can never move backwards |

And a gate that does not carry over is skipped outright when the two disagree.
The balance that session earned and spent from reset at midnight; there is
nothing left to bill, and billing today's balance instead would be precisely
this issue, one dimension over. Carry-over gates hold one continuous balance and
settle exactly as before.

The force-enable lookup moving to `billed_day` is the smaller half of the same
point, and it bites on its own: an override is keyed by date, so the grant that
approved a 23:50 session had expired by the time it ended. Asking `today` meant
`granted` came back false and the child was billed for time you had given them.

Cooldowns needed nothing — they are stored as `now + delta` timestamps, not
keyed by date.

## Tests

Six engine tests, with two small helpers: `on_day`, which is the existing `at`
with the day spelled out, and `run_session_between`, which advances the wall and
monotonic clocks by the gap between two wall-clock times.

| Test | What it pins | Fails pre-fix |
|---|---|---|
| `usage_is_billed_to_the_day_the_session_started` | the whole session on the start day, nothing on the end day | ✅ |
| `a_session_across_midnight_leaves_the_new_days_quota_untouched` | what the child notices: `max_run_if_started_now` is the full quota after midnight, and short by the session before it | ✅ |
| `a_grant_after_midnight_survives_a_session_that_started_yesterday` | the clobber above | ✅ |
| `a_force_enable_from_the_start_day_still_exempts_the_spend` | the override lookup follows the billed day | ✅ |
| `a_carry_over_gate_is_still_spent_across_midnight` | carry-over gates are *not* skipped | regression guard |
| `a_failed_launch_across_midnight_is_billed_to_neither_day` | the [#135](https://github.com/aarmea/lunchbox/issues/135) exemption still holds on both days | regression guard |

The four marked ✅ were run against the pre-fix behaviour — `billed_day` reverted
to `now.date_naive()`, the override lookup to `today`, the skip disabled — and
all four fail there. The other two pass either way, which is what they are for.

## Verified end to end, headless

Mock time advances naturally from its starting offset, so crossing midnight for
real costs a fixture and a minute of waiting. One always-available `process`
entry running `/usr/bin/sleep 600`, `daily_quota_seconds = 1800`:

```sh
./scripts/shepherd dev headless --config dev-runtime/midnight-fixture.toml \
    --time "2026-04-27 23:59:20"
printf '{"request_id":1,"api_version":1,"method":"launch","params":{"id":"midnight-game"}}\n' \
    | nc -q1 -U dev-runtime/shepherd.sock
# ...wait past mock midnight...
printf '{"request_id":3,"api_version":1,"method":"stop_current","params":{"mode":"graceful"}}\n' \
    | nc -q1 -U dev-runtime/shepherd.sock
```

```
Session started  entry_id=midnight-game deadline=2026-04-28 00:29:24
Session ended    entry_id=midnight-game duration_secs=129 reason=UserStop
```

Launched at mock 23:59:24 on the 27th, ended at mock 00:01:33 on the 28th. The
`usage` table afterwards:

```
midnight-game | 2026-04-27 | 129
```

One row, on the start day. And `list_entries` right then — i.e. on the 28th —
reports `max_run_if_started_now = 1800s`: the new day's quota is whole.

(Use `nc -q1`. A bare `nc -U` holds the connection open after the response and
looks like a hang — noted in the history doc.)

## Not changed

- **Mid-session evaluation still asks about `now`.** A session that has crossed
  midnight is checked against the new day's quota by `evaluate_entry`, but only
  to paint the launcher grid, and nothing may launch while a session is current.
  Re-checking the *running* session against the new day is the crossing-midnight
  problem [#170](https://github.com/aarmea/lunchbox/issues/170) put out of scope.
- **No wire, config, or UI change.** The admin dashboard reads the `usage` table
  by date and simply sees the corrected rows.

Docs: a "Which day a session is billed to" section in `crates/shepherd-core/README.md`,
the store README's usage example and `token_balances` schema note, and
`docs/ai/history/2026-09-05 003 bill-usage-to-the-start-day.md`.
