## Description

**Closes [#157](https://github.com/aarmea/lunchbox/issues/157).** Advances [#172](https://github.com/aarmea/lunchbox/issues/172) without closing it, and narrows [#156](https://github.com/aarmea/lunchbox/issues/156). The
closed siblings for context: [#144](https://github.com/aarmea/lunchbox/issues/144), and its [#147](https://github.com/aarmea/lunchbox/issues/147) / [#148](./0148.md) / [#158](./0158.md).

| ticket | what this does for it |
| --- | --- |
| **[#157](https://github.com/aarmea/lunchbox/issues/157)** Sensitive file hardening | **Closed.** Policy, database, BLE admin record and reset sentinel move to a uid activities do not have, and are served over a socket that admits one cgroup. |
| **[#172](https://github.com/aarmea/lunchbox/issues/172)** Activities can kill shepherdd | **Advanced, not closed.** A shepherdd that dies now tears the session down (`loginctl terminate-session`, since `swaymsg exit` cannot work once the compositor socket is unlinked). Closes the third of the doors [#144](https://github.com/aarmea/lunchbox/issues/144) opened onto: policy and state are files owned
by the uid every activity runs as. [#147](https://github.com/aarmea/lunchbox/issues/147)/#148 closed the compositor's socket and
[#158](./0158.md) closed shepherd's own; both are about *runtime* effects. This is about the
state those effects operate on.

`shepherdd/src/main.rs` watches the config file's parent directory and reloads on
a write, so a file write is a live policy change. Observed on an installed kiosk,
from a plain activity — no socket, no credential, no root:

```
sqlite3: update usage set duration_secs = 0     -> shepherdd reports duration_seconds: 0
sqlite3: delete from audit_log                  -> 6 rows to 0
>> config.toml: [[entries]] id = "attacker-shell", max_run_seconds = 0
   INFO shepherd_core::engine: Policy reloaded entry_count=2      (3s later, unprompted)
   launch {"id":"attacker-shell"} -> {"Approved":{"deadline":null}}
```

`deadline: null` — supervised by shepherd, with no time limit, from a file write.
Also exposed: `<data_dir>/admin.toml`, which carries the minted HTTP token, and
the factory-reset sentinel.

## Why not confinement

Both candidates were built and measured before anything else was, and both are
dead ends. Full measurements in `docs/ai/history/2026-08-29 005`.

**Not Landlock.** It needs `no_new_privs`, which breaks `snap-confine` (file
capabilities: *"snap-confine is packaged without necessary permissions"* — Firefox
ships as a snap) and `pkexec` (*"pkexec must be setuid root"* — the firewall
helper's launch path). And it is escaped outright: `systemd-run --user` in service
mode, or a raw `StartTransientUnit`, hands back a fresh unrestricted process that
read the protected file and copied it out.

**Not AppArmor.** It closes both doors — the file *and* the escape, since it
mediates D-Bus — but the one rule that closes the escape
(`deny … StartTransientUnit`) also breaks `snap run`, which uses the same call for
its own scope, and AppArmor cannot match on call arguments. It is also a
**deny-list of spawn routes**, which is the shape [#158](./0158.md) explicitly rejected for the
socket: `cron` is active on a stock device too, and the next release will bring
another route.

**Not file permissions.** shepherdd runs at the uid it would be defending against.

## What does work

A uid boundary, gated by the check [#158](./0158.md) already built and verified. Every escape
route above produces a process at the **child's own uid**, so `0700` on another
uid's directory refuses all of them without having to know they exist.

`shepherd-stated` runs under the system manager as `shepherd-state` — **not root**;
it opens a SQLite file it owns, reads TOML it owns, and asks logind a read-only
question. It serves two directories over `/run/shepherdd/state/<user>.sock`:

| | | |
| --- | --- | --- |
| `/var/lib/shepherdd/state/<user>/` | the policy and the database | one per kiosk user |
| `/var/lib/shepherdd/admin/` | the BLE admin record, the unbond queue, the reset sentinel | one per **device** |

Both `0700`, both owned by `shepherd-state`, both created by the same
`StateDirectory=`.

| peer | verdict |
| --- | --- |
| a process in the kiosk's logind session scope — shepherdd | accepted |
| root, from any cgroup, so `sudo` still reaches it | accepted |
| anything else, including anything that cannot be identified | **refused at accept** |

The check is `PeerPolicy::for_cgroup`, the same `SO_PEERPIDFD` + `PIDFD_GET_INFO`
one-`u64` compare [#158](./0158.md) makes. Only the source of the number differs: this daemon
is deliberately outside the session, so it names the trusted cgroup rather than
comparing against itself. It resolves it from logind, requiring `class=user`,
`type=wayland`, a seat, and **not `closing`** — that last term came from a device,
where after `systemctl restart gdm` the outgoing session was still listed, still
seated, still owned a live cgroup, and logind had it `closing`.

**Socket activation, and it earns more than convenience.** `2026-08-29 004`'s
finding 2 concluded that stopping an activity taking a socket's *name* needs the
socket created by something other than the daemon — *"which `shepherdd` cannot use
while sway `exec`s it"*. This daemon can, so that class does not exist here:
`/run/shepherdd/state/` is root-owned and the kiosk uid cannot unlink it.

## One policy, and a signpost

`config.toml` is **moved** into the protected directory, like the database and
the admin record, and a signpost takes its place at
`~/.config/shepherd/config.toml` naming where it went and how to change it. One
file decides what a child may do, and it is the one at a uid no activity has.

An earlier draft of this kept a real copy at the home path — the seed migration
read, and the fallback shepherdd reads — with a `policy_diverged` diagnostic to
report when the two drifted apart. It worked, and it was the wrong shape: two
files that look equally authoritative, only one of which decides anything, and a
diagnostic whose whole job was to report the confusion the arrangement created.
Removing the second copy removed the need for it, and both are gone.

The signpost parses and grants nothing, but nothing reads it as a policy: a
device with a signpost has a custodian, and a shepherdd that cannot reach its
custodian refuses to start rather than running on whatever is in the home
directory (below). Keeping it valid is belt-and-braces — if some path ever does
read it, what it grants is nothing.

### Setting a policy

Three ways in, landing on the same file, all reloading within a second:

```sh
sudoedit /var/lib/shepherdd/state/kiosk/config.toml
sudo shepherd install policy --user kiosk --source ./new-config.toml   # from source
sudo shepherd-admin policy kiosk --source ./new-config.toml            # packaged
```

The `--source` forms exist because a hardened device has no route to the first
through the kiosk user: `harden apply` gives it `nologin` and denies it SSH, so
there is no `su` into it to edit a config in an editor. They take a policy from
anywhere an administrator can name and write it straight to the custodian.

**The `--source` forms validate first**, and `sudoedit` does not. shepherdd
tolerates an unparseable policy on *reload* — `reload_policy` keeps the running
one and logs — but at startup `load_policy` is fatal, and sway's fallback then
ends the session. So a typo costs nothing until the next boot and then costs the
session, on a device whose kiosk user has no shell to fix it from: the failure
surfaces at the greeter rather than at the terminal where it was made. A file
that does not validate is reported and not installed.

`shepherd-validate-config` ships in the package for this — it was a source-tree
binary, so before this a packaged device could not check a policy by any means.

Two things are refused rather than commented on, because both are quiet and
expensive: `install policy` will not push a signpost (that would replace a
device's policy with an empty one, every activity gone), and the migration will
not treat one as a policy to move, so re-running it does not move a file it
wrote itself.

## The claim is the device's, not a child's

The split above is the thing the second directory exists for, and it took a
wrong turn first. The custodian is templated per kiosk user, so putting the
admin record in its directory made the *claim* per-user — while the bond it
names is not. A BlueZ bond lives in `/var/lib/bluetooth` at one adapter, is
owned by root, and `Adapter::remove_device` forgets it for the whole machine.

A device with two kiosk users then behaved in ways nobody chose: a phone claimed
for the first arrived at the second already bonded, read `Unclaimed` there, and
could claim it too; and a factory reset for one user cleared that user's record
while queueing a `remove_device` that took the *system* bond with it, leaving
the other user's record claiming a bond that no longer existed — the mirror of
the lockout `PendingUnbondStore` exists to prevent, across a boundary the rest
of the design keeps carefully.

`ProtectedFile::scope` now says whether a file is a fact about a child or about
the machine, and `LocalProtectedFiles::scoped` routes each to its root. A device
*without* the custodian keeps one directory and both scopes in the kiosk user's
home: there is no protected root to share there, which is what a pre-custodian
device always had.

The migration splits accordingly, and where two users were separately claimed
before the custodian existed the **first wins** — one bond table means one
record, and picking the later one would discard a pairing that still works. The
one left behind is reported, not deleted. `--restore-to-home` un-merges: the
device's files are *copied* to every user's home and the shared originals
dropped only after the last one, because per-user is the arrangement being
restored.

What this does not fix is `authorize`, which gates on the claim and lets any
bonded peer through — an address that does not match the record is logged and
allowed under the v1 single-admin policy. That is [#149](https://github.com/aarmea/lunchbox/issues/149)'s answer to give, and it
wants the resolved identity or the IRK rather than whichever address BlueZ
surfaced. Two simultaneous graphical sessions are also untested: the custodian
refuses two sessions for *one* uid, so two uids with one each satisfies it, and
two `shepherdd`s would then contend for one adapter's GATT registration. Both
are written down in `crates/shepherd-ble/README.md` rather than left to be
rediscovered.

## Opting out

`--no-state-custodian`, its own flag rather than a third meaning on
`--no-restrict-ipc-peers`, following the reasoning that split that one: they are
different risks wanted at different times. One decides who may *drive* the daemon,
one decides which code it *runs*, and this one decides whether its state is
reachable by the software it supervises. Carried by `sway.conf` and the e2e
harness, asserted by the headless harness, and stripped by `shepherd install
sway-config` — which fails the install if the strip did not take. Disarmed, the
daemon is byte-for-byte what it is today.

## A custodian that was installed and cannot be reached is fatal

The fallback used to be justified by "an unprotected kiosk beats a child staring
at a dead screen". That held while the home directory still had a real policy
and a real database in it. Once migration *moves* them, falling back opens a
fresh empty database, finds no admin record, and reads a signpost that grants
nothing — so what it actually produces is a launcher with no activities on it.

That is the worst failure available, because it is **ambiguous**. An empty grid
looks like an ordinary evening with nothing available, or like something still
loading. Being returned to the login screen does not: it says something is
wrong, and the journal says what.

So the two situations that wore the same error are split:

| | |
| --- | --- |
| no custodian installed | **starts**, reports `state_not_protected` |
| custodian installed, unreachable | **exits**; the session ends at the greeter |

A device that never had one has nothing missing — its state is where it always
was — and refusing would be refusing over a protection it was never given. A
device whose state has *moved* is a different thing, and it names
`systemctl status shepherd-stated@<user>` in the message, because the journal is
where whoever meets this will be looking.

An earlier draft of this branch went the other way: it kept the fallback and
added machinery to make it survivable — `ClaimError::StateUnreachable`, a
`claims_unreachable` flag through `ClaimMachine` and `BleServerConfig`, and a
`custodian_expected` field carried through two enums to reach them — so that a
degraded device would at least not present itself for claiming. Failing closed
deletes all of it: a device that does not come up cannot be claimed. 232 lines
out, 128 in.

**An ambiguous session no longer spends restart budget.** Separately, `resolve`
refuses to choose between two graphical sessions, which is right, but it used to
refuse by failing — and the unit's own comment records where that ends: five
quick failures failed the *socket* unit, and every connection for the rest of
the boot was refused. A second session is transient in the ordinary case (a
`switch user`, a login overlapping a logout), so it is now waited out like the
no-session case and stops cleanly with the socket armed if it does not clear.
The safety property is unchanged — it still never guesses a cgroup — and the
wait now watches session *departures* too, since the ambiguous case is waiting
for a session to go and no arrival will ever signal that.

## Getting back out

The migration **moves** the database and the admin record, so it needed an exit
that is a command rather than an assumption:

```sh
sudo shepherd uninstall state --restore-to-home   # from source
sudo shepherd-admin restore-state                 # packaged
```

It stops the custodian first — it holds the database open for its whole life, and
moving a file from under a live writer is how a database gets a journal that no
longer matches it. Then each user's `shepherdd.db` (SQLite side files with it)
and policy go back to their home, the device's files are *copied* to every
user's home and the shared directory removed after the last one, and the units
come off. Every user under the state root, because an uninstall is already
device-wide and a device with two kiosk users would otherwise end up half moved
— and because per-user is the arrangement being restored, which is why the
device's files are copied rather than handed to whichever user came first.

Non-destructive in the same direction as the migration: a real file already in
the home is never overwritten, because on the way *out* that copy is the one the
older build will read. The signpost is the one exception, and it has to be — it
exists to say the policy lives elsewhere, and after this it does not.

`docs/INSTALL.md` gains **Operating a device after the state moved**, covering the
three habits that quietly stopped working: downgrading (above), backups (state is
now in two places, and neither `/home` nor `/var/lib` alone is enough — with the
uid note for restoring onto another machine, where `shepherd-state` may have a
different id), and reading the database by hand (`sudo sqlite3` leaves root-owned
`-wal`/`-shm` in a directory `shepherd-state` owns, after which the custodian
cannot write its own database; `sudo -u shepherd-state` is the form that works).

## Both CLIs can run it

The three operations above are new, and all three landed on `scripts/shepherd`
— which is not shipped. The `.deb` installs `shepherd-admin`, a slim entrypoint
over the same libraries, and it has no `install` or `uninstall` verb. So a
packaged device could enable the custodian and then neither populate it, set a
policy through it, nor get back out of it.

The first of those was the sharpest: `setup-user` enabled the socket and stopped
there, so the custodian came up owning an empty directory while the device's
usage history, quota balances and BLE admin record stayed in the home directory,
unread — an upgrade that looked like a factory reset. `warn_if_stale_home_db`
noticed and named `shepherd install state`, which is advice a packaged operator
could not take. `setup-user` now does the whole per-user half.

The other three are commands of their own:

| | |
| --- | --- |
| `shepherd-admin policy USER --source PATH` | install a policy, validated |
| `shepherd-admin migrate-state USER` | move a user's state under the custodian |
| `shepherd-admin restore-state` | move it all back, before a downgrade |

`restore-state` deliberately does less than `uninstall state --restore-to-home`:
it stops the custodian and moves state home, and leaves the binary and units
alone, because on a packaged device those belong to dpkg and `apt` is what
removes them. Deleting them behind its back is what `uninstall` already declines
to do to conffiles.

Each is a thin wrapper over the same function the from-source verb calls — the
shared halves were extracted rather than reimplemented, so the two CLIs cannot
drift about what these operations mean.

## One fact, one place

The policy problem above was one fact written twice with a comment holding the
copies together. The rest of the series was audited for the same shape, and it
had four more — one of which had already drifted into a bug.

**`unbond-queue.toml` was never migrated.** `ProtectedFile` lists four files;
`install.sh` carried its own list of what to move, and the queue of BlueZ bonds
still to be removed was not on it, although `PendingUnbondStore::custodial`
writes it into the custodian's directory. A pending unbond survived an upgrade
only where nothing reads it any more, so the bond it was queued to remove
stayed — the old phone still works after a factory reset, which is the one thing
a factory reset is for. Narrow window, exact opposite of the intent.

The two lists cannot become one list, so a test compares them.
`installer_covers_protected_files.rs` asserts every `ProtectedFile` is either
migrated or *declared* as deliberately left behind — the second category is
written down rather than merely omitted, so "decided against" reads differently
from "forgotten". It names the file and the array to add it to, and it was
checked against the real bug by removing `unbond-queue.toml` again.

It also checks the *scope* each file is filed under, which is the sharper half:
the list the installer moves a file to decides which directory it lands in, and
`ProtectedFile::scope` decides which directory the custodian serves it from. A
file the installer treats as a user's and the daemon reads as the device's is
one the daemon never finds.

**The systemd units restate three constants** — `ListenStream`,
`StateDirectory`, `User=` — that `socket_path`, `state_dir` and `STATE_USER`
also state, and systemd cannot call Rust. A drift there fails in the least
helpful way available: the manager binds one path, shepherdd dials another, the
connection is refused, and the diagnostic reads exactly like a custodian that
was never installed, with nothing pointing at the two files that disagree.
`units_match_the_constants.rs` compares them, including the `0700` that is the
boundary itself.

Both tests follow what this series already does elsewhere: `install sway-config`
fails the install if a flag strip did not take, and `headless.sh` dies if
`sway.conf` stops passing `--no-state-custodian`. A duplication that has to
exist gets something that breaks loudly when it drifts.

**The BLE admin record had two homes, and one of them was a config knob.**
`admin_record_path` and `reset_sentinel_path` let an operator put the record and
the factory-reset sentinel anywhere, which is what forced `AdminStore` and
`PendingUnbondStore` to carry a two-variant `Backend`: `ProtectedFiles` can
express "a named file in the custodian's directory" and nothing else, so the
configurable arm needed a path-based implementation beside it.

Both knobs were already dead on any device with the custodian — `BleServer::new`
took the other arm and never read them — while staying editable in the config
editor and documented in `config.example.toml`. An administrator could type a
path, save it, push it, and have nothing happen: the same trap the policy had,
one field over. The commented example even pointed at
`/var/lib/shepherdd/admin.toml`, outside the custodian's per-user directory, so
following it would have asked for the HTTP bearer token to sit back at the uid
activities share — had it been honoured at all.

Nothing set them: no config in the tree, no fixture, no test, no harness. So
they are gone, and the two-backend design with them — `Backend`, both
`Option<&Path>` accessors, `pending_unbond_path`, the path-based
`check_reset_sentinel` and the branch in `BleServer::new`. `BleServerConfig`
takes one `Arc<dyn ProtectedFiles>`, which shepherdd fills with the custodian's
handle or a `LocalProtectedFiles` over the data directory. 327 lines out, 169
in.

That also dissolved a coupling: `files` used to be `policy_files`, which is
`None` when the custodian holds no *policy* — so a custodian serving a perfectly
good admin record would have been ignored for it over an unrelated migration
gap. The two handles are separate now, each gating only what it decides.

One more name unified on the way: the unbond queue was
`ble-pending-unbond.toml` locally and `unbond-queue.toml` custodially — the same
queue under two names depending on which arm built it.

**The `Store` method list was written out three times** — the `StateRequest`
variant, the client method that builds it, and the server arm that turns it back
into a call. Two of those the compiler checked: a generated
`impl Store for RemoteStore` does not compile if a method is missing or
mistyped. The third it could not, and that was the dangerous one — an arm
calling a *different* store method than its variant names typechecks perfectly,
and only a test stood between that and a device writing the wrong row.

`crates/shepherd-state-proto/src/methods.rs` holds the list once and hands it to
a callback macro, so the three sites stay in their own files and none restates
it. The client method and the server arm for a method now come from the same
line and cannot disagree about which method that is; the test that used to be
the only guard is a regression guard now. The one part that is not mechanical —
how each argument crosses the wire — is five modes with a table in the module
docs.

`is_healthy` is the single exception, written out at all three sites: it returns
a bare `bool` rather than a `StoreResult`, so it has nowhere to report a broken
connection and cannot share the generated shape. Deliberately *not* a proc macro
on `trait Store` itself, which would remove the last copy at the cost of putting
this protocol inside `shepherd-store` — a crate with no business knowing there
is a socket.

467 lines out and 142 in across the three sites, against 202 in the new table:
roughly even in total, and `get_usage` now appears in exactly one file. It also
took `PROTO_VERSION` to 2, because generating the no-argument variants makes
them struct variants with no fields — `{"LoadSnapshot":{}}` rather than
`"LoadSnapshot"`. Both ends ship together, so that can only surface as a
half-finished upgrade, which is what the handshake refuses.

**Smaller:** `bluetooth.sh` had its own copy of the custodian's directory with a
comment saying it "must match install.sh's", plus its own spellings of
`admin.toml` and `.factory-reset-ble`; it sources `install.sh` now. `admin.sh`
called install.sh's functions while only *documenting* that an entrypoint would
have sourced them — it held by luck of ordering, and broke the moment anything
sourced it alone; it declares the dependency now. The socket unit's instance
name was spelled out at both `systemctl enable` sites and is built in one place.

- **`fix(codegen)`** — every wire enum the companion decodes gains an `UNKNOWN`
  fallback and a custom serializer, so a phone one release behind degrades a value
  it does not know rather than failing the decode of everything around it. Needed

  `WireTypes.generated.kt` and `wire-types.generated.ts` are in the diff.
- **`fix(install)` for [#172](https://github.com/aarmea/lunchbox/issues/172)** — `sway.conf` starts the daemon as
  `… shepherdd … || swaymsg exit` so a failed shepherdd leaves no unsupervised
  compositor. Since [#144](https://github.com/aarmea/lunchbox/issues/144) shepherdd unlinks sway's IPC socket — but only *after*
  it has connected, so a startup failure (a bad policy, say) still finds the
  socket and still ends the session. What breaks is the other case: a daemon
  that dies once it is running has taken the socket's name away, and `swaymsg`
  then has nothing to connect to. The installer rewrites it to
  `loginctl terminate-session "$XDG_SESSION_ID"`, which needs no compositor socket
  and no polkit authorisation. Rewritten at install rather than in `sway.conf`
  because a development sway inherits the developer's own `XDG_SESSION_ID`. [#172](https://github.com/aarmea/lunchbox/issues/172)
  stays open — the wrapper runs at the kiosk uid, so an activity can kill it
  before shepherdd and leave nothing to run the fallback, and shutting that door
  needs a watcher the child cannot signal.
- **`fix(e2e)`** — the harness counted every matching process on the host, so an
  unrelated one made it fail or pass for the wrong reason.

## Breaking changes

- **`~/.config/shepherd/config.toml` is no longer the policy.** Installing the
  custodian moves it to `/var/lib/shepherdd/state/<user>/config.toml` and leaves
  a signpost at the old path. Anything that wrote a policy there — an Ansible
  template, an scp from a build host, a config editor's save — now writes a file
  the daemon does not read. Use `sudoedit` on the custodian's copy, or
  `sudo shepherd install policy --user <user> --source PATH`.
- **The `policy_diverged` diagnostic is gone**, along with `DiagnosticCode`'s
  variant, and is removed from the generated TypeScript and Kotlin. It reported
  that two policy files disagreed; there is one now. Anything matching on that
  code should drop the arm — a companion that predates this build is unaffected,
  since the value simply stops arriving.
- **`--force` is gone** from `shepherd install config`, `install all` and
  `shepherd-admin setup-user`. Under the custodian it was the worst of both: it
  replaced the copy in the home directory and left the custodian's — the one
  shepherdd reads — untouched, so the operator saw "Overwrote user configuration"
  and the device kept running the old policy. Replacing a policy is
  `install policy`'s job, which writes the file that decides what a child may do
  and validates before it does. Scripts passing `--force` now fail loudly rather
  than silently doing nothing.
- **A device whose custodian is installed and unreachable no longer starts.**
  shepherdd exits and the session ends at the login screen, rather than running
  on an empty database with a launcher that has nothing on it. A device with no
  custodian is unaffected and still boots with `state_not_protected`. This is
  the one place the branch prefers a visible failure to a working-looking one,
  and the reasoning is in the section above.
- **Rolling back needs `--restore-to-home` first.** The database, admin record
  and policy are *moved*; an older shepherdd finds nothing, opens an empty database, and with
  no `admin.toml` reports itself unclaimed — a factory reset by another name. Run
  `sudo shepherd uninstall state --restore-to-home` before downgrading.
- **The factory-reset sentinel moved**, and has no kiosk user in its path:
  `sudo touch /var/lib/shepherdd/admin/.factory-reset-ble`. A reset forgets the
  machine's one BlueZ bond, so it is the device's instruction, not a user's. Any
  runbook or script naming the old path — under the data directory before the
  custodian, or under `state/<user>/` in an earlier draft of this branch — does
  nothing at the new one, silently, because a sentinel that is not there is
  indistinguishable from one already consumed.
- **`admin_record_path` and `reset_sentinel_path` are removed from the config**,
  along with their two fields in the config editor. They pointed the BLE admin
  record and the factory-reset sentinel somewhere other than the custodian, and
  on a device with one they were already ignored. A config that sets either is
  now rejected as an unknown key rather than silently doing nothing. Nothing in
  the tree set them, and the defaults they carried are what every device used.
- **The package ships one more binary**, `shepherd-validate-config` at
  `/usr/bin`. It was a source-tree tool called `validate-config`; `install
  policy` validates before installing and a device has no source tree to build
  it from. Renamed on the way in, because shipping it put a bare
  `validate-config` on every device's `$PATH` — a name this project has no claim
  to, and it was the only binary in the set without the prefix. No compatibility
  shim: it has never been installed under the old name, so nothing on a device
  can be calling it.
- **New system user and units**, both surviving uninstall by design — discarding a
  device's usage history and BLE admin record is not something an uninstall is
  entitled to do.
- **Rust API**: `AdminStore::path()` / `PendingUnbondStore::path()` return
  `Option<&Path>`; `BleServerConfig` gains `files`.
- `SHEPHERD_DATA_DIR` no longer selects the protected state. It still governs the
  unprotected remainder (child logs, RetroArch saves).

## Testing

Unit and integration tests cover the peer rule (including the `closing` row that a
device taught us), the wire in both directions, and shepherdd's two failure
reports. `tests/round_trip.rs` runs both halves of the protocol over a real socket
and asserts on the **server's** store rather than the client echoing itself,
exercising all 26 `Store` methods. It was written because a dispatch arm wired
to the wrong method typechecks; generating the two sides from one table closed
that by construction, so the suite is a regression guard now rather than the
only thing catching it — and it covers the generated dispatch unchanged.

Green on the current base: `cargo test --workspace --all-targets` 1184 passed / 0
failed, `cargo test -p shepherd-e2e -- --include-ignored` 17 passed,
`clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all --check`,
`shellcheck`, the web UI suite (83 tests, import boundary, typecheck, 137/137
schema fields reachable — two fewer than before, being the two removed knobs), the companion's `:app:testDebugUnitTest`, `shepherd version check` and
`shepherd-validate-config config.example.toml`. The test run sets
`SHEPHERD_REQUIRE_PEER_CGROUP=1` as CI does, so the peer-cgroup tests this series
touches turn a skip into a failure rather than passing silently.

Rebased twice and re-verified after each. The first, onto `e75344d`, had one
substantive delta: `HudOrientation` regenerated under this series' tolerant-enum
codegen, which the drift test caught rather than a reviewer. The second, onto
`7796c8d` once [#176](./0176.md) had merged, replayed all 23 commits with no conflict and no
delta at all — the branch's own patch is byte-identical against either base,
compared hunk by hunk.

[#176](./0176.md) was checked against this series before it merged, and the seam is worth
recording because it is semantic rather than textual: [#176](./0176.md) makes the billed day
`session.started_at.date_naive()` while this series moves the store behind an
RPC. It composes because the day is a *parameter* —
`add_usage(entry_id, day, duration)` — that `RemoteStore` forwards verbatim. A
store that derived the day itself would have made the two a real collision.

The shell paths were verified against a temporary state root rather than
reasoned about, since none of them run in the dev harness. `install policy`:
a valid policy installs `0600` at the custodian's uid, an invalid one is refused
with the parse error and leaves the previous policy in place, a missing
validator dies naming `shepherd build`, and a signpost is refused by name.
Migration: a real policy moves and is signposted, the signpost validates as an
empty config, re-running moves nothing, a fresh install puts the example at the
custodian, and a device without a custodian is unchanged.
`--restore-to-home`, against a fixture with a real database row, a `-wal` side
file, an admin record and a pending unbond queue: the row survives, the side
file travels, the policy comes back over the signpost, the queue comes with it,
and a second run refuses to clobber what it restored. The packaged verbs the
same way, plus a real `.deb` built and inspected — twelve executables, every one
of them `shepherd*`, the postinst naming the new commands, and CI's xz and
arch-neutrality assertions still holding.
