## Description

The Response/Events poll loop `break`s on a read failure and the outer
loop's `ready.first { it }` returns immediately while `ready` is still
true. When kable reports the peripheral Connected while every read throws
NotConnectedException (a flaky / BT-toggle reconnect), the loop spins at
millions of iterations/sec on the main-thread dispatcher — pegging a
phone core, flooding logcat, and starving both the response poller and
the state collector that would set `ready=false`. RPCs then hit the 15s
`REQUEST_TIMEOUT_MS` and the UI wedges. This is the "unresponsive after
connecting/reconnecting several times" report.

On a read failure, never hot-loop: back off with the adaptive poll delay
(which also yields the dispatcher so the state collector can run) and,
after MAX_CONSECUTIVE_READ_FAILURES (~1.5s), force a real
`peripheral.disconnect()` so the reconnect loop rebuilds the session.
Reset the counter on any successful read.

Verified on-device: a BT-toggle reconnect that previously produced
5.4M log lines / 691MB / a pegged core now yields 2 read failures, 0%
app CPU, and a clean reconnect. compileDebugKotlin + testDebugUnitTest
pass.
