## Description

Follows 2026-09-05's `refactor(codegen): generate the per-kind config defaults`,
which did this for the answers a *kind* supplies. This does it for the rest.

The config editor's job for an unset field is to render the value the daemon
will actually pick — an unset switch as on or off, an empty number field with
the fallback as its placeholder, a slider with the inherited value on its track.
It did that by restating the Rust, in about forty places:

```tsx
checked={value?.disable_dev_tools ?? true}
const policy = value?.default ?? "deny";
const DEFAULT_COOLDOWN_MIN_SESSION = 120;
placeholder="2m"
<MenuItem value="">Top (the default)</MenuItem>
```

Which is precisely the drift the generated wire types exist to prevent: `tsc`
checks TypeScript against TypeScript and cannot see the Rust rule it claims to
copy. Nothing anywhere would have noticed the daemon moving.

## Two mechanisms, only one of which was reachable

The daemon applies defaults two ways, and the split is what decided the work.

**Serde defaults** — `#[serde(default = "…")]` on a `RawConfig` field — were
already there for the taking. `schemars` reads the attribute and writes the
value into the JSON Schema, so all **69** of them (42 on plain structs, 27
inside `kind` variants) needed no Rust-side work at all. Purely a rendering step.

**Load-time defaults** are `Option<T>` fields whose `None` means *"fall back"*,
resolved in `Policy::from_raw` long after deserialization. `schemars` sees only
`"default": null` and has nothing to say. These got the `EntryKindTag`
treatment: a new `shepherd-config::LoadTimeDefaults` collects the twelve the
editor needs, and `from_raw` reads the same constants it does.

Three of those were literals with no name — `3600` inline in `from_raw`, the
management API's `7890` and `300`, and `1.0` for the token earn ratio — and a
value nobody names is a value nobody can generate, so they became
`DEFAULT_MAX_RUN`, `DEFAULT_MANAGEMENT_API_PORT`,
`DEFAULT_MANAGEMENT_API_BIND_RETRY` and `DEFAULT_TOKEN_EARN_RATIO`.

The output is `field-defaults.generated.ts`, three tables in one file:

| Table | Source | Keyed by |
|---|---|---|
| `FIELD_DEFAULTS` | JSON Schema | the `Raw*` type that declares the field |
| `KIND_FIELD_DEFAULTS` | JSON Schema, `oneOf` variants | the `kind.type` |
| `LOAD_TIME_DEFAULTS` | `LoadTimeDefaults::current()` | the config key |

`RawConfig.service` and the like are dropped on the way out: a populated object
default is a nested struct expanded in place, whose own defaults are already
rendered under that type's name, and repeating them would churn the file on
every unrelated schema change. An *empty* object is kept — `env: {}` is a real
leaf value.

## Three checks, each verified to bite

The existing drift test covers the generated file's **contents**. It does not
cover everything that can go wrong here, so two more sit alongside it.

| Check | Catches | Proven by |
|---|---|---|
| `rpc_codegen_drift` | the generated file stale against the Rust | edited it; the test named the file |
| `defaults.test.tsx` (new) | a component that imports the constant and then still compares to a literal | restored `placeholder="5m"`; the test failed |
| `load_defaults.rs` (new) | a `from_raw` call site drifting from its constant | hardcoded `1800` at the call site; the test failed |

The middle one is the one worth arguing for: the drift test sees the file, not
whether any component reads it, so a migration that changed the imports and
nothing else would have passed everything. `defaults.test.tsx` renders real
controls with nothing set and asserts the generated value is what comes out, one
test per mechanism.

The third has a limit worth stating, because the first version of it was
tautological and I only noticed by trying to break it. It parses a config that
sets none of these fields and asserts the advertised values are what the parser
produces. That catches a call site drifting from its constant — the failure that
put the editor and the daemon out of step in the first place. It **cannot** catch
*changing* a constant, because both sides read the same one and both move
together. That is the design rather than a gap: a changed constant flows through
`current()` into the generated TypeScript on the next codegen run, and the drift
test fails until someone makes that run. The module doc says so.

## What [#171](https://github.com/aarmea/lunchbox/issues/171) added, and why it is in here

Rebased once onto `feat/171-hud-on-the-side` before it merged, because that
branch is the first thing to land a new default since — and it landed one of
exactly the invisible kind. `[service.hud] orientation` is an `Option` resolved
by `HudOrientation::default()`, and the Device page named the answer in prose:

```tsx
<MenuItem value="">Top (the default)</MenuItem>
```

That row is now `{DEFAULT_HUD_ORIENTATION_LABEL} (the default)`, a new export in
`hudOrientation.ts` that takes the generated value and looks its label up in the
list both menus already share, so the wording stays in one place.

[#171](https://github.com/aarmea/lunchbox/issues/171)'s own test asserts the literal `"Top (the default)"`, and I left it that
way rather than migrating it. Setting the generated value to `"bottom"` makes it
fail with `expected 'Bottom (the default)' to be 'Top (the default)'` — which is
a good tripwire to leave in place, naming both edges when someone changes the
Rust default.

## Two deliberate non-migrations

Both commented where a future reader would otherwise "fix" them, and stated in
`load_defaults.rs`'s module doc:

- **`clamp_volume`'s `unwrap_or(0)` / `unwrap_or(100)`**, and the editor's
  matching `?? 0` / `?? 100`, are the extents of a percentage slider — not a
  fallback an admin could have configured differently. Listing them would make
  the generated file a grab-bag of unrelated literals.
- **The internet section's seed writes a 300s interval**, which is what
  `config.example.toml` recommends and not the daemon's 10s fallback. Changing
  it would change behaviour for anyone who toggles the section on, which is not
  what a refactor is for. Left alone, with a comment saying which number is
  which — and the real fallback now appears as the field's placeholder, where
  before it was invisible.

That last point generalised: the migration surfaced **four defaults the editor
had never shown at all**. The Steam launch timeout, the media watched-grace, and
the internet check interval and timeout were blank fields with no placeholder,
so an admin had no way to learn what leaving them empty meant.

## For whoever adds the next default

A serde default needs nothing but a codegen run. A load-time one means adding a
field to `crates/shepherd-config/src/load_defaults.rs` as well, or the editor
goes back to guessing — its module doc says what belongs there and what does
not, and `CONTRIBUTING.md` gained a "Generated defaults" section covering both
paths.
