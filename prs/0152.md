## Description

Fixes [#151](https://github.com/aarmea/lunchbox/issues/151).

The embedded BPF object was included with `include_bytes!`, which yields
alignment-1 data. aya hands the slice straight to the `object` crate, whose ELF
header parse is a zero-copy cast that rejects anything not aligned to
`align_of::<elf::FileHeader64>()` (8). So `apply-cgroup` loaded only when the
linker happened to place the blob on an 8-byte boundary — a per-build coin flip
that any unrelated change to the helper's rodata can lose.

When it lost, every Flatpak and Snap entry with `[entries.firewall]` ran
completely unfiltered, and the only trace was one `warn!` per launch.

Three commits: the fix, failing closed, and the CI coverage that would have
caught it.

## 1. Embed the BPF object aligned (`82a56ae`)

```rust
static BPF_OBJ: &[u8] = include_bytes_aligned!(env!("SHEPHERD_FIREWALL_BPF_OBJ"));
```

aya ships this macro for exactly this problem (a `#[repr(align(32))]` wrapper).

Measured on an independently built helper (so this was never specific to
`copernicus`): the embedded `EM_BPF` object sat at vaddr `0x1953c` — **4 mod
8**. Extracting those bytes and running `readelf` on them gives a perfectly
valid `ELF64 REL / Machine: Linux BPF` object. Nothing was wrong with the BPF
program or the build; only its address was wrong. After the fix the blob in
`target/release/shepherd-firewall-helper` sits at `0x19b80`, 0 mod 32.

This also debunks the comment that stood above the failing call, which blamed
"monomorphization" for load failures when the `{e:?}` was removed from the error
closure. Adding or removing that formatting shifted rodata, moving the blob on
and off an 8-byte boundary. Replaced with a note recording the real cause; the
`{e:?}` itself stays, since `ParseError::ElfError` hides its inner error from
`source()`.

Guarded by `bpf::tests::embedded_bpf_object_is_aligned_and_parses`: asserts the
alignment, then calls `Ebpf::load` and fails only on `EbpfError::ParseError`
(everything past the parse needs `CAP_BPF`, which an unprivileged test run does
not have). Reverting just the include fails it.

## 2. Fail closed (`12f9e9f`)

Snap and Flatpak apps run in a scope their runtime creates, so the filter can
only be attached after the app is already running. Until now a failed attach was
one `warn!` and nothing else — the activity kept running with unrestricted
network. That is why this bug survived: an entry configured `default = "deny"`
browsed the internet freely, and the only person who could have noticed was
reading the journal.

`LinuxHost::spawn_firewall_guard` replaces the fire-and-forget `tokio::spawn`.
On failure it:

- kills the activity via `kill_activity`, which knows the snap/flatpak cgroup
  routes — signalling our direct child would miss an app the runtime put in a
  scope of its own;
- ends the session as `HostEvent::LaunchFailed`, not `Exited`, so the engine
  skips usage settlement and the child is not billed for an activity that was
  yanked out from under them ([#135](https://github.com/aarmea/lunchbox/issues/135));
- hands a survivor to the reconciliation sweep ([#136](https://github.com/aarmea/lunchbox/issues/136)) rather than leaving an
  unfiltered activity running with nothing supervising it;
- leaves an already-exited activity alone — a child who closed the app during
  the attach window did not suffer a launch failure, and ending the session
  twice would end whatever launched next.

`apply_firewall_to_existing_scope` now returns `Result<String, String>` so the
reason reaches the end reason and the audit log.

**The trade, stated plainly:** a host where the runtime never creates a scope
(no systemd user manager, say) now loses these activities ~5s in, loudly,
instead of running them unprotected, quietly. Documented in
`crates/shepherd-host-linux/README.md`.

Two tests drive real processes: `an_unappliable_firewall_ends_the_activity`
(mutating the guard back to fail-open fails it) and
`an_already_exited_activity_is_not_reported_as_a_launch_failure`.

## 3. CI coverage for the cgroup path (`8a05a30`)

`firewall_real` is the only firewall test CI runs, and it covers the Process
kind — which wraps the launch in `systemd-run` and lets systemd attach the
filter. It never loads the embedded BPF object, which is why this shipped.

`crates/shepherd-e2e/tests/firewall_cgroup.rs` creates a cgroup, has
`apply-cgroup` attach the program to it, then runs the existing
`run-firewall-probe.sh` inside that cgroup and asserts `allow=OPEN`,
`deny=BLOCKED`. No flatpak, no snapd, no polkit, no systemd user session, no
internet — just root and cgroup v2, which the existing privileged sidecar in the
`firewall` job already has. It runs there as root, before the workspace is handed
to `tester`.

Hermetic by construction: the allowed target is a loopback listener and the
denied target is a listener on *this host's own* routable IPv4 (found by
connecting a UDP socket to `192.0.2.1:9`, which sends nothing but consults the
routing table). A pre-flight connect from outside the cgroup proves the denied
target was reachable to begin with, so `BLOCKED` can only be the firewall.

`SHEPHERD_FIREWALL_CGROUP_REQUIRED=1` (set in CI) turns the "not applicable
here" skips into failures. That is deliberate: the flatpak and snap tests print
`[SKIP]` and exit 0 on a host that cannot run them, which reads as a pass.

`scripts/integration-tests/test-firewall-cgroup.sh` runs it locally — builds as
the invoking user, elevates only the run, so `target/` does not end up
root-owned.

## Verification

- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D
  warnings`, `cargo test --workspace`: clean.
- `firewall_cgroup` on `shepherd-26.04` (kernel 7.0, cgroup v2), three ways:
  - fixed helper → passes (6.2s, dominated by the probe's 6s deny timeout);
  - helper reverted to plain `include_bytes!` **and padded so the blob lands at
    1 mod 8** → fails with the issue's exact text,
    `ParseError(ElfError(Error("Invalid ELF header size or alignment")))`;
  - no-op helper that exits 0 without attaching → fails with `denied target ...
    was OPEN, expected BLOCKED`, so the assertion is not vacuous.
- Worth noting: the *unpadded* revert happened to land aligned in that build and
  passed. That is the character of this bug, and why the alignment assertion in
  the helper's unit test earns its keep alongside the integration test.

## Watch on the first CI run

Whether the sidecar's `/sys/fs/cgroup` is writable under `--cgroupns=host`. If
it is not, `REQUIRED=1` makes the job fail loudly rather than skip — the right
behaviour, but it will be the first thing to check if the `firewall` job goes
red.

## Not in this PR

From the options written up in the history note:

- a `wait_for_scope` unit test against a fake hierarchy (cheap, covers the
  `app-flatpak-<id>-` / `snap.<n>.<n>-` naming contract);
- the real flatpak probe in CI — `test-firewall-flatpak.sh` already builds and
  drives it, so what is missing is plumbing: flatpak baked into the base image,
  `flatpak build-init` with the Platform as its own SDK to avoid the ~1.5 GB
  Sdk download, and `loginctl enable-linger` for the test user so a systemd
  **user** manager exists to create the scope this path polls for;
- snap, same shape but snapd in a container is far more trouble.

Full write-up, including how the root cause was measured, is in
`docs/ai/history/2026-08-25 001 firewall bpf object misalignment (#151).md`.
