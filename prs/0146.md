## Description

Closes [#124](https://github.com/aarmea/lunchbox/issues/124).

Volume limits can now be set **per audio output**, so headphones can be capped
lower than speakers, and the displayed volume follows the selected output
instead of going stale. On top of that the management surfaces can now **choose**
which output sound plays through, which is what makes the per-device limits
usable without walking over to the machine.

## What a parent sees

A "Volume limits per device" card in the web admin UI and on the companion.
Devices appear once they have been plugged in; each row has a switch, a maximum
slider, a "Use this" button, and Forget.

- **Set a cap per device.** The strictest limit always wins — a per-device limit
  can lower the global `[service.volume]` cap but never raise it, and an
  activity's own limit combines the same way.
- **Caps bite immediately.** Setting one turns the volume down there and then;
  arriving on a capped output turns it down on arrival, whether the parent chose
  it or a jack insert did.
- **Choose the output.** "Use this" moves the sound. A device that is not
  plugged in keeps its row (so its cap is already set for next time) but the
  button reads "Not connected" and is disabled.
- **Everything stays in step.** The HUD, the browser and the phone all follow a
  sink switch made anywhere — including one made by the hardware.
- **A failed read says so.** If the audio devices cannot be read, the list keeps
  showing what was last true instead of claiming nothing is plugged in, the caps
  keep applying, and a condition appears on the device's warning channel until a
  read succeeds.

There is deliberately **no TOML for this**. `config.toml` is never written by the
daemon, so UI-set caps live in the store, following the auto-brightness
precedent: the stored value wins when present, config is the default when
absent. Audio hardware cannot be predicted well enough to hand-write a matcher
(see the scope doc), so the parent plugs the device in once and sets a limit on
the row they recognise.

## How it works

- Outputs are keyed `<device.name>:output:<route.name>` — byte-for-byte the key
  WirePlumber itself uses to persist per-route volume, so our notion of "an
  output" cannot drift from the volume PipeWire remembers for it. Matching on
  sink node name alone silently fails for the headphones-vs-speakers case the
  issue names, because plugging headphones into an analog jack changes the
  *route* and leaves `node.name` untouched.
- One `pw-dump` per read yields the reading, the active output and the full
  device list as a single `AudioSnapshot`, so no two fields can describe
  different moments. That torn-pair bug was caught by testing, not review.
- A 2s watch loop reacts to anything that changes behind the daemon's back — a
  jack insert, a dock, a bare `wpctl` call, a device appearing or disappearing —
  and broadcasts the whole volume state rather than just the number.
- Object ids are never stored. PipeWire recycles them across restarts and
  re-plugs, so the one `wpctl set-default` that needs an id resolves it from the
  dump it is used with.

Advisory `kind` (headphones / speakers / HDMI / …) drives only an icon and a
label. It cannot be determined for every device — a generic USB interface
reports a nondescript route and no udev form-factor — so `Unknown` is routine
and nothing depends on it.

## Fixes picked up along the way

Each is in its own commit. All but the first were found while validating; the
first came out of reviewing how this code talks to PipeWire at all.

- **A failed topology read was indistinguishable from an empty one, and it
  relaxed the caps.** `audio::dump()` returned `Option`, so "pw-dump is not
  installed" and "pw-dump ran and failed" arrived as the same `None`, and on a
  host already detected as PipeWire `observe()` turned that into an empty
  snapshot — byte-identical to a machine with no sinks.
  The serious half was a **fail-open**: `volume_restrictions()` resolved the
  active output through a read that answers `None` on failure, and
  `volume_restrictions_for(None)` falls back to the *global* limit, so
  headphones capped at 30 accepted 80 for as long as the fault lasted. A cap
  that relaxes itself under a fault is worse than no cap. It also blanked both
  device lists, since every stored row came back `available: false` — a
  transient fault rendered to the parent as "nothing is plugged in", on the one
  screen they would use to fix it.
  `dump()` now returns `Result` and keeps the two cases apart; `observe()`
  propagates rather than inventing an empty topology; and each caller decides
  what it knows. The restriction lookup and the ceiling enforcement fall back to
  the last output seen, which can only make the ceiling stricter — enforcement
  is the last place that should give up on a failed read. `get_volume` degrades
  to the bare reading instead of failing, because blanking the volume on every
  surface is a worse answer than the right number attributed to the last known
  output. `list_audio_outputs` reports the last liveness seen. The watch loop
  skips the tick instead of baselining an empty topology and raises
  `AudioTopologyUnreadable` on the [#143](https://github.com/aarmea/lunchbox/issues/143) channel, which clears itself on the next
  successful read.
  Independent of [#148](./0148.md): it lands the same "unreachable is not empty" discipline
  on the audio seam without touching the poll.
- **An unreadable volume was reported as 0%.** The same defect class, one layer
  down, and it matters more since the fix above: `get_volume` falls back to
  `get_status` when the topology cannot be read, so the degraded path was the
  one still able to invent a number. None of the three backends checked the exit
  status, so a command that failed fed an empty string to a parser that answered
  `0` — a plausible reading a parent could act on, indistinguishable from
  silence. `wpctl` did it via `.unwrap_or(0)`; `pactl` swallowed the spawn error
  outright with `if let Ok(output)` and reported an unreadable mute state as
  *not muted*, which is the wrong way round to be wrong; `amixer` left the same
  zeroed default when no line matched. Each reader now refuses output that did
  not run or does not parse, and the parsing moved into pure functions so the
  failure cases are testable with no sound backend present — nothing covered
  that layer before. A genuine 0% still reads as 0%.
- **The web UI received no events at all on a claimed device.** `sseUrl()` put
  the token in a query parameter, because `EventSource` cannot set headers;
  `require_auth` only reads `Authorization`. The stream 401'd and closed, so the
  UI only ever updated from its own mutations — it never followed a sink switch,
  and could silently write a stale cap back over one set from the phone. Both
  halves predate this branch. `useEvents` now streams with `fetch` and a Bearer
  header; the auth surface is unchanged and no credential goes in a URL.
- **The per-device switch shipped with no accessible name.** `inputProps` was
  removed in MUI v7 and this project is on v9. It was also a type error the
  whole time, which leads to:
- **Nothing typechecked the web UI.** `npm run build` goes through rsbuild,
  which transpiles without checking types, and there was no script for CI to
  run. Adds `npm run typecheck` and a CI job; confirmed it fails on exactly the
  bug that motivated it.
- **The two UIs were not the same control.** Same row, different behaviour in
  four ways: the first-use default (80 in the browser, 50 on the phone), whether
  off-then-on restored your number or reset it, a stale draft, and only one side
  disabling the row mid-write. All four now agree. Fixing the second exposed a
  fifth: the Compose rows had no `key`, so per-row slider state was positional
  while the device reorders rows on every sink change.
- **`IpcServer::shutdown()` deleted whatever socket was at its path.** Two
  daemons briefly overlapping — routine when a dev session is stopped and
  restarted in one breath — ended with the outgoing one unlinking the socket the
  incoming one had bound: healthy daemon, every client looping on `No such file
  or directory`. It now removes only the file it bound.

## Generated client types

Separable from the feature — it is one commit and could land on its own — but it
came directly out of this branch: adding a `DiagnosticCode` variant regenerated
the companion's Kotlin mirror automatically and left me hand-editing the web
UI's `types.ts`, where nothing would have failed if I had forgotten.

`shepherd-webui/src/api/types.ts` was 27 hand-written types mirroring the Rust
definitions with nothing connecting them. `tsc` checks TypeScript against
TypeScript and cannot see the daemon's shape, and the drift test only compares
codegen *outputs* against their checked-in copies — a file that is not an output
is invisible to it. That is the exposure that let the companion's Kotlin mirrors
drift twice (four missing `ReasonCode` variants; a renamed `DailyOverride` field
that broke every override lookup on the phone), which is why those are generated.
The web UI kept the hand-written mirror only because it had not yet been caught
doing the same thing.

Adds `ts_types.rs`, the TypeScript counterpart of `kotlin_types.rs`, rendering
the same wire JSON Schema to `wire-types.generated.ts`; `types.ts` re-exports it
and keeps only the presentation helpers.

**The drift test was never running in CI.** The codegen crate sits outside
`default-members` so `cargo build` never compiles `schemars` into the shipped
binaries — and the side effect was that `cargo test --all-targets`, exactly what
`ci.yml` ran, skipped the crate entirely. The check that `wire_schema.rs`
describes as failing CI on a stale mirror has never once run there. CI now uses
`--workspace`. Confirmed both directions: the bare command finds zero drift
tests, `--workspace` finds one, and removing a variant from a generated file
fails it.

Two deliberate differences from the Kotlin renderer, documented at the top of the
module:

- **Everything generates.** Kotlin skips `Event`, `EventPayload` and
  `LaunchOutcome` because kotlinx cannot express a `$ref` flattened beside its
  tag, or an externally tagged enum, as a sealed class. TypeScript's structural
  types make both ordinary, so `HAND_WRITTEN` is empty.
- **No `Unknown` fallback variant.** The Kotlin sealed interfaces each carry one
  because the companion is installed separately and can lag the device. The SPA
  is embedded into `shepherdd` at compile time, so it cannot skew; absorbing
  unknown values would buy nothing and would cost exhaustiveness checking.

The generated types are stricter than what they replace, and caught a live bug:
`AudioOutputsCard` tested `record.max_volume !== null`, but the field is optional
on the wire, so an absent one would have read as a cap that *is* set and pushed
`undefined` into slider state. Five fields in `shepherd-api` really do use
`skip_serializing_if`, so `?: T | null` is the honest rendering and the call site
was what was wrong.

## Documentation fixes

Two doc-only commits, separable from the feature and easy to drop:

- **`CONTRIBUTING.md` told you to run `./gradlew` directly but never mentioned
  the SDK path.** `deps install android` installs to `/opt/android-sdk`, not the
  `~/Android/Sdk` the toolchain probes, and `local.properties` is git-ignored —
  so every Gradle task dies in seconds with `SDK location not found`. CI never
  catches this because its Android job runs in a container that already exports
  `ANDROID_SDK_ROOT`, meaning a green CI run is no evidence a bare `./gradlew`
  works in your shell.
- **The `companion-pairing` skill claimed there is no config knob for adapter
  selection.** There is: `[service.ble_management]` takes an `adapter` address.
  This matters because on a host with two radios the daemon serves whichever
  BlueZ lists first, which need not be the one the phone is bonded to — the
  symptom is an endless "Connecting…" against a daemon that logs
  `BLE management advertising started` and looks perfectly healthy. Pinning the
  address is far less invasive than the `btusb` unbind the skill previously
  recommended. (See "Re-validated after the rebase" below — this bit during
  validation.)

built-in analog card and a passed-through Focusrite Scarlett 2i2 — plus the
companion on a phone and, for the first time, a real browser:

- A real USB unplug/replug (`/sys/bus/usb/devices/.../authorized`) is the closest
  thing on this host to headphones in and out: on unplug PipeWire fell back to
  the built-in, the daemon followed and pulled it 100% → 30% to obey that
  device's cap; the absent device kept its row and its own cap; on replug the
  switch went back and its cap was re-applied.
- Choosing an output from the browser and from the phone both moved the real
  default sink, with the reported percentage and ceiling following the device.
- With the built-in pinned as default and no RPC calls at all, unplugging and
  replugging the *other* device each produced an event carrying identical
  percent, ceiling and active output — nothing but the set of present devices
  had changed, and the watcher caught both.
- Both UIs tracked all of it untouched; the phone did so over BLE.

## Known limits

- **Bluetooth audio is unexercised.** The dev host has a BT radio but no BT audio
  device, so the `bluez5` branch of `kind` detection is unit-tested only.
- **No device here classifies as headphones or speakers** — one is `line_out`,
  one is `unknown` — so those icon/label mappings are unit-tested only.
- **PulseAudio and ALSA hosts** get no output identity, no picker and no watch
  loop; they keep today's flat behaviour.
- **Latency is bounded by the 2s poll.** `pw-mon` would make it event-driven;
  only latency is at stake, not correctness.
- **A clamping switch broadcasts `VolumeChanged` twice** — the watcher records
  the pre-clamp reading and broadcasts the post-clamp one, so the next tick sees
  its own correction. Harmless (every client refetches), one wasted round trip.
- **`min_volume` is stored and layered per output but not exposed in either UI,**
  and `enforce_volume_ceiling` only lowers, so a floor is not applied on arrival.
  The issue asked for a maximum; the floor can be surfaced if a use case appears.
