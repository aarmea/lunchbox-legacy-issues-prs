## Description

The companion could spin on "Connecting…" indefinitely, most often
after a long heavy-activity session, with nothing logged server-side —
then the first RPC would land minutes later, long after the 15s
timeout the user was watching for.

The stall was in connect(), not the RPC path: REQUEST_TIMEOUT_MS wraps
call() only, so nothing bounded connect() at all. Its post-connect
drain read until two consecutive empty reads with no timeout, no read
cap, and no delay, while events_forwarder filled a 256 KiB events
outbox whether or not anyone was connected. At 512 bytes per GATT
round trip that backlog is 13-26s of dead time on its own, and once
events arrived faster than the drain consumed them the exit condition
never occurred.

- Bound the drain (3s / 192 reads per characteristic). On exhaustion
  raise DrainStalledException and drop the link — the daemon clears
  both outboxes on peer disconnect, so the retry starts clean.
  Deliberately not LinkUnauthenticatedException: the link is fine, the
  backlog isn't, and conflating them points recovery at the bond.
- Wrap connect() at 20s in the session and pairing paths so a stall
  reaches the existing backoff ladder instead of parking on it.
- Add Outbox::push_coalesced and push StateChanged under it; snapshots
  are idempotent, so an hour of churn leaves one to drain instead of
  hundreds. Drop EVENTS_OUTBOX_BYTES 256 KiB -> 64 KiB.
- Log peer connect at info with both outbox depths, and log a drained
  backlog once per drain. Reads are debug-level, and nothing logged a
  connect, so this failure was invisible in the journal by
  construction.
- Offer re-pair instead of forcing it: exhausting the retry ladder no
  longer removes the OS bond. Reachable-but-unusable is consistent
  with a congested radio, a daemon restart, or this very stall, and
  auto-unbonding turned each into a mandatory trip to the TV. New
  LinkStatus.RepairSuggested surfaces Retry + Re-pair; only the user
  tapping Re-pair drops the bond.

Not yet validated against the live repro on hardware.
