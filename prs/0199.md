## Description

Closes [#197](https://github.com/aarmea/lunchbox/issues/197).

## The bug

A device that blanked on the 120-second idle timeout **never woke again**. The
child could not get the screen back by touching it; pressing the power key
suspended the machine instead of waking the panel, and the display only came
back after the session was logged out over the management API — at GDM, because
a fresh session re-initialises the output, not because anything asked for it.

The journal for the reported incident shows it twice in thirty minutes, and
never a wake:

```
17:51:10  Screen blank suppressed: an activity is running
17:53:26  Screen power set on=false
18:05:36  systemd-logind: Power key pressed short.  →  Suspending...
18:06:07  resume
18:06:54  a fresh gdm session (uid 60587)
18:09:44  Screen power set on=false
18:10:26  a fresh gdm session (uid 60588)
```

`shepherd_launcher: Screen power set on=true` never appears.

## Root cause

`swayidle` parses `resume` as a **suffix of the timeout it follows** —
`timeout <secs> <cmd> [resume <cmd>]` — not as a standalone event. [#154](https://github.com/aarmea/lunchbox/issues/154) appended
its 900-second administrator-idle timeout *between* the blank and its `resume`:

```diff
 exec swayidle -w \
     timeout 120 '$launcher --screen-off' \
+    timeout 900 '$launcher --admin-idle-timeout' \
     resume '$launcher --screen-on'
```

That silently re-parented the wake onto administrator mode's timer and left the
120-second blank with no resume at all. `swayidle -d` prints the binding — note
where "Setup resume" lands:

```
Register idle timeout at 120000 ms
Command: echo off                    ← no "Setup resume"
Register idle timeout at 900000 ms
Command: echo admin
Setup resume
Command: echo on
```

`--screen-on` is the only thing in the tree that calls `set_screen_power(true)`
(`crates/shepherd-management/tests/supervision.rs:295` says as much: *"swayidle's
`resume` is the only thing that asks"*). So once the blank fired, touching the
screen asked nothing. The only way back was to stay idle past 900 seconds — and
that path runs `--admin-idle-timeout`, which ends the session anyway.

Before [#154](https://github.com/aarmea/lunchbox/issues/154) there was a single timeout, so the trailing `resume` was correct by
accident of ordering. Neither `swayidle` nor sway reports either form.

## The fix

Put the pair back together, and add the new timeout after it:

```diff
 exec swayidle -w \
-    timeout 120 '$launcher --screen-off' \
-    timeout 900 '$launcher --admin-idle-timeout' \
-    resume '$launcher --screen-on'
+    timeout 120 '$launcher --screen-off' resume '$launcher --screen-on' \
+    timeout 900 '$launcher --admin-idle-timeout'
```

Waking is never suppressed, so `--screen-on` is safe on every resume. The
900-second timeout needs no resume of its own: leaving administrator mode is not
something to undo when the caregiver comes back.

## The guard

A comment alone would not have stopped [#154](https://github.com/aarmea/lunchbox/issues/154) — the bug was appending to a line
that *looked* appendable. `scripts/lib/headless.sh` now asserts the binding on
the derived sway config, alongside the existing `--no-harden-sway-ipc` /
`--no-restrict-ipc-peers` / `--no-state-custodian` exec-line assertions. It
joins the backslash continuations first, because the exec spans three lines and
a per-line grep would answer the wrong question.

Checked against all three shapes: the fixed config passes, the pre-fix ordering
fires the `die`, and a config with no `exec swayidle` fires the other one. Every
agent and human who boots `dev headless` runs it — which is the point, for a
failure that is invisible until a device blanks in someone's hands.

## The durable lesson

`swayidle`'s `resume` binds to the timeout it *follows*. Adding a timeout to
that line is never a safe append: anything placed after an existing
`timeout … resume …` pair is fine, anything placed *before* the `resume` steals
it. Verify with `swayidle -d` and read where "Setup resume" lands.
