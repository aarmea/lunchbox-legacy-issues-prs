## Description

Closes [#159](https://github.com/aarmea/lunchbox/issues/159).

Skips sponsor reads, self-promotion, "like and subscribe", intros and end cards
in YouTube videos, using the SponsorBlock database. **Off by default**; a parent
turns it on, and a single library can opt out (or in) on its own.

```toml
[service.media.sponsorblock]
enabled = true
# categories = ["sponsor", "selfpromo", "interaction", "intro", "outro"]
# api = "https://sponsor.ajay.app"     # point at a mirror if you'd rather
```

The Android app has the same thing as a per-library **Skip sponsors** checkbox
on its settings card, beside "Resume playback", also off by default. Both
front-ends share the categories, the filtering and the skip logic, so a video
skips the same way whichever one is playing it.

Design notes and the decisions behind them:
`docs/ai/history/2026-09-03 001 sponsorblock-scope.md`. User-facing
documentation: the new "Skipping sponsors" section of `docs/shepherd-media.md`.

## Why it is built this way

Three designs were on the table. Two of them look cheaper than they are:

| Design | Why not |
|---|---|
| Cut the spans out with `yt-dlp --sponsorblock-remove` at download time | Needs ffmpeg; only helps items in the video cache, so a cache miss or a lost prefetch lock streams the ads back in; impossible on Android, where YouTube is never cached and yt-dlp is a JNI `-g` call with no postprocessing; and cutting the file changes its timeline, silently invalidating saved resume positions |
| Mark them as chapters at download time | Same ffmpeg/cached-only/Linux-only problems, with the data smuggled through a container format |
| **Fetch the segments and skip at playback** | Identical behaviour cached or streaming, works on both front-ends, survives a database correction without a re-download, and can be turned off by config without touching the cache |

Split the way posters and playlists already are — a pure core, a shared disk
cache, and a per-platform fetch:

| Crate | What it owns |
|---|---|
| `shepherd-media-core` | The wire format, the filtering, the skip state machine, and the request URL. Pure, no I/O, shared by both front-ends |
| `shepherd-media-app` | `BucketStore`: file layout, TTL, atomic write, stale-on-failure fallback |
| `shepherd-media-cache` / `shepherd-media-android` | The HTTP call and where the cache directory is — ~60 lines each |
| `shepherdd` | Warms the buckets for videos it prefetches, so an offline library still skips |

The duration filter is ported from yt-dlp's `SponsorBlockPP` rather than
invented. A submission is made against a particular cut of a video; if the
upload was replaced, its timestamps point at real content. yt-dlp's rule has
been beaten on by a great many videos, and two tools disagreeing about whether a
segment is stale would be worse than either rule alone.

## Privacy

Only the hash-prefix endpoint is ever called: a request names a *bucket* — the
first four hex characters of the SHA-256 of the video id — and the service
answers with every video that hashes into it (~100 videos, ~40 KB), which the
device filters locally. The exact-video endpoint, which would be a description
of somebody's viewing, is never used. Nothing is submitted and nothing is voted
on.

That cost turns into a saving: caching the whole bucket means prefetching a
playlist touches far fewer buckets than it has videos, and a lookup landing in a
bucket already on disk costs nothing.

With the feature off, **no request is made at all** — not at launch, not on a
play, not in the background. That is asserted on the wire, below.

## Verification

Three things beyond the unit tests, all against a real video whose sponsor span
the database puts at 31.6s–100.3s (locked, 18 votes).

**Linux, in the headless dev session.** 45 seconds of playback, with `--resume`
on so the position reached is written to disk and can be read back:

| Run | Where playback got to |
|---|---|
| `--sponsorblock-categories sponsor` | **106.1s** |
| no flag | 43.5s |

Three repeats of the enabled arm landed at 105.9s, 106.2s and 106.1s.

**Android, on a Pixel 10a** (Android 17, arm64-v8a), same video, the app's own
per-library toggle:

| Setting | Wall clock | Video position reached |
|---|---|---|
| `sponsorblock = true` | 62s | **112.5s** |
| `sponsorblock = false` | 62s | 62.7s |

The off arm tracks wall clock exactly; the on arm runs ~50s ahead of it, which
is the span. The phone wrote its own `files/cache/sponsorblock/3e4f.json`, so
the hashing, the request and the cache all ran on the device rather than being
inferred from the Linux side, and mpv decoded with mediacodec zero-copy
throughout.

A second pass drove the settings UI rather than a seeded `settings.toml`:
ticking the checkbox wrote `sponsorblock = true`, it survived a force-stop, and
the next play planned its skip and reached 100.6s of video in 50s of wall clock.

**On the wire**, via the new `scripts/integration-tests/test-sponsorblock.sh`,
which runs the real player twice under `strace -e trace=connect`:

| Arm | Result |
|---|---|
| off (the default) | 0 of ~120 connections went to any address `sponsor.ajay.app` resolves to; 0 buckets cached |
| on, `--sponsorblock-api` at a stand-in | exactly 1 connection, to the stand-in; 0 to the public instance |

The ~120 is what makes the off arm worth anything: it is playing a YouTube video
over the network the whole time, so the silence is about SponsorBlock and not
about being offline. The on arm's single request is checked to be the
hash-prefix endpoint, to carry no `videoID`, to ask for every skippable category
and no marker one — and that it reached the stand-in rather than the public
instance also demonstrates the mirror override.

## Two defects that only running it could find

**A latched plan.** One of four early end-to-end runs played straight through a
sponsor it should have skipped. The plan was built once, from the first duration
the player reported, and kept — including when that first answer produced an
*empty* plan. A player that reports a provisional duration for a network stream
before the real one would therefore skip nothing for the rest of the video,
silently. It is now rebuilt whenever the duration moves by more than a
quarter-second, and each build is logged with the duration it used. (That this
was the cause of that particular run is not proven — it predates the logging
that would have shown it — but it is a real defect with exactly that signature,
and everything since has skipped.)

**An invisible log line.** The Android plan line was `debug`, and the app filters
to `info`, so the one line that says whether anything was planned — and against
which duration — could not be seen in logcat, which is the only window into a
device. It is `info` now.

## Judgement calls

- **Off by default.** It is the one media feature that talks to a service
  outside the house, and in a product that promises no telemetry nothing should
  reach a new host because a default said so.
- **Once on, the default categories are `sponsor`, `selfpromo`, `interaction`,
  `intro`, `outro`.** `preview`, `filler` and `music_offtopic` stay opt-in
  because their submissions are judgement calls that can cut real content: a
  recap is part of the episode for a viewer who missed last week.
- **The per-entry override is a boolean**, not a category list. The need it
  answers is "not in this library" — a channel whose sponsor reads are part of
  the show — rather than "differently in this library", and a list would have
  meant a mirrored category enum in `shepherd-api` and the config schema for a
  case nobody has. It mirrors `prefetch`, which sits beside it.
- **Read-only client.** No submitting, no voting, and no per-segment UI: what to
  skip is a parent's configuration, not a decision handed to the child
  mid-video.

## Caveat

`[entries.firewall]` is IP/CIDR-based (systemd `IPAddressAllow=`, no hostname
matching), and `sponsor.ajay.app` sits behind Cloudflare with rotating
addresses. An entry with a restrictive firewall cannot allowlist it by name; it
is in the same bucket as the googlevideo CDNs, which the same constraint already
applies to.
