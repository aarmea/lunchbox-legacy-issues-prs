## Description

**Closes [#172](https://github.com/aarmea/lunchbox/issues/172).** Finishes what [#161](./0161.md) left open, on the mechanism [#161](./0161.md) built. The
closed siblings for context: [#144](https://github.com/aarmea/lunchbox/issues/144), and its [#147](https://github.com/aarmea/lunchbox/issues/147) / [#148](./0148.md) / [#158](./0158.md) / [#157](https://github.com/aarmea/lunchbox/issues/157).

Every activity runs as the kiosk uid, and so does `shepherdd`. Signal permission
is a uid comparison, so **an activity can kill the daemon that supervises it**,
and nothing in the kernel's answer distinguishes a game from its supervisor.
[#161](./0161.md) made the ordinary case safe — sway `exec`s
`sh -c 'shepherdd … || loginctl terminate-session'`, so a daemon that *exits*
ends the session at the greeter. Two things walk straight past that:

* the `sh -c` wrapper is at the kiosk uid too. Kill it first, then kill
  shepherdd, and nothing is left to run the fallback. The session stays up with
  no time accounting, no bedtime, no stop-current, no audit.
* `kill -STOP shepherdd` does the same without killing anything. A stopped
  daemon holds every descriptor, never exits, and never ticks, so the `||` never
  fires.

Both are one line from any activity that can run a shell. **Both are reproduced
on a device below**, and the second one is what the fallback can never see.

## The watcher already exists

Everything at the kiosk uid is killable by everything else at the kiosk uid, so
the thing that reacts has to be outside the session at another uid — which is
`shepherd-stated`, built for [#157](https://github.com/aarmea/lunchbox/issues/157). It already runs as `shepherd-state`, is
started by the system manager on a root-owned socket the kiosk uid cannot
rebind, has already resolved *which* logind session is the kiosk's, admits
exactly that session's cgroup, and watches `SessionRemoved` for it. Everything
needed to notice was there except the noticing. A second daemon would have
duplicated all six and given the two a way to disagree about which session is
the kiosk's.

```
shepherdd ──Supervise──▶ custodian     "will anything happen if I die?"
          ◀──armed────   (asks polkit once, at startup)
          ──Heartbeat──▶ every 5s, emitted from the engine tick
              …
          ╳ killed       EOF        ─▶ settle 5s   ─▶ TerminateSession
          ╳ SIGSTOPped   no beats   ─▶ deadline 60s ─▶ TerminateSession
                                        still there after 10s ─▶ KillUser
```

**The beat comes from the engine tick** — shepherdd's existing 100 ms loop, the
one that decides whether a child's time is up — rate-limited to one every five
seconds. A heartbeat from a timer of its own would attest that *a thread* is
alive, which is not the property anyone wants from a watchdog: a shepherdd whose
engine has stopped and whose runtime has not is exactly the failure this is for.
The client refuses to send anything if that loop has gone quiet.

**Nothing has to be sent for it to fire.** A killed process closes its
descriptors whether it meant to or not, and that EOF is the signal; the
heartbeats exist only for the failures that keep the descriptor open. There is
deliberately **no goodbye message**: every orderly shutdown also ends with
shepherdd gone and the session ending anyway, and a disarm message would buy
nothing except a thing to spoof. Every disarm comes from logind; none from the
wire.

**`KillUser`, not `KillSession`, for the escalation.** A session scope holds
sway, the launcher, the HUD and swayidle; the activities are elsewhere —
`shepherd-<id>.scope` under the user manager's `app.slice`, or a snap's or
flatpak's own scope. `KillSession` in the one case the escalation exists for
would kill the compositor and leave the child's game running.

## Measured on a device

An installed kiosk: Ubuntu 26.04, systemd 259, `shepherd-kiosk` (uid 1001)
autologged into the Shepherd sway session by gdm, this branch's release
binaries, the custodian holding the other end. The recipe is now in
CONTRIBUTING, because a headless dev stack cannot reach any of this — it passes
`--no-state-custodian` and its sway is not a logind graphical session.

| | |
| --- | --- |
| the grant | `sudo -u shepherd-state pkcheck --action-id org.freedesktop.login1.manage` → `polkit\56result=yes` |
| armed, quietly | custodian: *"The session watchdog can end this session if nothing is supervising it session=11"*; shepherdd: *"…deadline_secs=60"*; `diagnostics: []` |
| **the attack** | kill both `sh -c` wrappers **first**, then `shepherdd` → session removed **5.10 s** later. sway, the activity and its firewalled scope all gone; `user@1001.service` stopped; reason logged `shepherdd is gone`; custodian exited cleanly, so its socket stayed armed |
| **`SIGSTOP`** | session removed **56.9 s** later — the 60 s deadline from the last beat — with the fallback's own processes **alive throughout**. Reason logged `shepherdd stopped sending heartbeats` |
| **a firewalled activity** | launched through the real `pkexec` chain: `Slice=user-1001.slice`, `BindsTo=session-11.scope`, `ControlGroup=/user.slice/user-1001.slice/shepherd-….scope`, `IPAddressDeny=0.0.0.0/0 ::/0` — the session derived correctly through `pkexec`, the BPF filter real, and the scope gone with the session |
| **reconnect** | `systemctl restart shepherd-stated@…` under a live session → *"The supervision channel broke; reconnecting backoff_ms=500"*, the new instance armed the same session, still active **99 s** later. No false fire |
| **the rule removed** | custodian `ERROR polkit refuses this daemon the right to end a session`; shepherdd raised `session_not_guarded` **critical** with its remedy, over the API and on into the launcher |
| **the negative control** | with the rule removed the same attack **succeeded** — session `active`, sway alive. The defect, reproduced; the rule is the whole difference. The escalation ran on schedule: terminate refused, then **exactly 10.000 s** later *"The session is still here; killing everything this user is running uid=1001"* |
| **a cold boot** | after an unplanned reboot the watchdog armed on session 1 with no diagnostics |

Two things this settles that were previously read rather than measured:
`TerminateSession` stops the session scope even though the manager reports
`KillUserProcesses=false`, and logind's user GC does stop `user@<uid>.service` —
just not in the same second the session ends.

**Not measured, and why.** *A suspend*: this host is a libvirt VM whose only
`/sys/power/mem_sleep` is `s2idle`, and it does not resume — the attempt needed a
hard reset. That case stays covered by unit tests and wants real hardware;
CONTRIBUTING now says so. *A second graphical session*: cannot be staged on one
seat. *The `{:#}` log change* below: verified by build and tests only.

## What must not fire it

A watchdog that fires when nothing is wrong costs a child their session
mid-activity, for a reason nothing on screen explains. That is why the deadline
is a minute rather than the twenty seconds first sketched — the loose direction
is the cheap one, because the case an activity would actually reach for is a
kill, and a kill is an EOF that settles in five seconds. Three cases are handled
rather than left to the deadline:

| | |
| --- | --- |
| **a suspend** | logind's `PrepareForSleep` stands the guard down and re-arms it on resume with a *full* deadline. Same signal `shepherdd` already uses for the activity clock ([#155](https://github.com/aarmea/lunchbox/issues/155)) |
| **a slow boot** | the first beat gets two minutes rather than the deadline's one: the channel opens while shepherdd is still starting, and the engine tick runs after that. Nothing is unguarded meanwhile — an activity cannot launch before the engine that would launch it |
| **a reconnect** | losing the connection starts the five-second settle rather than firing, so a client that comes back cancels it by arriving |

A fourth is structural: the guard is never armed against a session that did not
resolve to exactly one id, so a `switch user` cannot make it guess.

Every one is a unit test rather than a device, because the state machine has no
clock, socket or bus of its own — `Guard` takes `now` and returns an `Action`.

## The authority, and what it widens

`TerminateSession` from a uid that does not own the session needs polkit's
`org.freedesktop.login1.manage`, granted to `shepherd-state` by
`dist/polkit/50-shepherd-session-guard.rules` (installed with the custodian,
removed with it, a conffile in the `.deb` like the firewall helper's rule).

**Said plainly, because it is the first question a reviewer will ask:** polkit
passes no details for `TerminateSession`, so the rule cannot be narrowed to one
session or one user. It grants `shepherd-state` the right to end **any** session
on the machine, an administrator's SSH login included. What keeps that acceptable
is the shape of the thing holding it — no network, no subprocesses,
`ProtectSystem=strict`, `CapabilityBoundingSet=`, one call site, and a session id
resolved from logind rather than taken from the wire. The rule's own comments
carry this. The alternative, if that widening is ever judged too much: a second,
root-owned daemon whose entire protocol is "bytes arrived" — a worse trade, but
the one to make if the grant is refused.

## Saying so when it cannot fire

A protection that reports itself present and is not is the worst available
shape, so the daemon asks polkit at startup and the answer travels back on the
`Supervise` reply. shepherdd — alive at that moment, unlike the watchdog when it
is needed — turns it into `session_not_guarded`: **Critical** when polkit
refuses or logind cannot be reached, **Warning** when polkit could not be asked
at all. Not knowing is not the same as knowing it will fail. Silent on a device
with no custodian, which already says so through `state_not_protected`.

## Firewalled activities, fixed where they are created

A firewalled Process entry runs in a *system* manager scope — `IPAddressDeny=`
needs `CAP_NET_ADMIN` — which put it outside `user-<uid>.slice`, where neither
the terminate, nor logind's user GC, nor `KillUser` reached it. Only shepherdd's
own teardown ever stopped one, and the absence of shepherdd is the whole subject
here.

The tempting fix was to let the custodian stop those units, which would have
meant `org.freedesktop.systemd1.manage-units` — the right to stop *any* unit on
the machine — for a daemon whose discipline is custody rather than judgment. The
lifetime is declared where the scope is created instead, so the existing
`TerminateSession` finishes the job and nothing gains a new authority:
`--slice=user-<uid>.slice` (a unit implicitly `Requires=` its slice) plus
`BindsTo=`/`After=` the caller's session scope. **The session is derived, never
passed** — the polkit rule admits the `shepherd-firewall` group, which is the
kiosk user, so an argument would be attacker-chosen; it comes from the helper's
own cgroup, inherited through `pkexec`, validated to logind's shape. No session
found means the slice and no binding, rather than a guess.

The device run above confirms both properties on a real launch, and that the
scope dies with the session.

## What this does not close

* **A device without the custodian.** `--no-state-custodian`, or a packaged
  device where `setup-user` never ran, has no watchdog. Same premise as [#157](https://github.com/aarmea/lunchbox/issues/157),
  and `state_not_protected` already says it.
* **Code already inside the session scope.** The heartbeat is trusted exactly as
  far as [#158](./0158.md)'s cgroup check: anything in the kiosk's session scope could keep
  the watchdog fed. The launcher, the HUD and swayidle live there; an activity
  does not. No new trust — but that check is now load-bearing for a second thing.
* **A shepherdd that ticks but supervises nothing.** The beat rides the engine
  tick, which is a real attestation, not proof that the host adapter still
  launches or stops anything. [#135](https://github.com/aarmea/lunchbox/issues/135)'s supervision escapes are their own tracker.

## Two things the device showed that the design did not

* **A killed session *leader* leaves `shepherdd` orphaned and the session
  `closing`.** Nothing sets `PDEATHSIG`, and with `KillUserProcesses=no` logind
  waits for the scope to empty. `TerminateSession` on an already-closing session
  is a no-op — an unplanned second argument for the `KillUser` escalation, which
  is then the only step that reaches a session logind has given up on.
* **`shepherdd`'s policy watch does not reconnect** after a custodian restart,
  while the supervision channel does. Pre-existing ([#157](https://github.com/aarmea/lunchbox/issues/157)'s watch) and out of
  scope here, but a device whose custodian restarts quietly stops picking up
  policy edits. Worth its own issue.

## Tests

Eleven `Guard` cases as arithmetic against a fake clock — the kill, the
`SIGSTOP`, the suspend, the reconnect, the slow boot, the boot that dies, firing
once. Four in the firewall helper for the scope's lifetime, including every
shape that must read as "no session". A wire round trip that ends by *dropping*
the client, so the server sees the EOF the whole thing turns on. The polkit rule
checked against `STATE_USER` in `units_match_the_constants.rs` — a fourth fact
that cannot be stated once, since polkit cannot call Rust either. Both
diagnostic contracts in `shepherdd`.
