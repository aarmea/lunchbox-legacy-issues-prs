## Description

Closes [#165](https://github.com/aarmea/lunchbox/issues/165).

Everything on the media path is cached with a TTL and swept on a timer, and the waits compound. There was no way to say "go and look now" — `reload_config` re-reads `config.toml` and touches none of these caches.

| What | Where | Wait |
|---|---|---|
| YouTube playlist contents | `CACHE_TTL_SECS`, `shepherd-media-cache/src/playlist.rs` | 6 h |
| Prefetch sweep | `SWEEP_INTERVAL`, `shepherdd/src/media.rs` | 1 h |
| Retry after a failed download | `RETRY_COOLDOWN`, `shepherd-media-cache/src/download.rs` | 6 h |
| SponsorBlock segments | `DEFAULT_TTL`, `shepherd-media-app/src/sponsorblock.rs` | 24 h |

So: add a video to a playlist and it can be **6 hours** before the child's browse grid shows it, **7** before it is cached for offline play, and if that first download fails, another **6** before anything tries again. A segment submitted for a video already on the device is invisible for up to a day.

## What this adds

One RPC, `refresh_media`, behind a button in both management surfaces — **Refresh Media** in the web UI's Admin page, **Refresh media** in the companion's Maintenance card. It:

- re-fetches every playlist-backed library from YouTube, ignoring the 6-hour metadata cache;
- forgets every `<key>.failed` marker, so downloads inside their retry cooldown are attempted again immediately;
- re-fetches the SponsorBlock bucket for every video it caches, ignoring the 24-hour TTL;
- sweeps immediately rather than at the next tick, **including while an activity is running** — the press almost always happens with the child in front of the device asking where the new video is, which is exactly the state background prefetch declines to work in.

The caches are shared on disk with the `shepherd-media` player process, so refreshing from the daemon fixes the player too. That is what makes a daemon-side button worth having.

## Forcing the fetch, rather than expiring the cache

The obvious implementation — unlink the cache files so the next read misses — is wrong, and quietly so. Every cache here falls back to a stale copy when the live fetch fails (`cache::resolve` → `Resolution::Stale`), which is what keeps a device listing its library and skipping sponsors once it goes offline. **Deleting what you cannot replace leaves a refresh pressed on a flaky connection worse than no refresh at all.**

So `refetch_playlist` and `SponsorBlockCache::refresh` are the ordinary fetches with the freshness check removed: they write back on success and, on failure, leave the cached copy exactly where it was and return the error. Each store has a test for the property directly — *a failed refresh keeps the bucket it could not replace*.

`<key>.failed` is the exception and really is deleted, because there the marker *is* the staleness.

## What it deliberately does not do

**Re-download videos that are already cached.** A cached file is keyed by source URL *and* format selector, so the only way its bytes can be wrong is a re-upload at the same URL — and a button that silently re-spends 10 GiB of a household's bandwidth is not what "refresh" should mean on a kiosk. If the re-upload case turns out to matter it wants its own destructive, per-item affordance with a confirmation, not this button.

**Touch what the child has watched.** The `.played` / `.seen` interest markers and the resume positions under `$XDG_STATE_HOME` are untouched. A refresh is about freshness, not about forgetting what was watched — and wiping either would both lose history and re-score the entire cache as brand new.

**Posters.** Considered, and dropped despite being the same class of staleness: a new playlist item has a *new* thumbnail URL, so it is a cache miss and fetched at the next launch regardless. The only thing a poster refresh would fix is an image changing behind an unchanged URL, and only the player fetches posters — at launch — so the daemon could not act on it anyway.

## Which gates an explicit press overrides

Two, both of which exist to keep *background* work off a device somebody is using: `prefetch_while_session_active`, and the 30-second `RESUME_DELAY` after a session ends.

Everything else stands — including the per-entry `prefetch = false` opt-out, which means the refresh path reuses `PrefetchTarget` unchanged rather than needing a second, metadata-only target list. The two device-wide gates that survive are the ones a button genuinely cannot overrule: `service.media.prefetch = false` is a household decision, and an offline device has nothing to fetch. Both now say so out loud rather than returning silently.

## Reporting, and why it is a diagnostic

**The RPC returns as soon as the request is accepted.** It has to: a refresh runs `yt-dlp` once per playlist and then downloads videos, while the companion's `REQUEST_TIMEOUT_MS` is 15 seconds. So the button says "Refreshing media libraries…", not "done".

The outcome arrives as a new `media_refresh_failed` diagnostic — on `Service` when the whole refresh could not start, on `Entry` when one library fell back to cached data — cleared by the next refresh that gets through. State rather than an event, because "the last refresh could not reach YouTube" is a condition that stays true; it costs no new wire type, and both clients already render the diagnostic set.

A **scheduled** sweep touches that diagnostic in neither direction. It reads from exactly the caches a refresh exists to bypass, so a clean scheduled sweep is no evidence the source is reachable and must not clear a standing complaint about it.

An unreadable library still raises only `media_library_unreadable` — saying the same thing twice under two codes would just make the list longer.

## Shape of the change

`#[management_rpc]` generates `dispatch_json` and both transports route through it, so one trait method is one BLE method and one HTTP method with no per-transport code.

| Layer | What |
|---|---|
| `shepherd-api` | `DiagnosticCode::MediaRefreshFailed` |
| `shepherd-media-app` | `BucketStore::refresh`, `prefix_for` — shared with Android |
| `shepherd-media-cache` | `refetch_playlist`, `SponsorBlockCache::refresh`, `store::clear_all_failures` |
| `shepherdd` | `SweepMode`, `MediaPrefetcher::refresh`, a third arm on the `select!`, the `mpsc` in `main.rs` |
| `shepherd-management` | `refresh_media()` on the trait, `media_refresh_tx` on the service |
| generated | schema + both clients' method/param/result mirrors |
| web UI | `refreshMedia()`, a Media card on the Admin page |
| companion | `ManagementClient.refreshMedia`, `ShepherdViewModel.refreshMedia`, a button in the Maintenance card |
| docs | `docs/shepherd-media.md` "Refreshing now", `shepherd-media-cache/README.md`, `shepherd-http/README.md` |

Two details worth flagging for review:

- `refresh_media` returns `ManagementResult<()>` — **no count**. The service cannot know how many libraries a refresh will cover without duplicating the prefetcher's policy gates, and a number that disagreed with what it actually did would be worse than no number.
- The nudge is a **capacity-one `mpsc`** rather than a collaborator trait, so `shepherd-management` does not link the media stack. A second press while one is queued asks for the same sweep and is dropped rather than reported as a conflict — an error there would only train an administrator to press it again.
- The SponsorBlock refresh **deduplicates by bucket prefix**. `warm` gets the second video in a bucket free because the first one's fetch wrote the file; a forced refresh does not, so without it a 92-item library would make 92 requests where a dozen would do.

## Known limitation, documented rather than fixed

A media activity **already on screen** loaded its library when it launched. Refreshing updates the caches under it, and the child sees the new items the next time the activity is opened — or immediately, if the HUD's reset button (`reset_current`) is used to restart it in place. Noted in `docs/shepherd-media.md`.

- **The RPC returns immediately and the sweep happens.** Over BLE: `BLE RPC received … method=refresh_media` → `BLE RPC response queued … ok=true` in under a millisecond, well inside the companion's 15-second deadline, followed by `media refresh requested libraries=3 cooldowns_cleared=1` and every library re-walked in the same second — including retrying the YouTube one that had already failed, instead of waiting out its 6-hour cooldown.
- **Both buttons say the right thing.** The phone shows a "Refreshing media libraries…" snackbar; the web UI flashes the same. Neither claims the work is done.
- **The failure path reports itself on both.** With `service.media.prefetch = false`, pressing refresh raises `media_refresh_failed` on `Service`; it propagates over the event bus and renders — message *and* remedy — on the web Health page and on the companion's Device health screen.
- **A successful refresh clears it, on both.** Turning prefetch back on, `reload_config`, pressing again: the diagnostic is gone from the phone's health screen and the web page, while `media_library_unreadable` correctly remains for the example config's placeholder playlist URL.
- **No duplicate diagnostics.** The unreadable-library case raises `media_library_unreadable` only.
