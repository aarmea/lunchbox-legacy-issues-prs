## Description

# Stop the device dialling the admin phone over LE

Follows PR [#130](./0130.md), which fixed the companion's side of this. This is the
device side, and it is where the actual bug was.

## The symptom

Pair the phone, use the device for a while, then try to connect from the
companion: **"Can't reach this device securely"**, permanently. Force-stopping
the app, logging out and back in, restarting `shepherdd` — none of it
recovered the session. On the reporter's box a suspend/resume reproduced it
every time.

The tell in the logs is that there is no failure to see. The link comes up and
stays up; the phone just cannot read anything on it.

## Root cause

BlueZ probes `auto_connect` profiles (`a2dp`, `bap`, `hog`, `input` — a phone
matches several) on a bonded device and calls `device_set_auto_connect(TRUE)`
(`src/device.c:5551`), which sends `MGMT_OP_ADD_DEVICE` with `action = 0x02`.
From then on **the kernel** connects that address the moment it advertises.

Our companion is a GATT *server*, so a link the box originates makes the box
the central — and only a central may start encryption. The phone decides it
needs an encrypted link and then has no way to ask for one, while nothing on
our side asks either. Every read of an `encrypt_authenticated` characteristic
comes back `Insufficient Authentication (0x05)`, forever, on a link that never
drops. bluetoothd answers those reads itself, so our characteristic callbacks
never fire and the daemon cannot even see it happening.

Caught on the wire on 2026-08-17: bluetoothd issuing `LE Create Connection`
against the phone with nothing in shepherd having asked for it.

## The fix

**Pin each bonded peer to the BR/EDR bearer** (`Device1.PreferredBearer =
"bredr"`). That makes `device_set_auto_connect` return before
`adapter_auto_connect_add()` — BlueZ's own comment there reads *"Remove device
from auto-connect list so the kernel does not attempt to auto-connect to it in
case it starts advertising"*. BR/EDR auto-connect is untouched, which matters
on a handheld whose radio is also the user's headphones. BlueZ stores it in the
bond record, so it survives restarts.

Alongside it, four failures found while chasing this:

- **Re-arm the advertisement on resume, not just on power-on.** A suspend does
  not always move `Adapter1.Powered`; on the reporter's box a resume left the
  device off air while `ActiveInstances` still read 1 and `Powered` read true —
  a device that has silently vanished is indistinguishable from a healthy one
  through every property we can query. Now also driven by the daemon's own
  `SystemResumed`.
- **Survive a failed pairing-agent registration.** One transient
  `NoReply` from a busy bluetoothd used to kill BLE management for the whole
  session — no advertising, no retry, one ERROR line. Now retried with backoff,
  and the server runs without an agent (costs pairing, not everything).
- **Stop evicting silent peers.** The previous watchdog dropped links at 25 s,
  which landed inside the Numeric Comparison window and made pairing
  impossible. It now only reports; eviction survives as a fallback at 90 s,
  gated on the bearer being unpinned *and* a real session having happened this
  boot (a first pairing never has).
- **Discard the stale outbox on connect** instead of shipping it. A companion
  drains both outboxes before its first RPC, so ~4 KiB of superseded snapshots
  turned a 1.5 s reconnect into 3.3 s. Measured 5.35 s → 2.04 s with a 13-frame
  backlog. `clear_if_aligned` declines if a drain is already in flight, so a
  frame is never cut in half.

## Deployment: this needs a bluetoothd drop-in

`PreferredBearer` is `experimental` upstream, so on a stock bluetoothd it does
not exist. `dist/systemd/10-shepherd-bluetooth-experimental.conf` adds `-E`;
the installer renders it against the daemon path read back from the *installed*
unit (a drop-in pointing at a wrong path stops Bluetooth working entirely), and
the `.deb` does the same from its postinst. Documented in
`docs/INSTALL.md` → "Keeping the device from dialling the phone".

**Without it shepherd degrades rather than breaks**: it says so once in the
log, with the two ways to fix it, and falls back to the 90 s eviction.

## Verification

Unit tests cover the decisions (re-arm triggers, `clear_if_aligned` alignment,
framing/peer-change resets): 56 pass in `shepherd-ble`.

The rest was verified on hardware — a Pixel 10a against a Realtek dongle,
through the headless dev session:

- The property appeared, shepherd pinned the peer on the startup sweep, and
  BlueZ persisted `PreferredBearer=bredr` into the bond record on disk.
- **The wire.** `btmon` across the 30 s after a disconnect, with the pin set,
  recorded exactly one HCI command from the box: `LE Set Extended Advertising
  Enable`. No `LE Create Connection`, no `Add Device`. The kernel auto-connect
  list is never armed — the failure chain is cut at the first link.
- Four connect/disconnect cycles, a force-stop/relaunch, a controller power
  cycle (re-arm fired, back on air, RPCs again ~8 s later), and a launch pushed
  over the events path and rendered on the phone. **Zero warnings or errors**
  from `shepherd_ble` for the whole session.

Reconnect to first RPC: 3.1 s, against 5.1 s in the same test before the pin.

This run does *not* re-prove the unpinned box dialling; that is the 2026-08-17
capture in the history note.

## Also in here

- **A `TransportState` refactor.** Seven functions carried
  `#[allow(clippy::too_many_arguments)]` because the same seven pieces of
  session state were threaded through all of them individually
  (`spawn_device_watcher` took nine parameters, seven of which never varied).
  Bundled into one struct; every allow is gone, the widest signature left is
  six, −104 lines, no behaviour change.
- **A release-tooling fix.** `shepherd-firewall-bpf` is excluded from the
  workspace and carries its own lockfile, which `version set` never refreshed
  and `version check` never inspected — so every release left it a version
  behind, resurfacing later as an unexplained modified file. That is what the
  stray `0.3.5 → 0.3.6` lockfile in this repo was.
- Version bumped to **0.3.7**.

## Known limits

- The `id == 1` new-session sentinel still misses roughly 10% of sessions (a
  companion that resumes its connection mid-sequence). The disconnect-driven
  wipe covers those, but a monotonic session token would be the real fix.
- Nothing surfaces whether the pin took in daemon health/status output — today
  it is only in the log.
- Wi-Fi/BT coexistence stalls on a combo radio are inherent and not addressed.
