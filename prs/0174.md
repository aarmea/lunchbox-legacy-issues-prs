## Description

Closes [#171](https://github.com/aarmea/lunchbox/issues/171).

On some hardware or activities a strip down the side costs less of the screen
than a bar across the top. This adds the vertical HUD — the same bar rotated a
quarter turn to the left — and the configuration to choose it, device-wide
under `[service.hud]` and per activity with `hud_orientation`.

```toml
[service.hud]
orientation = "left"        # device-wide default

[[entries]]
id = "wide-game"
hud_orientation = "left"    # just this activity, for the life of its session
```

Everything the issue asked for: the bar down the left, the X at the top with an
unrotated icon, vertical sliders, the activity title read sideways, the wall
clock as an analog face, and the time remaining at two significant figures.

## How it is put together

**The layout is one rule, not two.** Rotating the bar to the left maps its
*right* end to the *top* of the screen, so the vertical bar is the horizontal
one read backwards. That lives entirely in `HudOrientation::flow_append`, which
prepends instead of appending — so the end-session button at the far right
lands at the top and the page-turn buttons at the far left land at the bottom,
without a single line of construction code being reordered. The two layouts
cannot drift apart because there is only one place they differ.

**Three things could not simply be rotated:**

- *The activity title.* GTK4 removed `gtk_label_set_angle`, so `rotated_label.rs`
  is a `GtkWidget` subclass wrapping a real `GtkLabel`, swapping the axes in
  `measure` and handing the child a `translate(0, height) · rotate(-90°)` in
  `size_allocate`. Keeping a real label is what preserves the CSS-driven font
  size *and* the ellipsize behaviour that stops a long title pushing the "X" off
  the bar ([#160](https://github.com/aarmea/lunchbox/issues/160)).
- *The wall clock.* `HH:MM` is wider than the bar and a clock read sideways is
  worse than none, so `analog_clock.rs` draws a round face — the first
  `GtkDrawingArea` in the repo.
- *The warning banner.* Warning text is operator-authored prose of no fixed
  length (`"10 minutes left - start wrapping up!"`) and GTK clips rather than
  wraps, so the bar keeps the icon — which carries the severity colour and the
  critical blink on its own — and the message drops out of it as a popover.

**The edge travels over IPC**, because the HUD does not read `config.toml`;
shepherdd does. `HudOrientationChanged` fires when the *effective* edge moves,
and `get_hud_orientation` is asked on every connect — because that event fires
only on change, and a HUD that started late or reconnected mid-session would
otherwise sit on the wrong edge, with its exclusive zone reserved on the wrong
side of the activity, for the rest of the session. That is the same hole [#118](./0118.md)
found for the scale factor, and this is deliberately the same shape as
`HudScaleChanged`/`get_hud_scale`.

**A change of edge rebuilds the bar rather than restyling it**, for the reason
[#118](./0118.md) documents: GTK validates a widget's style when it is *mapped* and leaves it
alone while hidden, so anything hidden across the change — the confirm prompts,
the warning — would keep the previous layout's sizes. Two consequences a
reviewer should know before touching `build_hud_content`:

- Every timer it registers is generation-guarded and retires when a newer bar
  replaces it. Without that, each rebuild leaves another 500ms timer driving
  widgets that are no longer on screen. Anything new that registers a timer
  needs the same guard.
- `HudContent::teardown` exists because a `GtkPopover` attached with
  `set_parent` is not owned by its parent the way a box child is, and the
  confirm prompts are themselves rebuilt on every scale change — so the teardown
  reads the *current* popover through the `Rc<RefCell<..>>` rather than one
  captured at build time.

## Worth a reviewer's attention

**`gtk4` gains the `v4_10` feature.** The drawn clock face takes its colour from
CSS via `gtk_widget_get_color`, which is gated behind it. Enabling it only
changes which bindings compile — shepherd already requires Ubuntu 26.04
(GTK 4.18+), well past the 4.10 it asks for — but it is a workspace-wide
dependency change rather than a local one. The alternative was a second copy of
the palette in Rust, which is the kind of drift the `scale_px_literals` design
exists to avoid.

**`--anchor` changes meaning: it is now an explicit *pin*, not a default.**
Given, it wins over config and the HUD ignores `HudOrientationChanged` — which
is what makes `SHEPHERD_HUD_ANCHOR=left` useful in development and a footgun on
a device. Absent, which is how `sway.conf` starts the HUD, the bar starts at
`top` and follows shepherdd.

The consequence is visible: a device configured for a side bar shows a top bar
for the fraction of a second before the first connect. That is a deliberate
trade — a HUD that waits for the daemon before showing itself is a HUD a child
cannot end a session from when the daemon is slow or down. Happy to make it
wait instead if you would rather not see the flash.

**The bar renders 54px, not 48px — and always has.** `--height 48` sets the
layer-shell *exclusive zone*; the surface is sized to its content, which is 54px
(a 32px `.indicator-button` plus its 4px padding plus the bar's 6px). So the
horizontal bar has overhung its reserved zone by 6px since long before this
change. I brought the vertical bar to the same 54 rather than to a nominal 48 —
parity with what ships, not with what the flag says. Worth knowing that the
number in the flag has never been the rendered thickness.

**Two sizing traps that are easy to reintroduce:**

- Both sliders need `set_inverted`, because GTK puts a vertical range's minimum
  at the *top*. Without it, dragging up turns the volume down.
- Axis-specific CSS has to be turned with the bar. Rules naming 80px of slider
  length, a 4px-thick trough and `padding: 0 4px` between control groups were
  being demanded *across* the bar; the surface measured **124px** wide until
  `.hud-vertical` swapped them. Anything axis-specific added later needs the
  same treatment — there is a note in the crate README.

## Config editor

Both halves are reachable: `hud_orientation` on an activity's Behaviour tab, and
the device-wide setting in a new "HUD" section on the Device page. The option
list and the description of what the vertical HUD *is* live in
`model/hudOrientation.ts`, shared by both menus and typed as
`RawHudOrientation`, so an edge added to the Rust schema fails the type check
until it is given a label rather than quietly going missing from both.

Two behaviours the new DOM tests pin, because the obvious implementation gets
each wrong:

- Clearing the **device** setting removes the whole `[service.hud]` table rather
  than leaving an empty one. The daemon reads `top` either way; the difference
  only shows in a file people annotate.
- Clearing an **activity's** setting unsets the key rather than writing `"top"`.
  "Inherit" and "top" are different answers — an activity pinned to top keeps
  its top bar when the device moves to a side bar, and an inheriting one
  follows.

Writing those tests caught a bug before it shipped: MUI renders a select whose
value is `""` as a blank box, so both menus read as *empty* when unset instead
of "Top (the default)" / "Use the device setting" — the one thing a control
about defaults has to tell you. Fixed with `displayEmpty` and a pinned label.
