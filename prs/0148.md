## Description

Closes [#147](https://github.com/aarmea/lunchbox/issues/147).

Every compositor interaction spawned a `swaymsg` subprocess, parsed its stdout and exited. That was defensible while the tree query was rare — the module header said as much — but it stopped being true: `list_windows` is on the supervision path now, read every two seconds for the whole uptime of the daemon by the escape and orphan sweep, and twice a second for up to five minutes per launch by the window-ready watch.

The process count was never the reason to fix it. Measured on a headless sway 1.11, a `swaymsg` round trip costs 0.891 ms and 0.853 ms of CPU against 0.103 ms and 0.025 ms on a held connection — 36.8 s of CPU a day versus 1.1 s at the sweep's rate. Untidy, not urgent. The reason is that the two open supervision-escape classes and the orphaned-window work all live at this seam, and the seam sampled the compositor twice a second and could not tell a failed query from an empty screen.

## What changes

**A sway IPC client** (`crates/shepherd-host-linux/src/sway_ipc.rs`). The protocol from `sway-ipc(7)`: a unix socket at `$SWAYSOCK`, a 14-byte header of the `i3-ipc` magic plus a `u32` length and `u32` message type in *native* byte order, then JSON. One connection behind a mutex for requests, because sway serialises replies per connection; a second connection per event subscription.

**Losing an established connection is terminal**, not retried. shepherdd is `exec`'d by sway and dies with it, so a dropped connection means the session is over rather than that the compositor will be back — and reconnecting would be incompatible with the socket hardening below, which destroys the only path a reconnect could use. A connection that has *never* been established is still retried, so one transient error at startup does not disable the compositor for the whole session.

**The parse seam is untouched.** `parse_outputs`, `parse_displays`, `walk` and `is_window` still take bytes and are still tested against literals with no compositor. What is new is coverage of the *transport*, against a fake sway on a temporary socket — framing, wrong-type replies, a missing magic string, a refused subscription, a connection that dies mid-request. Nothing tested the subprocess layer at all.

**Escape detection becomes event-driven.** Reconciliation was a sampling detector: a 2 s sweep asking "is there a surface on screen that shepherd does not own?". For a problem whose entire symptom is an unexpected window, sampling is the wrong shape — an orphan went unnoticed for up to 2 s, and one that mapped and unmapped inside a single sweep was never noticed at all. The host now subscribes to `window` and nudges the monitor, which sweeps on its next 100 ms tick.

**`RECONCILE_EVERY_TICKS` becomes `RECONCILE_SAFETY_NET_TICKS` at 60 s.** Worth keeping, because it is the only thing that catches a bug in the event handling itself; worth running rarely, now that it is not the detector.

**First-window billing is exact.** `WINDOW_READY_POLL` is replaced by a `window::new` wake, so a launch costs a handful of tree reads instead of up to 600. A 5 s tick remains for the two jobs events cannot do: bounding the liveness and deadline checks, and catching a window that mapped before the watch subscribed. Recorded session times shift by up to half a second, in the accurate direction.

**`display_watch` moves onto the same client** and drops its `swaymsg` subprocess and respawn loop. `logout` moves off `swaymsg exit` too — leaving one shell-out behind is how the previous situation justified itself.

## The defect that shaped the design

Both sweep callers discarded the error:

```rust
let windows = crate::sway::list_windows().await.unwrap_or_default();
```

So a compositor that could not be reached was indistinguishable from a clear screen. `report_unowned_windows` saw zero windows and reported no orphans; the escape sweep saw nothing on screen and closed nothing; the daemon concluded all was well. Nothing was logged, because the error had already been thrown away. Same class as the prefetch-sweep logging fixed in e66408c: a broken mechanism and a quiet success producing identical output.

The sweep now takes `Option<&[WindowInfo]>`, and on `None` skips the window half **entirely** rather than treating it as empty — including the pruning of `unowned_reported`, which would otherwise forget orphans it already knew about on a transient failure. It raises `CompositorUnreachable` (the [#143](https://github.com/aarmea/lunchbox/issues/143) channel, `Critical`), which clears itself the moment the compositor answers again.

That needed a seam. The three escape-sweep tests passed *because* of the silent failure — they call `reconcile_escaped` in a process with no compositor and relied on `unwrap_or_default`. They now pass `Some(&[])`, which says what they mean.

`spawn_window_watch`'s `unwrap_or_default` stays, with a comment saying why it is not the same defect: a failed query there costs at most one `WindowReady`, and billing falls back to the whole session — the documented safe direction.

## Closing the socket behind us (the [#144](https://github.com/aarmea/lunchbox/issues/144) shape, on a different socket)

While scoping this against [#144](https://github.com/aarmea/lunchbox/issues/144) it became clear sway's own IPC has the identical defect with worse consequences. Any process running as shepherdd's uid — which is every activity — can issue `RUN_COMMAND "exec …"`, verified working: the spawned process is sway's child, so it is in none of shepherd's process tables **and not inside the cgroup the per-entry firewall is attached to**. An activity configured `default_deny` can ask sway to make its network requests for it. `exit` ends the kiosk session, `kill` closes the HUD, `scratchpad show` reveals the parked Steam client. Sway's `ipc` permission blocks went away in 1.0, so there is nothing to turn on.

Nothing about paths or permissions helps while everything shares a uid, and both dead ends were checked so nobody re-checks them: `/proc/net/unix` is world-readable and lists the bound path of every filesystem socket on the machine, and `/proc/<sway-pid>/environ` is readable at the same uid and contains `SWAYSOCK=` verbatim.

What works is removing the *name*. Sway keeps its listening socket open and established connections keep working, but nothing can connect by path afterwards. Verified on sway 1.11: after the unlink `swaymsg` reports `Unable to connect`, and following the path out of `/proc/net/unix` reaches nothing. Sockets also cannot be reopened through `/proc/<pid>/fd/<n>` (`ENXIO`), and under `ptrace_scope=1` an activity cannot trace sway, which is its ancestor.

**This is only possible because of the first two commits.** While every call re-exec'd `swaymsg`, the path had to exist for the life of the session. A daemon that holds its connections needs it once.

## Hardening is the default, and development opts out

This started as opt-in — `--harden-sway-ipc`, added by `shepherd install sway-config` — on the reasoning that the worst case for opt-in is an unhardened device while the worst case for opt-out is a wrecked developer session. That weighed the two wrong. An unhardened device is one where an activity can ask sway to `exec` for it, outside supervision and outside the per-entry firewall's cgroup, so `default_deny` means nothing — and the only thing standing between a device and that was a single `sed` line in the installer.

So the flag is now `--no-harden-sway-ipc`, and hardening happens unless something asks it not to. The hazard it guarded against has not gone away — the unlink applies to whatever sway session shepherdd is inside, so run by hand in a developer's own desktop it takes that desktop's socket from every other client — so every development entry point in the repo names the flag explicitly:

| entry point | how |
| --- | --- |
| `sway.conf` | on the `shepherdd` exec line; this also covers `run-dev` and `shepherd dev run`, which boot this file directly |
| `shepherd dev headless` | inherits it from `sway.conf`; `--harden-ipc` now *strips* it |
| `crates/shepherd-e2e` | `--no-harden-sway-ipc` on the spawned daemon |
| `shepherd install sway-config` | strips it, so a device — and the `.deb`, which stages through the same function — gets the default |

What changes is which way a mistake falls. A new development entry point that forgets the flag breaks its own `swaymsg` immediately and says so; a device that forgot the old flag shipped silently unprotected.

Both guards were briefly wrong in an instructive way: `grep -F` over the whole file also matches `sway.conf`'s comment explaining the flag, which would have failed a correct install *and* passed a headless session about to unlink the socket out from under itself. Both checks are now scoped to the `^exec .*shepherdd -c` line, and the `sed` in the headless harness is line-addressed to match.

## The regression a real deployment found

Flipping the default surfaced something no test could have: **idle screen
blanking was broken, silently.** `sway.conf` blanked the screen with
`swayidle` running `swaymsg "output * dpms off"`, which after the unlink has no
socket to connect to. Nothing checks a `swayidle` command's exit status, so the
only symptom was a handheld whose screen stopped turning off. Found on
`leibniz` while validating that the socket really was unreachable — exactly the
class of failure that made hardening opt-in in the first place, showing up in
the one place the original review did not look.

The timer stays where it is. `swayidle` is what notices nobody has touched the
device, and shepherdd cannot know that — `InputMonitor` watches device
*presence* for hotplug gating, not input *activity*, so absorbing idle
detection would mean polling evdev or becoming a Wayland client for
`ext-idle-notify-v1`, duplicating a daemon that already does it correctly.
Only the privileged half moved: `HostAdapter::set_screen_power` runs
`output * dpms on/off` over the connection shepherdd already holds, reached
from `swayidle` through a short-lived `shepherd-launcher --screen-off` in the
same connect-call-exit shape as the volume and brightness keybindings.

That also retires `--is-idle-allowed`, and with it a race. The gate was a
separate process — `--is-idle-allowed && swaymsg …` — so a launch landing
between its answer and the blank turned the screen off on a child
mid-activity. shepherdd now checks and acts under one lock, and returns whether
it acted, so a suppressed blank is distinguishable from a failed one. Waking is
never suppressed: a device that blanked just before a launch still has to come
back.

Three tests in `shepherd-management/tests/supervision.rs` pin the suppression,
the happy path, and the wake. `MockHost` gained a `screen_power_calls` log,
because "was the compositor asked at all" is the only way to tell a suppressed
blank from a silent no-op — the same distinction this whole PR is about.

## Notable decisions

**Hand-rolled rather than `swayipc-async`.** The issue asked for this to be decided deliberately. The crate depends on `async-io 2` and `async-pidfd`; this workspace is tokio-only, and `async-io`/`async-std`/`smol` appear nowhere in `Cargo.lock` (the `polling` entries are `calloop`'s, via wayland). Adopting it would add a second async reactor, with its own thread, to a daemon on a handheld — and bring `swayipc-types::Node`, which would displace the tested parse seam the issue explicitly wanted kept. The framing it replaces is a header and two `read_exact`s.

**The event is a trigger, never the data.** A `window` event's `container` carries `pid` and `app_id` but **no workspace**, so `in_scratchpad` cannot be derived from it — and both consumers filter on that. The sweep re-reads the tree instead, exactly as `display_watch` already does for outputs, which is what leaves `walk`, `report_unowned_windows` and `is_infrastructure` untouched and still tested.

**Only four change types sweep.** One terminal's life emits `new, title, focus, floating, move, close, move`; `title` and `focus` fire constantly under a browser or a game, and reconciling on those would make *more* compositor traffic than the poll being replaced. `move` and `floating` are what a scratchpad transition looks like, which is how the Steam client is parked. Draining the nudge channel rather than sweeping per event is the debounce — sway emits a burst for one user-visible change, and reconciliation is already idempotent.

**Order is load-bearing: connect, then alias, then unlink.** `--sway-ipc-alias` hard-links the socket to a second name first (a hard link, so it must be inside `$XDG_RUNTIME_DIR`; connecting resolves a path to the inode, and the inode lives while any name points at it). An alias that was asked for and could not be made **aborts the unlink** — a session that is still drivable beats one that is hardened and inert. Aliasing is idempotent, and shepherdd never removes an alias.

**Hardening runs late in `run()`, after every sway connection is open.** Two event subscriptions (`window`, and `output` when docking is enabled) plus the request connection, which is lazy and so is forced with `connect_now()` before the unlink — unlinking first would leave it permanently unable to connect. `Subscription::open` has exactly two callers and `connect_now` one, all above the hardening call, which is the invariant to re-check if anything ever wants a new compositor connection later in the daemon's life.

**`dev headless` always routes through the alias, and takes `--harden-ipc`** to boot the way an installed device does. Both paths are driven identically, so the hardened path is exercised in dev rather than first meeting a real machine. Its readiness check is now two stages: either socket name means sway is up, and the alias appearing means shepherdd connected — two failures that used to be one indistinguishable "Sway did not answer IPC" timeout, and the second is by far the more common dev failure.

**The `Mod4+Shift+Escape` binding drops `&& swaymsg exit` for `||`.** shepherdd's shutdown already asks the compositor to exit over its held connection, so the tail was redundant; under hardening a `swaymsg` there could not connect anyway. It stays as the fallback for when shepherdd is not running to be asked.

## What this does not close

**[#144](https://github.com/aarmea/lunchbox/issues/144) itself stays open.** That issue is about shepherdd's *own* management socket — `crates/shepherd-ipc/src/server.rs` granting `Admin` by peer uid, and never consulting the role at dispatch. None of that is touched here. This closes the same class of hole on a different socket, which surfaced while scoping [#144](https://github.com/aarmea/lunchbox/issues/144).

Because the sway half shipping first makes it easy to assume the technique carries over, the design for the remaining half is written up in `docs/ai/history/2026-08-29 001 shepherdd-socket-peer-credentials.md`. The short version, so the PR stands alone:

- **The unlink does not transfer.** It worked here only because shepherdd could be made to hold its connections, after which sway's socket needed its name exactly once. shepherdd's own socket is permanently in the `swaymsg` position by design — the volume, brightness, stop-current and now screen-power bindings are all short-lived processes connecting by path, and there is no moment after which no new client connects.
- **Nor does a bearer token**, which is the next thing that suggests itself. Under a shared uid any secret a trusted client can read, an activity can read: `/proc/<pid>/environ` and `/proc/<pid>/cmdline` are readable at that uid, and a token file is owned by it. That is the same dead end this PR already documents for `SWAYSOCK`.
- **Peer credentials work**, but the credential is the easy half. `SO_PEERCRED`/`SO_PEERPIDFD` give an unforgeable pid; the hard part is what shepherdd compares it against. The check has to be an allow-list or it fails open on the cases it cannot classify, and the identity has to be the **cgroup** rather than the process group — `setsid` is unprivileged, so `tracked_pgids` is advisory rather than a boundary.
- **The prerequisite is coverage.** Scope creation is currently conditional on `options.firewall`, so a non-firewalled activity inherits shepherdd's own cgroup and is genuinely indistinguishable from the launcher, while a Steam game satisfies neither the cgroup nor the pgid test. Every activity needs its own scope before any of this is a boundary. That is the bulk of the work.

The threat-model half of this PR — why no path or permission scheme helps under a shared uid — transfers verbatim.

**Closing sway's IPC removes the command channel, not the compositor as an attack surface.** Every activity is still a Wayland client, and sway has no per-client protocol filtering: `zwlr_layer_shell_v1` can cover the HUD, `zwp_virtual_keyboard_v1` and `zwlr_virtual_pointer_v1` can synthesize input, `zwlr_screencopy_manager_v1` can capture the screen, `zwlr_output_power_manager_v1` can blank it. `exec` is the only one of these that escapes both the firewall and the supervisor, which is why it was worth doing — but the claim should be read that narrowly.

**Two failure modes are left open, deliberately.** The transport rewrite changes what "the compositor is gone" means and the hardening changes what recovery is available, so every component's death was walked and recorded in the [#147](https://github.com/aarmea/lunchbox/issues/147) note's *Failure modes when a component dies* register — most of it working as designed, written down so it is not re-investigated. Two rows are open defects, neither blocking:

- **A dead `window` subscription is silent.** The task logs and returns; no diagnostic is raised. Subscriptions are separate sockets from the request connection, so `list_windows` can keep succeeding and `CompositorUnreachable` never fires — escape detection degrades from ~100 ms to the 60 s safety net with one `warn!` as the only evidence. A smaller version of the defect this PR exists to remove, and `windows_for_sweep` already has the pattern to copy.
- **A shepherdd crash after hardening leaves sway up.** `sway.conf`'s `… shepherdd … || swaymsg exit` fallback cannot connect once the socket is unlinked, so a crash mid-session leaves a compositor with no supervisor. A *startup* failure is unaffected, because hardening runs late in `run()` and the name still exists then; a graceful shutdown is unaffected, because `logout` goes over the held connection. Pre-existing in mechanism — it applied to any device the installer opted in — but the default flip makes it the norm rather than the exception. No fix is proposed here on purpose: handing an alias to a supervisor would re-open the socket to everything at that uid and defeat the point.

**Nothing notices when a shepherd window disappears.** `is_infrastructure` exempts the launcher, HUD, pairing display and `wl-mirror` from orphan reporting, and there is no counterpart reacting to one going away — so an activity that issued `[app_id=org.shepherd.hud] kill` removed the HUD for the rest of the session. Hardening removes that hostile route but not a crash, and nothing respawns either surface. A `window::close` on an infrastructure `app_id` is exactly the signal for a respawn or a `Critical` diagnostic, and it is the same subscription this PR adds. Left out deliberately: it is its own issue, not a rider on this one.

- CI's `shellcheck` invocation over the changed scripts.

Beyond that, the whole stack was booted headless both ways, because none of the interesting behaviour has a unit test that could prove it:

- **Unhardened** (plain `dev headless`, the development default): `sway-ipc.<uid>.<pid>.sock` still present and `swaymsg -t get_version` answers on it, log shows aliased-but-not-unlinked. This is the property every dev entry point depends on.
- **Hardened** (`dev headless --harden-ipc`): the opt-out is stripped from the derived config, the log says "socket unlinked", the ambient name is gone, and `dev tree` / `dev shot` keep working through the alias.
- **The installed shape**: `install_sway_config`'s rewrite produces an exec line with no opt-out, while `sway.conf`'s keeps one.
- **The live IPC path**, from a hardened boot: window-event subscription and output-event watch both open, a launch billed off `Activity window appeared` (the `list_windows` hot path this branch rewrote), the launcher focused again after `stop_current`, and no `CompositorUnreachable` raised at any point.
- **From an activity's position** (only `XDG_RUNTIME_DIR` in the environment): no socket found, and following the bound path out of `/proc/net/unix` yields `Unable to connect`.
- **Screen blanking, on a hardened session** — i.e. one where `swaymsg` genuinely cannot connect: `--screen-off` takes the output's `dpms` from `True` to `False`, `--screen-on` brings it back, and with `lofi-beats` running the blank is refused (`Screen blank suppressed: an activity is running`) and the output stays on.
- **Event latency**: an unowned `foot` window spawned into a hardened session was reported **0.109 s** later — most of that being foot's own startup, the rest one monitor tick. Previously up to 2 s, or never, for a window that came and went inside one sweep.

Two failures that showed up in the headless runs are unrelated to this branch and pre-date it: `config.example.toml`'s Lofi Beats YouTube URL is dead upstream, and the dev machine has no Bluetooth adapter, so the BLE server errors out.
