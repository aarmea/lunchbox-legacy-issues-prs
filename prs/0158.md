## Description

Fixes [#144](https://github.com/aarmea/lunchbox/issues/144)

Closes the half of [#144](https://github.com/aarmea/lunchbox/issues/144) that the sway work ([#147](https://github.com/aarmea/lunchbox/issues/147)/#148) left open. That branch
closed the *compositor's* socket; this one closes shepherd's own — and then,
after review, closes the four ways round it that turned up when the check was
attacked rather than admired.

`crates/shepherd-ipc/src/server.rs` derived a role from the peer's uid at
accept — and every activity runs as shepherdd's uid, so every activity got
`Admin`. The role was then stored, logged, and **never consulted at dispatch**,
so there was no partial protection to preserve: a game could call
`stop_current`, `launch` another entry, or `logout`. Observed, not inferred —
from inside a firewalled activity scope, `health` and `service_state` answer in
full.

## Why not the two obvious fixes

**Not the unlink.** Sway's socket could lose its name because shepherdd holds
its connections and nothing else needed the path again. Ours is permanently in
`swaymsg`'s old position by design: `sway.conf` binds short-lived clients that
connect by path at arbitrary times all session long — volume, brightness,
`stop_current`, `swayidle`'s screen blanking. There is no moment after which no
new client connects.

**Not a token.** Under one uid, any secret a trusted client can read, an
activity can read: `/proc/<pid>/environ` at the same uid, `cmdline`
world-readable, a token file owned by the uid that is also the activity's. It
would look like protection while providing none.

## What does work

The peer's **cgroup**. The kernel maintains it, every descendant inherits it —
including double-forked and reparented ones, where a PPID walk falls apart —
and an unprivileged process can neither forge it nor climb out of it.

shepherdd accepts a connection only from:

| peer | verdict |
| --- | --- |
| a process in shepherdd's own cgroup — sway, the launcher, the HUD, sway's keybinding one-shots | accepted |
| root, from any cgroup, so `sudo` still reaches the daemon from an operator's own shell | accepted |
| anything else, including anything that cannot be identified | **refused at accept** |

Decided **once per connection, at accept**, not per call: one decision instead
of many, it cannot be forgotten when someone adds a method, and a peer that
should not be reading state at all never reaches the event stream. A refusal
just closes the connection — a refusal that answers is a refusal that can be
probed.

It is an **allow-list**, and the distinction is load-bearing rather than
stylistic. "Refuse peers I recognise as activities" fails open on the cases it
cannot classify, and there is a working escape that lands in exactly that gap:
an activity can ask `systemd --user` to start a process for it in a cgroup that
is in no shepherd scope at all. Only "is it *in shepherd's* cgroup" refuses
that.

The cgroup id comes from `SO_PEERPIDFD` + `PIDFD_GET_INFO`, so the decision
never goes through `/proc` and never looks anything up by pid — the pid-reuse
race does not arise rather than being mitigated. `cgroupid` is the cgroup
directory's inode, so the comparison is one `u64` against a value cached at
startup.

## Then the check was attacked, and it did not hold

A deliberate hunt for ways round the allow-list (`docs/ai/history/2026-08-29
004`) found three, one of them reachable by any activity with a single file
write. All three are fixed here; the rest of this PR is that work.

### 1. An activity chose shepherdd's entire environment

`shepherdd` execed `systemd-run`, `pkexec`, `snap`, `flatpak`, `systemctl`,
`wpctl` and twenty more **by bare name**, resolved through `$PATH`. That would
be untidy if the session's `$PATH` were merely inherited. It is worse: on a
stock 26.04 + GDM host the kiosk user *dictates* it. `/etc/pam.d/gdm-password`
and `gdm-autologin` carry `pam_env.so … user_readenv=1`, and libpam-modules
still honours it, so `~/.pam_environment` — a file every activity can write —
sets the session's environment.

Measured against GDM's own PAM stack with a `pam_getenvlist` harness:

```
$ sudo ./pamenv gdm-password shepherd-kiosk
PATH=/home/shepherd-kiosk/evil:/usr/bin:/bin      <- attacker-chosen
```

So: write one file, drop a `systemd-run` on the resulting `PATH`, and at the
next login shepherd execs it — as a direct child of the daemon, **in the
daemon's own cgroup, which the management socket accepts as `Admin`**. The same
substitution turns `user_scope_argv_prefix` into a no-op, so every activity
lands in shepherd's cgroup too, and nothing fails loudly.

Sanitising `$PATH` would not have been enough, because the environment is
attacker-chosen wholesale. `helpers::resolve` therefore does not read the
environment at all: it searches a compiled-in list of root-owned directories
and returns an absolute path. A name found nowhere resolves to
`/usr/bin/<name>` rather than falling back to a `$PATH` lookup — that fails at
spawn exactly as a missing tool always did, which `pactl` and `wl-mirror`
legitimately are, while being something an activity cannot satisfy.

**And the rule is enforced, not just documented.** `clippy.toml` now disallows
`std::process::Command::new` and `tokio::process::Command::new` workspace-wide,
pointing at `helpers::command()`. Legitimate spawns take an
`#[allow(clippy::disallowed_methods)]` with a comment naming which exception —
an activity's own command from `config.toml`; the sidecars and pairing overlay,
already resolved; the firewall helper, which only ever runs under `pkexec` and
so gets polkit's replaced environment (measured: its `PATH` is root-owned
throughout); `shepherd-media-cache`, which must not depend on
`shepherd-host-linux` and has an injected resolver for that reason; and tests
and build scripts.

Arming that lint found a live gap on its first run: `brightness.rs` was still
exec'ing `brightnessctl` through `$PATH`. The original sweep matched
`Command::new("<literal>")` and this one names the binary in a `const`, so it
had been missed — exactly the failure mode a grep-based guard would also have
missed.

### 2. An activity could take over the management socket's name

Demonstrated end to end: the socket lives in a directory owned by the uid every
activity runs as, so an activity can `unlink()` it and `bind()` its own listener
at the same path. Existing connections survive; every *new* one — a relaunched
launcher or HUD, a keybinding one-shot, `swayidle`'s screen blank — reaches the
impostor, and nothing checked who answered.

The obvious fix does not work, and the reason generalises. Measured:

```
root-owned dir, 0755:  bind: BLOCKED -> [Errno 13] Permission denied
sticky bit, 1777:      activity unlink: SUCCEEDED
```

A directory shepherdd cannot write is one it cannot *bind* in, and the sticky
bit restricts deletion to the file's **owner**, which an activity is — it shares
the daemon's uid. **No file mode helps while the uid is shared.** Prevention
needs the socket created by something other than the daemon (systemd socket
activation), which shepherdd cannot use while sway `exec`s it.

So the question is asked backwards. `IpcClient::connect` now identifies the
listener with the same `SO_PEERPIDFD` machinery the daemon uses on its peers:
shepherd's own clients live in the daemon's cgroup, so "is the server in my
cgroup?" is exactly the question, and an activity's listener is in a scope of
its own by construction. The name can still be taken; what an impostor cannot
do is be *believed*.

The two failure modes fail in **opposite directions**, deliberately. A server
that cannot be identified is refused — an impostor can *cause* that by exiting
once the connection is accepted. A client that cannot read its *own* cgroup
warns and continues — nothing an activity does causes that, and refusing would
leave a device with a launcher that will not start.

An abstract socket would have made the takeover impossible — no directory entry
to unlink — and `server.rs` now carries a comment saying why it is still not the
answer: an abstract name ignores filesystem permissions entirely, which would
foreclose the fix that ends this class, uid separation plus a 0700 socket
directory ([#105](https://github.com/aarmea/lunchbox/issues/105)/#157).

The residual is denial: an activity can still make the session unreachable.
`IpcServer::socket_was_replaced` compares `(st_dev, st_ino)` against what was
bound, polled once a minute, raising the new `Critical` diagnostic
`ipc_socket_replaced` — because that should not look like a launcher that
stopped working for no reason.

### 3. A refused peer could bury the warning

Each refusal cost a `warn!` line and a diagnostic whose text names the peer's
cgroup — and a diagnostic whose text has changed wakes every subscriber: the
web UI, the companion app, the launcher. An activity could `connect()` in a loop
and drown the exact channel an administrator watches for this.

A refusal is also **audited** now (`AuditEventType::ClientRejected`), which the
issue asks for and which was missing while an *acceptance* was being recorded —
so a peer that connected legitimately left a trace and one that was turned away
left none.

The note first suggested dropping the cgroup from the message so repeats dedupe.
That is wrong: naming it is a deliberate, tested decision, and it is what turns
"something probed the socket" into "this activity did". So the *reporting* is
rate-limited instead. The first refusal is reported in full — a single probe is
never silent — then at most one a minute, carrying the count it suppressed.
Measured against a live daemon: **200 refused connections produced zero extra
reports.**

### 4. The source: `~/.pam_environment` itself

shepherdd no longer trusts its environment, but that file still set the
environment of everything *else* in the session. `shepherd harden apply` now
strips `user_readenv=1` from every `/etc/pam.d` service that enables it — seven
GDM services on a stock 26.04 — and `harden revert` puts them back.

Deleting the file instead would not work, for the same reason a root-owned
socket directory does not: the user owns their home, so they can remove a
root-owned file there and put their own back. The configuration that *reads* it
is what has to go, and that lives in root-owned `/etc/pam.d`. Verified with the
attack file left in place: before, the session got
`PATH=/home/shepherd-kiosk/evil:…`; after, the stock `/etc/environment` one.

Fixing that surfaced two more bugs in `harden` itself, both fixed here: it
aborted on any second run (`grep -l` exits 1 when it finds nothing — the success
case — under `set -o pipefail`), leaving a half-hardened user that `harden
revert` then declined to touch; and it backed up *system-wide* files per user,
so hardening two users and reverting the first silently un-hardened the second.
System-wide changes now live in one refcounted place and are restored only when
the last hardened user is reverted; shared files that take a per-user rule get a
marked block that revert removes surgically.

## Two preconditions, enforced rather than assumed

**Activities have to be somewhere else.** Firewalled entries already get the
helper's system-manager scope, snap and flatpak are scoped by their runtimes,
and Steam is preloaded as a snap. Only plain `Process` entries needed anything,
and they now go through `systemd-run --user --scope --collect` —
**unprivileged**, no helper and no polkit, because all this must achieve is "not
shepherd's cgroup". Like the helper's `systemd-run`, it execs in place, so every
pid/pgid/kill path is unchanged.

**shepherdd must not itself sit in the user manager's delegated cgroups**, where
any process at this uid can join any other outright. shepherdd reads its own
cgroup at startup and raises `ipc_socket_not_hardened` (`Critical`) if it finds
itself there. Both failures leave the session running, matching
`harden_compositor_socket` rather than [#152](./0152.md)'s fail-closed: an unhardened kiosk
beats a child staring at a dead screen, as long as it is said out loud.

## Opting out

Two flags now, because one was doing two jobs. `--no-restrict-ipc-peers` decides
who may **drive** the daemon; `--trust-environment` decides which binaries it
**runs** and where it writes browser policy. Coupling them meant every dev and
e2e run took binaries from `$PATH`, so the trusted-directory resolution a device
uses was exercised only by unit tests. Only the e2e suite passes the second (it
stubs `flatpak`, `pkcheck` and `pkexec`), so an ordinary dev session now
resolves helpers exactly as a device does.

**None of the development switches read the environment any more.** They did,
and it was a complete bypass: measured before removal,
`SHEPHERD_NO_RESTRICT_IPC_PEERS=true` disarmed the peer check outright, so on a
device that had not run `shepherd harden apply` an activity could put that in
`~/.pam_environment` and switch off the whole of [#144](https://github.com/aarmea/lunchbox/issues/144) at the next login.
`--sway-ipc-alias` lost its binding too, and was the worst of them: it does not
disarm a check, it hands out a *working compositor socket* at a path the caller
picks. A flag can be stripped from the installed config and verified — which
`shepherd install sway-config` now does for all three, dying if any strip fails
— and an environment variable can be neither.

While there, every remaining `SHEPHERD_*` variable was audited:

| variable | status |
| --- | --- |
| `SHEPHERD_*_BIN`, `SHEPHERD_FIREWALL_HELPER`, `SHEPHERD_BROWSER_ROOT`, `SHEPHERD_RETROARCH_ROOT` | gated behind `--trust-environment` |
| `SHEPHERD_NO_*`, `SHEPHERD_SWAY_IPC_ALIAS` | no longer settable from the environment at all |
| `SHEPHERD_LIBRETRO_DIR`, `SHEPHERD_RETROARCH_CONFIG_DIR` | ungated by design — both document a production use; they want to be `config.toml` settings, i.e. [#157](https://github.com/aarmea/lunchbox/issues/157)'s surface |
| `SHEPHERD_DATA_DIR`, `SHEPHERD_SOCKET` | **[#157](https://github.com/aarmea/lunchbox/issues/157)** — read by `shepherd_util::paths` for every binary, so deleting the clap binding would look closed while staying live |
| `SHEPHERD_MOCK_TIME` | `#[cfg(debug_assertions)]`, inert in the release build a device ships |

Gating `SHEPHERD_RETROARCH_ROOT` needed its tests restructured first —
`paths_for_in` / `prepare_in` take the root as an argument, so four tests pass a
scratch root and touch no environment at all.

## Testing

`cargo fmt`, `clippy --workspace --all-targets -- -D warnings`, and the full
workspace suite (**1015 tests**) are green, as is the e2e suite the way CI runs
it (`--include-ignored --test-threads=1`).

**[#144](https://github.com/aarmea/lunchbox/issues/144)'s acceptance criteria are all met**, including the regression test it
asks for: *"connect from an unregistered process, assert `adjust_tokens` and
`extend_current` are refused."* That is
`crates/shepherd-e2e/tests/ipc_peer_check.rs`, with a `restrict_ipc_peers`
option on the harness to arm the check.

Two details are what make it test something rather than pass. It cannot use
`IpcClient` — that verifies the *server's* cgroup before it speaks, so from a
foreign cgroup it would refuse the daemon and never reach the daemon's
allow-list, proving the call fails but not that the server refused it. So
`src/bin/peer-probe.rs` speaks the protocol over a raw socket. And it was
checked against a *disarmed* daemon, where the foreign peer does reach
`adjust_tokens` and gets an answer back: a refusal test that cannot observe an
acceptance is not evidence.

**The gap the last revision of this description called out is closed.** It said
"there is no e2e test for the check… closing it means teaching the harness to
boot into a system-manager scope — its own piece of work." That work is here.
`shepherd dev headless --harden-ipc-peers` strips the opt-out the way
`--harden-ipc` does, and runs the session in a system-manager scope, which is
not delegated and is structurally what a display manager's session scope is. It
verifies the outcome rather than assuming it: asking for the armed check and
getting a degraded one is invisible from the outside — the session comes up and
every client still connects — so the harness greps the daemon's own log and dies
with the daemon's reason if it did not arm.

Measured in that session, and separately against a hand-started daemon:

| peer | result |
| --- | --- |
| the launcher, the HUD and sway's one-shots (8 clients, sharing shepherdd's cgroup as on a device) | accepted |
| a probe from another cgroup, same uid | refused at accept, refusal logged |
| root from another cgroup (`sudo`) | accepted |
| 200 refused connections in a burst | one report, not 200 |

The `sudo` row is the one worth having measured rather than assumed: if it were
wrong, hardening a device would lock its operator out, and no unit test proves
it against a real socket. The recipe for reaching the armed path without a
device is in `crates/shepherd-ipc/README.md`.

One test-hygiene bug is fixed here too, because it bit during this work. Three
fixtures wrote stand-ins that ran `while true; do sleep 0.05; done`; each test
kills what it spawned, but a failing assertion unwinds past that and the
stand-in outlives the test process. One escaped and sat on the box for six
hours, and what it eventually broke was not itself —
`firewall_unsupported_path_gates_activity` asserts that no `sleep` is running,
and matches any process on the machine. The loops are bounded now, so the panic
path leaks something that dies rather than something that does not.

Two CI problems surfaced on the way and are fixed here:

- **The peer tests could not run at all.** These jobs run in a container, so
  they get the host's kernel however new the image is, and the runner's was
  older than `PIDFD_GET_INFO`. They now skip below the floor — and because a
  skip is invisible (cargo captures a passing test's output),
  `SHEPHERD_REQUIRE_PEER_CGROUP=1` on the `test` and `e2e` jobs turns a skip
  into a failure naming the reason.
- **CI ran as root, and that hid a bug.** Once the runner was upgraded past the
  floor, `an_armed_policy_refuses_a_peer_from_another_cgroup` failed: `classify`
  accepts root from any cgroup by design and checks that *before* the cgroup, so
  passing `Some(getuid())` never reached the comparison. Two neighbouring tests
  were passing for the same wrong reason. All three now claim a fixed non-root
  peer uid and test the same thing wherever they run — and the `test` job now
  runs the suite as an unprivileged `ci` user so the class cannot come back. That
  needed the toolchain moved out of `/root/.cargo`, where a non-root job cannot
  reach it, to `/usr/local`; the cache paths in both workflows follow. Verified
  by building the CI image and running the step in it: the peer tests execute as
  `ci`, with the guard armed and no skips. What that cannot cover is how the
  runner mounts the workspace, so the first CI run is the real test of it.

## What is deliberately not in here

**No per-method role tiers.** `ClientRole` is consulted nowhere, and once the
allow-list is in place every accepted peer is either root or shepherd's own
code, so a tier split would have nothing to enforce.

**This closes the local socket, and only that.** [#156](https://github.com/aarmea/lunchbox/issues/156) (the management HTTP API,
a superset of this surface, open by default) and [#157](https://github.com/aarmea/lunchbox/issues/157) (policy and usage state
file-backed at the activities' own uid) both reach the same effects and are out
of scope. [#157](https://github.com/aarmea/lunchbox/issues/157)'s note has been extended with the environment doors to that same
state.

**Prevention of the socket-name takeover.** Only socket activation closes it;
here it is reported, not prevented.

## Still worth confirming on a device

The armed path has now been exercised for real, but not on a GDM-started kiosk:
what remains unproven is that a real kiosk session lands in a non-delegated
cgroup. First boot on `leibniz` should log `Management socket accepts only this
session and root` and raise no `ipc_socket_not_hardened`; any other line names
which precondition failed.

Worth checking too, because they changed and fail quietly: brightness
(`brightnessctl` was resolved through `$PATH` until this branch), RetroArch
saves across a stop/relaunch, `swayidle`'s screen blank, and that the kiosk user
can still log in after `shepherd harden apply`.
