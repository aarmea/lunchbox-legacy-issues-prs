## Description

Follow-up to the poll-spin fix (`2026-07-09 001`). Investigating "why do previously-paired BLE admin sessions fail to reconnect" surfaced several distinct bugs across the shepherd daemon and the Android companion. This PR fixes them together since they're the same feature area and interact (one server fix makes a companion bug reachable in normal use).

## Server-side (`crates/shepherd-ble`)

**1. Clear transport session state on peer disconnect** (`a8c6f40`)
The read-poll Response/Events outboxes and the Request-side `FrameReader` hold a per-session byte stream, whose only reset was the client's `id == 1` sentinel — sent only on a *fresh* `ShepherdConnection`. On a transient BLE drop the companion reuses the connection and resumes its id counter mid-sequence, so `id == 1` never fires and stale bytes desync the reassembler → corrupt frames, RPC timeouts. Now a BlueZ device-disconnect subscription wipes both outboxes + the reader when a peer drops.

**2. Remove the BlueZ bond on factory reset — both paths** (`23ef756`)
Factory reset cleared the admin record but left the bond, so the phone stayed bonded while the device went Unclaimed → reconnects came up encrypted then got `not_claimed`, and re-pair couldn't recover. The sentinel path relied on a stub that always returned `None`; the RPC path never attempted removal at all. Both now call `Adapter::remove_device` (the RPC path via a lifetime task that owns the adapter).

## Companion (`companion-android`)

**3. Recover from one-sided bonds + connection-lifecycle bugs** (`a06f353`)
Audit of the companion (see history doc) fixed the top cluster:
- **One-sided-bond recovery**: on connect give-up while still OS-bonded, scan-probe for the device — if it's still advertising the shepherd service yet the encrypted link won't hold, the bond is stale → `removeBond` (hidden reflection) + surface `NeedsRepair` so re-pair works. Without this the loop spun reconnects forever showing "Connected" (reachable now that server-side factory reset removes the bond).
- `connect()` propagates encrypted-drain failures instead of masking them (gated by `probeEncryptedLink` so the pre-bond pairing flow isn't misclassified).
- Fail in-flight RPCs on disconnect (no more 15 s hang); idempotent `close()`; close the connection on give-up (no leaked pollers).
- Track the pairing coroutine so backgrounding cancels it (was leaking a live link + doing background BLE); guard `onForeground`/`adopt` against a raced session.
- Guard `isBonded()` against `SecurityException`; use all backoff values; `factory_reset()` also clears the OS bond.

**4. Don't treat "shepherd not running" as a lost bond** (`42831a4`)
When the box is on and the bond is intact but shepherd isn't running (different user signed in), the encrypted drain fails identically to a real one-sided bond, so the earlier `LinkUnauthenticatedException → removeBond` fast-path wiped a good bond and forced a needless re-pair. Removed that fast-path — the scan-probe is now the *only* thing that removes a bond, and only on positive evidence (device still advertising the shepherd service). Shepherd down ⟹ service not advertised ⟹ scan finds nothing ⟹ retryable `Disconnected`, bond intact.

## Testing

- `cargo test -p shepherd-ble` (44), `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --all -- --check` — all clean. New unit tests cover the disconnect reset, both factory-reset bond-removal paths, and the unclaimed no-op.
- `companion-android :app:testDebugUnitTest` — passes.
- **On-device** (Pixel 10a ↔ live `shepherd-kiosk` daemon, booted headless as that user): validated happy-path connect, no poll-spin regression on BT toggle (17 log lines vs. the old 5.4 M), server-side disconnect-clear firing on hardware, and the full asymmetric-bond recovery (one-sided bond → scan-probe → `removeBond` → "Bond lost — re-pair needed"; the hidden `removeBond` reflection is not blocked on this device). The hardware pass caught two bugs now fixed: the detection point (encryption fails inside `connect()`, not at the first read) and `connect()` breaking the pairing flow.
