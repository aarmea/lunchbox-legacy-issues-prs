## Description

Closes [#140](https://github.com/aarmea/lunchbox/issues/140).

The management API has carried `list_windows` / `act_on_window` since the
BLE work landed, and the web UI has rendered them as a "Sway Windows"
page for as long. The companion app — the primary admin interface, and
the only one that works without a network — could not reach them. The
Android spec anticipated the gap and left it open ("useful for a hidden
developer panel", §4.9). This closes it.

## What's here

**Device controls → "Windows…"**, below "Log out device session":

- Two sections, **On screen** and **Scratchpad**, one card per window:
  title, `app_id`/`class` · pid · id, workspace, and a
  Focused/On screen/Hidden/Scratchpad chip.
- **Hide** / **Show** / **Close** per card — the same three actions
  `act_on_window` exposes. Close confirms ("Anything unsaved in it is
  lost"); Hide and Show don't, since they're reversible from the same
  screen.
- Refreshes every 5 s while the screen is open, plus a Refresh button.

The typed client (`listWindows`, `actOnWindow`) and the wire types
(`WindowInfo`, `WindowAction`, the `RpcMethods` constants) already
existed — generated from the Rust trait — so this is UI and view-model
only.

## Decisions

- **Not part of `DeviceUiState`.** The list is fetched only while its
  screen is open; putting it in the shared snapshot would spend an RPC on
  every connect for a list nobody is looking at.
- **Polled, not pushed.** `EventPayload` has no variant for a window
  opening, closing, or being stashed, so the screen polls while composed
  and stops when it isn't.
- **A failed refresh keeps the previous list**, with the error above it.
  Blanking on a refresh that lands mid-reconnect would pull the rows out
  from under a finger already reaching for a button — and the ids under
  those buttons are what `act_on_window` acts on.
- **The list is cleared when the active device changes.** Window ids are
  per-compositor; carrying one box's ids to another would act on whatever
  container happens to hold that id there. Reconnects to the *same*
  device keep the list, matching how the rest of the app treats a dropped
  link.

## Verification

`./gradlew :app:testDebugUnitTest :app:assembleDebug` passes. New tests:

- `WindowPresentationTest` — the title fallback chain (name → `app_id` →
  class → `Window <id>`, blank titles included), the subtitle, and
  scratchpad vs. merely-unrendered.
- `WireTest` — a two-window `list_windows` payload in both Wayland and
  XWayland shapes, and the `close`/`hide`/`show` wire spellings.

End-to-end over BLE against the headless dev session with a Pixel on USB
(`companion-pairing` skill), each phone action confirmed against
`shepherd dev tree`:

| Action | Phone | Device |
|---|---|---|
| Open the screen | "On screen (1)", launcher card, Focused chip | — |
| Hide | row → "Scratchpad (1)", "Moved to the scratchpad." | `visible: false` |
| Show | row → "On screen" | `visible: true`, focused |
| `swaymsg exec foot` on the device | second card appears unprompted within 5 s | 2 windows |
| Close → confirm | card gone | 1 window |

## Notes for the reviewer

- The run started with the app stuck in "Reconnecting…" and no connect
  attempt in the daemon log: shepherdd had selected the Qualcomm radio
  (`hci1`, `DC:56:7B:1F:7D:EA`) that the `companion-pairing` skill
  documents as individually broken. Unbinding it from `btusb` moved the
  daemon to the Realtek dongle and the link came up immediately. **The
  Qualcomm adapter is left unbound on the dev box**;
  `echo -n 3-6:1.0 | sudo tee /sys/bus/usb/drivers/btusb/bind` restores
  it, possibly under a different `hci` index.
- `actOnWindow(id, act)` spells its second parameter `act` because
  `action` is the private RPC-error wrapper it delegates to, which the
  parameter would otherwise shadow.
