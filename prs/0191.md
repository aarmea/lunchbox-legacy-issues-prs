## Description

Closes [#149](https://github.com/aarmea/lunchbox/issues/149).

BLE management could only ever be paired to one phone. That is fine for a
single-parent household and breaks down the moment there are two caregivers, or
the device travels between two homes.

The first phone to reach an unclaimed device still claims it on the spot —
there is nobody to ask yet. Every phone after that bonds, calls `claim`, and
gets back six digits plus a pending request that an existing administrator
approves from their own app. That is the shape [#156](https://github.com/aarmea/lunchbox/issues/156) built for letting a browser
in, reused deliberately: the number is compared across two screens, so a phone
racing the one you meant carries different digits.

TOFU is right for the first phone and wrong for the rest. A BLE pairing's anchor
is standing in front of the TV, and the person who does that most is the child
the device exists to supervise.

## Decisions taken before building

Scoped in `docs/ai/history/2026-09-07 007`, and settled with @albert:

| Question | Answer |
| --- | --- |
| Who may become the second admin? | Approval by an existing administrator. TOFU stays for the first phone only. |
| Simultaneous sessions, or turn-taking? | Turn-taking. Per-peer transport state is a follow-up, not this PR. |
| `minSdk`? | Lowered 31 → 30, so an Android 11 handset can run the companion at all. |

The `minSdk` change is the same argument as the feature: a household has
whatever phones it has. Below Android 12 that means the legacy Bluetooth
permissions and a location grant — the platform has no way to express
`neverForLocation` there — picked by SDK level in `ui/App.kt`.

## Either surface can approve

The roster — list administrators, approve a waiting phone, revoke one — is on
`ManagementService`, not routed inside the BLE server, so a browser can do it
as well as a phone. That is the shape [#156](https://github.com/aarmea/lunchbox/issues/156) already established:
`AdminSummary` and `EnrolmentRequestInfo` sit in `shepherd-management` beside
`WebSessionInfo` and `LoginRequestInfo`, and a new `AdminRoster` trait there is
implemented by `ClaimMachine`, exactly as `AdminAuthority` already was.

Putting them on the trait meant the BLE special-casing could be *deleted*
rather than duplicated: they pass the same gate every other RPC passes on each
transport — `authorize` over BLE, the session middleware over HTTP.

**The browser flow is the better one, for a non-obvious reason.** A peripheral
stops advertising while a peer is connected, so approving from another phone is
a relay: B asks, B is parked, A approves, A is parked, B collects. The browser
never touches the radio, so B stays connected throughout and flips to "Paired"
on its next poll.

Two consequences worth knowing while reading the diff:

- **`is_self` left the wire.** It only ever meant something for a phone, and
  over HTTP there is no phone to be. Keeping it would have meant threading a
  `viewer` argument through `ManagementService` for one transport's benefit, or
  the device guessing. The companion computes it locally — it already knows its
  own identity address, and the summary carries the same string.
- **The claim machine owns bond removal now.** `revoke_admin` and
  `factory_reset` queue their own unbonds rather than the BLE server doing it,
  because an HTTP caller has no channel to hand them. The unbond channel became
  unbounded so the send works from the synchronous trait.

## `authorize` compares addresses now

It used to allow any peer that reached it, on the reasoning that an
encrypt-authenticated write proves a MITM-protected bond and v1 only ever had
one. The second half stopped being true — and was never quite true, because
nothing stopped a phone from bonding and simply *not* calling `claim`, and the
device stays pairable while claimed with an agent that accepts everyone. A
child's phone, in the room, in front of the TV, had the whole management
surface. That is closed here.

## Wire and on-disk changes

- **Protocol → v2.** `claim` answers with a tagged `ClaimOutcome`
  (`claimed` / `pending`) rather than a bare `AdminRecord`. An older app would
  decode that as a malformed record, so the version gate turns a confusing
  failure into "update the app".
- **`admin.toml` → `[[admins]]`.** The v1 single `[admin]` table is read and
  rewritten on load, keeping its token and minting an id. Tested against a real
  pre-change record, not a synthetic one.
- **`AdminAuthority`** is now `verify_http_token` + `has_admin` rather than
  `current_http_token`. Each administrator has their own token; handing callers
  a `Vec<String>` of live credentials would push the constant-time comparison
  out to every one of them.
- **New RPCs** on `ManagementService`, so both transports and both clients get
  them generated: `list_admins`, `revoke_admin`, `list_enrolment_requests`,
  `approve_enrolment_request`, `deny_enrolment_request`. `claim` and
  `factory_reset` stay BLE-only, as before.

## Worth a reviewer's attention

Three things the unit tests could not have caught, all found on the bench and
all fixed here. The details are in `docs/ai/history/2026-09-07 008`.

**A peer has two addresses, and the difference decides whether an administrator
can reconnect.** A GATT request names its peer by D-Bus object path — for a
phone using privacy, the random address the link came up on. `Device1.Address`
on the same object is the identity address the bond is filed under. They are
equal often enough to fool a single sample, and differ exactly when a phone
claims mid-pairing, which is the normal case for a *second* phone: measured here
as a claim from `79:C2:1B:08:F0:32` against a bond being written to
`64:11:A4:B0:7B:D9`. Recording the path address writes an administrator that can
never authorize again.

So `resolve_peer` reads the identity once per session, records hold it, and
`PeerIdentity::matches` accepts **either** address — which is what keeps records
written before this working. The Pixel's migrated record is exactly that case,
live: it holds `78:61:DF:9B:2C:8E` and resolves to `B8:F4:A4:E5:20:F1`. Matching
only the resolved identity would have locked out the device's existing
administrator on upgrade.

**Removing a bond needs the path back.** `Adapter::remove_device` addresses by
object path, so revoking failed with `Bluetooth device does not exist` — and the
startup drain's "is this address in `device_addresses()`?" check would then have
read the same absence as *already settled* and dropped the queue entry, leaving
the bond forever with nothing left saying it should not be there. `device_path_for`
translates identity → path; both the live unbond task and the startup drain go
through it. This bug predates [#149](https://github.com/aarmea/lunchbox/issues/149); routine revocation is what made it
reachable.

**The protocol constant was hand-mirrored.** Bumping it device-side and not in
the companion's `Protocol.kt` compiles cleanly on both sides and surfaces only
as a phone refusing to pair, blaming *the app* for being out of date — on a
phone that had just been given the new build. `protocol_constants_match_the_companion`
now asserts the version and the five GATT UUIDs against the Rust definitions.

**Turn-taking is enforced by the radio first.** A peripheral stops advertising
while a peer is connected, so the second phone's scan lists nothing while the
first holds the link — and BlueZ goes on reporting the advertisement as
registered (`ActiveInstances` = 1), so the daemon looks perfectly healthy
throughout. The transport-level rule (`InProgress` for a second writer, empty
reads for a non-owner) is therefore defence in depth rather than what users hit.
Worth keeping: it is what stops the single-session `TransportState` from being
load-bearing on an accident of BlueZ configuration. It does mean the two-phone
flow is inherently a relay — B asks, B is parked, A approves, A is parked, B
collects.

## Known gaps, deliberately left

- **A denied or abandoned enrolment leaves the requester's BlueZ bond.**
  `authorize` refuses it, so it is a nuisance rather than a hole. Unbonding on
  denial was considered and dropped: the refusal is delivered on the requester's
  *next* poll, and removing the bond first takes away the link that would carry
  it.
- **Per-peer transport state** — agreed as a follow-up issue.
- **Recovery when the last admin phone is lost** is still `factory_reset`. The
  scope raised a TV-displayed enrolment code as the alternative; nothing here
  changes that answer.
- **A phone revoked and then re-approved keeps its old `http_token`**, because
  the companion only calls `claim` during pairing and reconnects on the bond
  alone. Inert today — BLE authorization compares addresses, not tokens, and
  the app never reads the stored token back — but it would matter the moment
  that token is offered to a human.

## One thing to agree with deliberately

A web session can now enrol a phone, and that phone outlives the session. The
web credential was already administrator-level — it can set the password and
rewrite the policy — and revocation sits on the same card, so this is
recoverable rather than a hole. But the *persistence* is new, and it is the one
part of this change that should be a decision rather than a default. Say so if
you would rather approval stayed on the phone.
