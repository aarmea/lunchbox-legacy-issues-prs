## Description

The counter-scale the HUD applies while an `xwayland_native_resolution`
activity holds sway at scale 1.0 only reaches sizes the HUD's own
stylesheet states, because it works by multiplying the `Npx` literals in
that stylesheet. Anything left to the GTK theme keeps its logical-pixel
value and so renders 1/factor too small on screen.

Two dimensions were falling through:

- `.warning-text` named no `font-size`, so the banner rendered at the
  theme's default font — 10px cap height against the 16px it should have
  been at factor 1.5. Fixed by stating the base size on `.hud-bar` (and
  on the confirm popover's contents, its own surface), so any label
  without an explicit size inherits a scaled one.
- The slider knobs asked for `min-width`/`min-height: 12px`, below the
  16px the theme picks on its own — so the theme won at factor 1.0 and
  the counter-scaled value only reached 18px where the un-hacked HUD
  draws 23px, shrinking the touch target exactly on a HiDPI panel. Now
  stated at 16px, along with the theme's -8px knob overhang, which has
  to scale too or the trough thickens under the bigger knob.

Both values match what the theme already does at factor 1.0, so the
un-hacked HUD is pixel-identical (verified: bar 54, knob 16, trough 4 at
scale 1.0; bar 81, knob 23, trough 6 at scale 1.5 — unchanged).

Verified in the headless dev session against a fixture with two
otherwise-identical entries differing only in
`xwayland_native_resolution`: under the hack the knob goes 18 -> 24 px
and the warning text 10 -> 16 px, matching the scale-1.5 reference.
