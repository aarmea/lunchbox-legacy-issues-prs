## Description

Closes [#185](https://github.com/aarmea/lunchbox/issues/185).

The graphical config editor has been complete since August and deliberately
unrouted: its only `ConfigSource` edited a file on whatever computer was doing
the browsing, so a "Config" tab in a device's own management UI would have read
as "edit this device's configuration" while doing nothing of the sort. [#185](https://github.com/aarmea/lunchbox/issues/185) was
gated on [#156](https://github.com/aarmea/lunchbox/issues/156) landing first, because writing a config runs whatever
`kind = { type = "process", command = … }` is given, and before the login
existed the API shipped open on an unclaimed device.

This routes it, against the device's real policy.

<!-- screenshots: the Config tab, and the Danger Zone on the Device tab -->

## What it does

`GET`/`PUT /api/v1/config` hand the editor the device's `config.toml` and take
it back. A save writes the file — atomically, through a rename — and the state
custodian's watch turns that into a reload within a second, the same path
`sudoedit` and `shepherd install policy` already take. There are three ways to
change what a device allows now, and this is the only one that needs neither a
terminal nor a file.

Comment preservation is the whole point of the editor and it holds end to end:
a label changed in the browser's form and saved to a device rewrote **one line
of a 51 KB file, with all 666 comment lines intact**.

## Three decisions worth reviewing

**The write is behind `require_auth` and nothing more.** The 2026-08-19 scope
gated this on privilege separation — a config write restricted to some subset
of the credentials. [#156](https://github.com/aarmea/lunchbox/issues/156) settled that question the other way when it shipped
`set_web_password` with *"no old password required: the caller has already
proved they are the administrator by reaching this trait at all"*. A surface
that already hands over the device's management credential permanently is not
made safe by withholding a config write. The gate that did have to exist is
that the surface is shut at all, and since [#156](https://github.com/aarmea/lunchbox/issues/156) it is. **The phase-4 clause is
struck, not satisfied**, and the docs say so, so nobody goes looking for a
control that was decided against rather than forgotten.

**The endpoints are not RPCs.** `#[management_rpc]` builds a `dispatch_json`
arm for every `async` trait method, and BLE serves that dispatcher against a
16 KiB frame cap — while a real policy is comfortably 50 KB. A config on the
JSON-RPC surface would be a method that exists and cannot work, in both
directions. The trait carries `read_policy` / `write_policy` as **synchronous**
methods, which the macro skips; `shepherd-http` reaches them over dedicated
routes, the same way [#156](https://github.com/aarmea/lunchbox/issues/156) kept the login exchange off the trait. Consequence
worth stating: **the companion cannot edit a config**, now a decision rather
than an accident.

**`If-Match` is required, not optional.** A device's policy has three writers,
and the other two are a person at a terminal. Forgetting the precondition
answers 428 rather than silently discarding their work; a stale tag is 412,
which tells a client to re-read rather than retry. `If-Match: *` is how a
caller says "overwrite whatever is there".

## Two bugs found on the way, both pre-existing

**`reload_config` blanked the launcher on every installed device.** It read
`config_path` while the daemon's own reload reads the custodian — and since
[#157](https://github.com/aarmea/lunchbox/issues/157) those are different files: the custodian holds the policy, the home path
holds the *signpost*, a valid policy with zero entries. Pressing "reload" over
HTTP or BLE replaced the running policy with an empty one. Fixed here because
it is the same plumbing, and because leaving that on the screen this PR adds
was not a thing to do deliberately.

**The config watcher never fired on a relative `--config`.** It compared whole
paths — the one `--config` was spelled with against the one `notify` reports.
Every dev entry point passes `-c ./config.example.toml`, so auto-reload was off
for the *entire development stack* while the log line said it was on. On a
device the path is absolute, which is why nobody had seen it. Found because
this PR's write path is deliberately reloadless and rests on that watch: on the
dev stack, a plain `touch` on the config reloaded nothing.

## The Danger Zone

`[service.management_api]` is *in* the file being edited. A save that disables
the API, moves it to an address the browser cannot reach, or drops TLS on a
non-loopback bind ends the session that made it — on a device where
`harden apply` has left the kiosk user `nologin` and no SSH. Every other
section on that page is recoverable by editing it again from the same place, so
that one gets a red rule and a sentence naming what goes wrong.

Only that one: losing Bluetooth management does not lock anyone out of HTTP,
and a danger zone that contains everything warns about nothing.

## Cost

`dist/` goes 1 635 281 → 3 140 996 bytes, ~950 kB of it the wasm validator, so
about **+5% on a release `shepherdd`**. Both are lazy chunks — a browser that
never opens the tab never fetches them — so the cost is the binary and the
`.deb`, not first paint.

## Verified on hardware-ish

Driven on the headless dev stack with Firefox over Marionette, not just built:

- `GET` returned the whole 51 KB `config.example.toml` with an `ETag`,
  `text/plain`, `no-store`.
- `PUT` with that tag changed an activity's label and **the launcher grid
  showed it within a second, with no reload call** — the journal shows
  `Policy replaced through the management API` then `Config reloaded`.
- 412 on a stale tag, 428 with no `If-Match`, 422 on TOML that does not parse
  (carrying the parser's own line and column), 401 with no credential. Nothing
  written in any failure case.
- The wasm module serves as `application/wasm`.
- Comment preservation, as above: `1 insertion(+), 1 deletion(-)`.
- The concurrency guard: with the editor open, a `sed` against the file
  standing in for `sudoedit`, then a save — *"The config on the device changed
  while this was open — someone edited it over SSH, or from another browser.
  Reload to see what is there now; this copy has not been saved."* The SSH edit
  survived.

Full `cargo test` (workspace), clippy, `fmt`, `tsc`, the config-editor import
boundary, schema coverage and vitest all pass. Every commit in the series
builds on its own (`git rebase --exec cargo check`).

## Not done

- **No diff-before-save view.** Phase 3 of the 2026-08-19 list, and more useful
  now: `If-Match` tells you *that* somebody else wrote the file; a diff would
  tell you what they wrote.
- **The editor on a phone** is the same desktop-shaped editor, now with the
  whole viewport. Accepted, not solved.
- **The companion still cannot edit a config**, per the transport decision
  above.
