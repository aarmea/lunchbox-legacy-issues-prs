## Description

Read-only network status on both management UIs: the wireless network the device
is on, its addresses, the connectivity checks, and where the web interface is
listening — if it is.

Closes [#182](https://github.com/aarmea/lunchbox/issues/182).

## Why

The companion app reaches a device over BLE and has no idea what its address is.
Without this, using SSH or the web interface means `arp`-ing or `nmap`-ing the
LAN for a device that does not announce itself. The web UI gets the same page for
symmetry, but the phone is the consumer that cannot answer the question any other
way.

## What it looks like

Both UIs show, in this order: whether the device is online, where the web
interface is listening and the URLs that reach it, the connectivity checks, then
the interfaces — the ones another machine can reach first, everything else folded
behind a disclosure. Addresses and URLs are tap-to-copy, which is the whole point:
an address is only useful once it is in an SSH client.

On the device this was built on, that is two URLs (`http://192.168.0.139:8080`
and the ZeroTier `http://172.27.154.85:8080`), one wireless card reading
"Connected to … — 60% signal · 5 GHz", and "Show 3 other interfaces" hiding
loopback, `lxcbr0`, and a down `p2p-dev-*` device.

## Shape

```
LinuxNetworkInfo (NetworkManager over D-Bus, getifaddrs fallback)
  → NetworkSnapshot                      raw parts, per host
      +
    WebListenerHandle                    what the listener is really doing
  → NetworkStatusView::new(…)            every judgement, made once
  → network_status()                     one RPC, both transports
      → NetworkPage.tsx / NetworkScreen.kt
```

`#[management_rpc]` generates the dispatcher and both transports are
pass-throughs, so the new trait method needed no route, no handler, and no auth
work. `shepherd-wire-codegen` produced the TypeScript and Kotlin payload types.

`NetworkStatusView::new` is where `reachable`, the interface ordering, the cap and
the management URLs are decided. A `NetworkInfoProvider` hands over what the host
said and nothing more, so a second host implementation cannot quietly disagree
with the first — and every one of those decisions is unit-tested without a D-Bus
daemon to talk to.

Reading NetworkManager needs no new dependency (`shepherdd` already proxies it for
the suspend cover and the connectivity re-check) and no polkit rule — every
property is readable unprivileged. A host without it still reports interfaces and
addresses via `getifaddrs`, just no SSID, and says so through
`NetworkSource::Interfaces` rather than rendering a blank.

## The web listener, and a failure that used to be invisible

The configured `bind`/`port` is an intention, not an outcome: the bind is retried
while its address does not exist (`bind_retry_seconds`, for a VPN interface still
coming up at login), `port = 0` binds to something else entirely, and a bind that
never succeeded reached exactly one `error!()` line — on a device whose web
interface is precisely how somebody would have read that log. From every UI, a
device whose management API never came up looked identical to a healthy one.

So `HttpServer` now publishes its real state into a `WebListenerHandle`, and a
listener that gives up raises `DiagnosticCode::ManagementApiUnavailable` — which
surfaces on both existing Health screens with a remedy, for free. It is a
`Warning`, not a `Critical`: the companion is on BLE and unaffected, so this is
one path lost rather than a device lost.

Deliberately not raised while a bind is still being retried; otherwise a VPN
interface coming up at login would alarm every boot and clear seconds later.

## Decisions worth a look

- **`reachable` is derived, not reported.** Loopback and container bridges are
  never a way in; a VPN always is; an unrecognised device type is treated as
  reachable, because being wrong about a veth costs a line in a list while being
  wrong about a real interface costs the address somebody needed. On a box running
  containers, `10.0.3.1` looks exactly as much like an answer as `192.168.0.139`
  does, and only one of them is.
- **One URL per interface, IPv4 preferred.** The first working version returned
  five URLs from a `0.0.0.0` bind — one IPv4 plus three IPv6 privacy-extension
  temporaries plus the VPN. Every address is still listed under its interface;
  only the "open this from another device" list is narrowed.
- **A listener that is not serving offers no URL at all.** An address that will
  refuse the connection sends somebody to debug their phone instead of the device.
- **The connectivity checks are not duplicated onto the wire type.** They already
  ride `ServiceStateSnapshot.internet_status`. The companion holds a snapshot
  already; the web UI queries per page and had no `service_state` call, so the web
  client gained one whose only caller is this page. One source for one fact.
- **No MAC addresses or BSSIDs.** They are the fingerprintable part and serve
  neither "SSH in" nor "open the web UI". Easy to add later if wanted.
- **IPv6 link-local is listed but never offered as a URL** — `fe80::…` needs a
  zone index, and the phone's zone is not the device's.

## Verification

Beyond the unit tests, the parts no unit test can reach:

- `from_network_manager()` against the real system bus as an unprivileged user
  (an `#[ignore]`d test in `shepherd-host-linux`): SSID, signal, band, addresses,
  gateway, DNS, ZeroTier typed `vpn`, `lxcbr0` typed `bridge`. This is the
  assertion that the D-Bus property names and types match what NM actually
  publishes.
- `interfaces_from_kernel()` in a plain unit test — it has to work in a CI
  container with no NetworkManager, which is exactly when it is load-bearing.
- The RPC end to end over the real HTTP API against a running daemon.
- The web page rendered by a real browser in the headless dev session, against
  that same daemon.

## Docs

Three gotchas that cost real time here are now written down in the repo rather
than left for the next person to rediscover:

- **`CONTRIBUTING.md`** — `schemars` renders a fieldless enum two different ways
  depending on whether its variants carry doc comments, and documenting *some* of
  them fails codegen with a message that names the wrong fix
  (`add it to HAND_WRITTEN`).
- **`CONTRIBUTING.md`** — Gradle 8.10.2 cannot parse the JDK 25 that Ubuntu 26.04
  ships as `default-java`, and fails with a bare `25.0.4` that mentions neither
  Java nor Gradle.
- **`.claude/skills/headless-dev/SKILL.md`** — how to drive a browser inside the
  headless session: `dev click` does not activate a link on a web page any more
  than it does a GTK widget, the SPA has no URL routing to deep-link with, and
  Firefox is a snap whose `--profile` cannot point outside
  `$HOME/snap/firefox/common`.

Crate READMEs for `shepherd-host-api`, `shepherd-host-linux` and
`shepherd-management` cover the new trait, the NM implementation, and
`WebListenerHandle`. The scope investigation and the implementation note are in
`docs/ai/history/` (`2026-09-07 003` and `004`), including where the scope turned
out to be wrong.

## Out of scope, as filed

Any wifi configuration — joining a network, forgetting one, toggling an adapter.
Read-only throughout.
