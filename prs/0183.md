## Description

**Closes [#156](https://github.com/aarmea/lunchbox/issues/156).** Finishes what [#161](./0161.md) left open. [#161](./0161.md) moved `admin.toml` behind the
state custodian, so an activity can no longer read the minted bearer token off
disk — but it recorded that the API "still has no login, which is what [#156](https://github.com/aarmea/lunchbox/issues/156) is
about". This is the login. It also settles the static-token question [#65](https://github.com/aarmea/lunchbox/issues/65)'s
design left open in June.

There was a bearer token here, and not much else. That token was the password
and the session at once: it crossed the wire on every request, never expired,
could not be revoked without a factory reset that also drops the phone's bond,
and travelled in cleartext to the one person on the network with a motive to
read it.

## What was wrong

Six things, and only the first is the one the issue names.

1. **No exchange step.** The long-lived secret *was* the credential presented on
   every call. Sniff one request, hold admin forever.
2. **No expiry, no revocation.** The only way to withdraw a token was
   `bluetooth clear` — which unpairs the phone. A wildly disproportionate
   response to "my laptop was stolen".
3. **No way to get the token.** 32 base64 bytes, typed by hand into a phone. The
   only copies live in `config.toml` or in the custodian's `admin.toml`, so the
   honest answer to "where does the parent get it" was *ssh in and cat a TOML
   file*. The companion already holds it in Keystore storage and never used it.
4. **Cleartext.** `config.example.toml` ships `bind = "0.0.0.0"`. The shipped
   example was a plaintext admin credential on the family LAN.
5. **It failed open.** No static token *and* no BLE claim meant the entire
   management surface answered anyone who could reach the port — silently, with
   nothing in `list_diagnostics` to say so.
6. **`localStorage`.** Any script in the SPA's origin could read the token out,
   and it survived forever with no server-side record that it existed.

## Who the adversary is

Stating this decided most of what follows, so it is worth being explicit: the
threat model is **a motivated child on the same LAN, with physical access to the
device and time**. That inverts several usual instincts.

- *Passive sniffing is the realistic attack*, not an active MITM. Which is why a
  self-signed certificate — worthless against someone present at first contact,
  effective against everything else — is worth more here than its reputation.
- *The login page is reachable by the adversary*, from the device's own browser
  activity as well as the LAN, so rate limiting is not optional.
- *The device's own screen is an untrusted display for approvals* — the child is
  sitting in front of it. It is a **trusted** channel for exactly one moment:
  first boot, when the parent is holding the device and the child has not met it.
  That asymmetry is why the setup code is on the TV and "approve this login" is
  never on the TV.

## What this does

A credential — a password, or an approval tapped on the paired companion — buys
a **session**, and it is the session that travels.

| Credential | Who presents it | Can it sign a person in? |
|---|---|---|
| `shepherd_session` cookie | a browser | it *is* the signed-in state |
| session token as `Bearer` | cross-origin browser, a script holding a session | yes — same session |
| machine token as `Bearer` | `curl`, e2e harness, the companion | **no.** authenticates the call, opens nothing |

**Open mode is gone.** `shepherdd` always builds the credential store alongside
the API, and an *unconfigured* store is closed: five pre-auth endpoints answer
and nothing else does.

**Bootstrap is a code on the television, not a shipped default.** A shipped
default password is a known credential on every device whose owner never changes
it. The device generates one, shows it in a corner card — not full-screen; it is
up for minutes while a parent finds a browser — logs it for the SSH case, and
tears the card down within 30s of a password existing.

**Companion approval is the second door.** The browser shows six digits, the
paired phone shows the same six with who is asking and from where, the parent
compares and taps. Nothing secret crosses the LAN in either direction, and an
attacker racing the parent shows a *different* number — which is the entire
security property. The request id is the secret capability; the digits are not.
This is also what stops a forgotten password being an SSH problem: the phone can
set a new one.

**Plaintext off loopback is now a config error, not a warning.** `tls.mode`
defaults to `auto` — plaintext on loopback, a generated self-signed certificate
anywhere else — so saying nothing is never the insecure answer *and* never an
error. `files` mode (`tailscale cert`, Let's Encrypt via DNS-01, a home CA) is
the one with a real padlock. Because the self-signed fallback always exists, the
hard stop can never lock a device out of its own management UI.

`SameSite=Strict` plus an `Origin`-vs-`Host` check covers CSRF; bearer callers
are exempt, since nothing attaches a bearer header automatically.

## Upgrade notes

- **A device binding beyond loopback starts serving HTTPS.** Existing configs
  say nothing about `tls`, so they resolve to `auto` → `self_signed`. Bookmarks
  on `http://…:8080` stop working, and the first visit shows a certificate
  warning; the fingerprint is in the journal so it can be checked rather than
  guessed at. Set `tls.mode = "files"` for a warning-free padlock.
- **Prefer a concrete `bind` to `0.0.0.0` on a device with a reservation.** A
  wildcard bind contributes no address to the generated certificate, so reaching
  the device by its LAN address adds a *name mismatch* to the issuer warning.
  Naming the address (`bind = "192.168.1.20"`) puts it in the SAN and the
  certificate then verifies cleanly. Measured, not assumed — see Verification.
- **The first person to open the UI is asked for a setup code**, shown on the
  device's screen and logged at `WARN`. There is no upgrade path that leaves the
  API open.
- **A BLE factory reset does not touch web access.** The web password is one a
  parent chose, not the phone's; it survives, and so do browsers already signed
  in. The login page simply stops offering "Approve on my phone" until a phone
  is paired again. `shepherd web-auth reset` is the tool for the web side.
- **`auth_token` keeps working for scripts** and stops working as a way for a
  person to log in. The e2e harness therefore always configures one.
- **The dev loop moves to `https://127.0.0.1:8080`**, and seeding
  `localStorage.apiToken` no longer signs a browser in.

### On the Clippy commit

Worth a sentence because it looks like a flake and is not one. `split` returned
the whole 400 as its `Err` — an `axum::Response`, 128 bytes, exactly
`clippy::result_large_err`'s threshold. CI failed; the dev box did not, because
it was on **1.97** while the CI image installs plain `stable` and had moved to
**1.98**. `.ci/Dockerfile` pins no version, so this can recur: check
`rustc --version` against the image before suspecting anything else.

The fix is not an `#[allow]`. `split` now returns a 16-byte description with an
`IntoResponse` impl that produces the byte-identical response, so the `Err` is no
longer something every caller pays for on the success path — which is what the
lint is actually about.

### On real Bluetooth hardware

The earlier revision of this PR asked not to be read as claiming the phone flow
worked, because the build machine had no adapter and no phone. **That gap is
closed.** Everything below was run against a real daemon over a real radio
(Pixel 10a on `adb`, kernel `7.0.0-31`, shepherdd pinned to the Realtek
controller), in the order the handoff note listed.

- **The companion still works** after seven methods were added to
  `ManagementService` and the Kotlin wire types regenerated: the app reconnected
  on its existing bond and listed all 17 entries with their reasons.
- **`web_auth_status` over BLE.** Device controls → Web access shows the password
  card and "No browser is waiting to sign in". The handoff flagged the 3-second
  poll's two round trips as the thing most likely to strain the 15-second RPC
  deadline; **measured, the pair completes in ~500 ms**. No need to fold them
  into one call.
- **The approval handshake, including the property the whole design rests on.**
  Two browsers requesting at once got **different codes**, the phone showed two
  cards (`348263 Chrome on macOS`, `063297 Edge on Windows`), and approving the
  first signed in **only** the first — the second poll still returned `pending`.
  "Not me" → `denied` and the card vanished; an untouched request → `expired` at
  T+2:09 and the card vanished. Through a real browser: Firefox showed `122646`,
  the phone showed the same digits labelled "Firefox on Linux · 127.0.0.1", and
  the tap signed the browser in **within one second**.
- **`set_web_password` from the phone.** Old password → 403, new one → a session,
  and the three existing sessions kept working, which is the deliberate
  behaviour.
- **`companion_available` is honest in both directions, live.** Unclaimed, the
  login page renders `Sign in` only — no phone button, checked in the DOM and in
  a screenshot, not just in the API. After pairing it flips to `true` **without a
  daemon restart**, so the `set_companion` wiring reads the claim machine rather
  than latching at startup.
- **A factory reset does not strand web auth.** The bond went, the app showed
  "Bond lost — re-pair needed", `Re-pair` led back to the scan list and paired
  again first try (digits matched on both sides, `keySize=16`, `claim` recorded)
  — and `web-auth.toml` came through byte-identical, with the password still
  signing in. Browsers already signed in stay signed in; that is now written down
  in `docs/INSTALL.md` rather than left to be discovered.
- **`list_web_sessions` / `revoke_web_session` answer over BLE.** They have no
  companion UI yet, so they were driven from a throwaway probe build (reverted;
  nothing of it is in the branch). Both work — the revoked session's cookie went
  401 on the next request.

### The self-signed certificate on a real LAN address

The previous revision listed this as an open question. Measured on hardware:
with a wildcard bind the certificate names only `localhost`, the hostname and
loopback, and a client reaching the LAN address gets
`no alternative certificate subject name matches target ipv4 address` on top of
the issuer warning. **Binding the concrete address fixes it entirely** — the
address lands in the SAN and `curl --cacert` verifies and returns 200.

**Recommendation: leave the certificate's name selection as it is.** Enumerating
live interfaces sounds like the fix until you look at what it would put in the
certificate on a developer box — `10.0.3.1` (lxcbr0) and `172.17.0.1` (docker0)
alongside the real address — and it still would not survive a DHCP move. A
concrete `bind` or `files` mode are the honest answers and both already exist;
documenting the concrete-bind trick is worth more than the code change.

One unrelated find while checking this, recorded because it looks like a broken
TLS config and is not: rustls **rejects the SNI** for a hostname whose rightmost
label is numeric (this box is `shepherd-26.04`), before the certificate is
considered. Nothing server-side can fix it, and a device called `living-room-tv`
never meets it.

  verifiable by the parent rather than by whoever reads the journal.
- A diagnostic for "no password set" (the config error already makes "reachable
  without TLS" unreachable).
- `POST /auth/request` mints a request even when no companion is available. The
  UI never gets there and it cannot produce a session — and it is charged against
  the peer's throttle like a failed login, so it is not a way to fill the pending
  list — but a `CompanionUnavailable` error would be tidier.
- mDNS, which would fix both the certificate's name problem and the setup card's
  "port 8080 on this device" on a DHCP lease that moves.
