## Description

Closes [#177](https://github.com/aarmea/lunchbox/issues/177).

`conffiles` means "the admin owns this file; keep their edits and ask before
replacing them". None of the files this package declared as one was that, and
one of them misbehaved on every device, on every upgrade.

## What was wrong

Five files were declared as dpkg `conffiles` in `scripts/lib/package.sh`:

```
/etc/sway/shepherd.conf
/etc/udev/rules.d/71-shepherd-uinput.rules
/etc/polkit-1/rules.d/50-shepherd-firewall.rules
/etc/polkit-1/rules.d/50-shepherd-session-guard.rules
/etc/systemd/system/bluetooth.service.d/10-shepherd-bluetooth-experimental.conf
```

1. **The bluetoothd drop-in was a conffile the postinst rewrote.** dpkg
   checksums a conffile at unpack; the postinst then `sed`ed the build host's
   `bluetoothd` path out of it. Every *later* upgrade therefore saw a
   locally-modified conffile — on every device, without anyone having edited
   anything — and either prompted, or under `--force-confold` / an unattended
   upgrade silently kept the stale copy.

   Nobody hit this locally because when the build host and the target share a
   `bluetoothd` path the `sed` is a no-op and the checksum still matches. It
   needs a device whose daemon path differs, and it becomes a *lost update* the
   first time that file's contents change between releases.

2. **`shepherd.conf` was a conffile while `docs/INSTALL.md` said the opposite.**
   The file is generated, with rewrites `install_sway_config` verifies and
   `die`s on ([#144](https://github.com/aarmea/lunchbox/issues/144), [#157](https://github.com/aarmea/lunchbox/issues/157), [#172](https://github.com/aarmea/lunchbox/issues/172)). Those checks run when it is written and nowhere
   else — so a preserved admin copy carried unverified content across upgrades
   forever, including an exec line predating [#172](https://github.com/aarmea/lunchbox/issues/172)'s fix, on exactly the devices
   whose operator was hands-on enough to have edited it.

3. **The udev and polkit rules were vendor files in admin directories.** The
   tell: the polkit *action* already shipped to `/usr/share/polkit-1/actions/`
   while the *rule* went to `/etc`, from the same install step.

4. The state custodian's units were already (correctly) not conffiles, and
   nothing recorded why.

## What this does

### The drop-in is rendered by the postinst, not shipped

`install_bluetooth_dropin` branches on `DESTDIR`: a real install renders the
drop-in as before; packaging stages the *template* (with `@BLUETOOTHD@` intact)
to `/usr/share/shepherd/systemd/`. The generated postinst renders it from there,
picking the daemon path out of `systemctl cat bluetooth.service`.

Rendering rather than shipping-then-`sed`ing is what removes the defect: dpkg
never holds a checksum of a file that is about to change, so there is nothing to
prompt about. It also means an `apt upgrade` re-reads the host's `bluetoothd`
every time instead of possibly keeping a stale `ExecStart`.

### The rules moved to their vendor directories

- `UDEV_RULES_DIR`: `/etc/udev/rules.d` → `/usr/lib/udev/rules.d`
- `POLKIT_RULES_DIR`: `/etc/polkit-1/rules.d` → `/usr/share/polkit-1/rules.d`

Both subsystems read the vendor directory *and* `/etc`, with `/etc` winning — so
an admin override still works exactly as before. shepherd's own copy simply
stopped squatting in the override location.

`shepherd.conf` stays where it is and is now replaced outright on upgrade, which
is what `docs/INSTALL.md` had always promised. Site config belongs in the
unmanaged `/etc/sway/shepherd.conf.d/`.

**The package now declares no `conffiles` at all.** The reasoning for each of the
files that used to be listed — and for the state custodian's units staying out —
is written where the file used to be generated in `_package_write_control`.

### The upgrade path, which is the part that needed care

dpkg does **not** remove a conffile just because a new version stopped shipping
it: it keeps the file and remembers it as `obsolete`. Left alone, every upgraded
device would keep older udev and polkit rules in `/etc`, still winning over the
copies that replaced them. So the generated `preinst`/`postinst`/`postrm` call
`dpkg-maintscript-helper rm_conffile` for the three moved rules, with
`Pre-Depends: dpkg (>= 1.15.7.2)` as policy requires.
`PACKAGE_LAST_CONFFILE_VERSION` (`0.4.1`) is the `prior-version` argument.

The drop-in is deliberately *not* retired that way. Its path did not move — the
postinst writes it — so `rm_conffile` would rename every device's copy to
`.dpkg-bak` a moment before the postinst wrote a fresh one over the top. dpkg
keeps an obsolete conffile record for it instead, which costs one stale line in
`dpkg-query -W -f='${Conffiles}'` and buys the file being cleaned up on purge.

From-source installs get the same treatment through `remove_superseded_copy`,
called on real (non-`DESTDIR`) installs; the `uninstall_*` steps clear both the
new and the legacy path.

### The session watchdog's rule ([#172](https://github.com/aarmea/lunchbox/issues/172))

`main` gained the session watchdog while this was open, and it shipped a third
rule into the admin directory this change is emptying —
`50-shepherd-session-guard.rules`, installed by `install_state` to
`POLKIT_RULES_DIR` and declared a conffile alongside the rest. The rebase
conflicted on exactly that line, which is the right place to have conflicted.

Moving it came for free. Retiring the copies already on devices did not, so it
joins all three cleanup paths above. No *release* ever declared it a conffile —
only builds of `main` after 0.4.1 was cut — and those carry 0.4.1's version
number, so `PACKAGE_LAST_CONFFILE_VERSION` covers it unchanged; where it was
never registered the helper is a no-op.

Leaving it out would have been the quiet failure this whole change is about: a
stale `/etc` copy outranking the rule that replaced it, and an uninstall leaving
a uid holding the right to end any session on the machine.

## One intended behaviour change

`apt remove` now deletes `/etc/sway/shepherd.conf` and the rules, where before
they survived as conffiles until `purge`. They are shepherd's files, so removing
the package should take them. Called out in `docs/INSTALL.md`.

## How it was verified

Run for real on the dev box (Ubuntu 26.04, dpkg 1.23.7) against its actual dpkg
database — not a fake root. The from-source install was removed, packages were
installed and upgraded for real, and the box was put back afterwards.

Baseline: a `.deb` built from `origin/main` (0.4.1) declaring all five
conffiles, with the drop-in rewritten to point at a *different* machine's
`bluetoothd` (what 0.4.1's postinst writes on a device whose path differs from
the build host's — the condition the defect needs), the sway config hand-edited
the way an operator might, and the udev rule hand-edited too.

1. **0.4.1 → 0.5.0, unattended, no force options.** No prompt and no `==>`
   message. Three `Removing obsolete conffile` lines — both polkit rules and the
   session watchdog's — and the hand-edited udev rule preserved as `.dpkg-bak`,
   which is the other `rm_conffile` branch. Both admin directories clear, all
   three rules present under `/usr`. The sway config replaced, operator edit and
   all; `shepherd.conf.d/` untouched. The drop-in re-rendered from the staged
   template with *this* machine's `ExecStart`, recovering from the planted
   device path.
2. **The subsystems read the moved files.** `/dev/uinput` is `root:input 0660`
   and `udevadm test` names `/usr/lib/udev/rules.d/71-shepherd-uinput.rules`.
   `pkcheck` answers `yes` for `org.shepherd.firewall.apply-process` as a
   `shepherd-firewall` member and `yes` for `org.freedesktop.login1.manage` as
   `shepherd-state`, both resolved from `/usr/share/polkit-1/rules.d` — and
   `auth_admin_keep` for a uid neither rule names, so the check discriminates
   rather than answering yes to everything. `systemctl show bluetooth.service -p
   ExecStart` resolves through the drop-in.
3. **`apt install --reinstall`, no `--force-confmiss`,** after deleting all five
   files behind dpkg's back: all five come back (the drop-in via the postinst),
   and the `dpkg-query -L` diagnostic in `docs/INSTALL.md` names exactly the
   missing ones.
4. **0.5.0 → 0.5.1 with the drop-in template edited** — the same change 0.4.x
   could not deliver. It lands, `ExecStart` is still correct for the machine,
   and there is no `.dpkg-dist`.
5. **`apt remove`** takes the postinst-written drop-in *and* its directory —
   dpkg would not have, since it never unpacked it — and leaves
   `/var/lib/shepherdd/{state,admin}` and the `shepherd-state` uid alone.
   **`apt purge`** clears the rest, `.dpkg-bak` included.
6. **From-source symmetry, on the real box.** A legacy copy planted at
   `/etc/polkit-1/rules.d/50-shepherd-session-guard.rules` is removed by
   `install state` (`Removing the superseded …`), and `uninstall all` clears both
   of its locations.

## Notes for review

- **`PACKAGE_LAST_CONFFILE_VERSION` is `0.4.1`** — the last released version
  that declared conffiles — and this ships in 0.5.0. It is the `prior-version`
  handed to `rm_conffile`, so it must stay at or above the highest released
  version that still had them. It does not need touching again unless a conffile
  is reintroduced.
- **The obsolete conffile record for the drop-in** survives every ordinary
  upgrade, reinstall and remove, and clears on purge — measured. It *also*
  clears if the file is already gone from disk when dpkg unpacks over it, which
  then changes what `dpkg-query -S` (and so `path_owned_by_dpkg`, and so a source
  `uninstall all`) says about that path. Both outcomes are defensible; the
  history note records the distinction so nobody rediscovers it as a bug.
- **Seen in passing, not from this change and not fixed here:** on the very
  first connection after `claim`, the companion app logged `dispatch: failed to
  parse response frame (7456B)` for the `service_state` reply and dropped it, so
  the activity list sat empty until the next connect. It does not reproduce on a
  clean connect. Being chased separately.
