## Description

Closes [#127](https://github.com/aarmea/lunchbox/issues/127).

Media activities were configured as `type = "process"` with a hand-written `shepherd-media` argv, and video caching only ran while `shepherd-media` itself was open — so the first play of anything always buffered, and a library became watchable offline only if the child happened to leave the grid up long enough. This makes `media` a real kind and moves the cache somewhere shepherdd can fill it while nobody is watching.

## What changes

**A first-class `media` kind.** `type = "media"` takes `library`, `mode`, `item`, `quality`, `sort_by`, `reverse`, and `resume`; shepherdd builds the command line from them in a testable `media_argv`. A `mode = "play"` without an item, an item under `mode = "browse"`, or a quality that isn't a preset are config errors now, instead of a tile that dies on the child's screen.

`library` replaces the old `library_id`, because the value is a library *source* — a path or a playlist URL — while `library_id` names the library inside that file. Nothing in the wild used the old field: the kind existed as scaffolding whose launch path ran `xdg-open` on the library and discarded its args.

The connectivity check is deliberately **not** a field. shepherdd already knows it from `[entries.internet]`, falling back to `[service.internet]`, and now hands it to the activity through `SpawnOptions` so browse mode can hide online-only items while offline; `forward_check = false` opts out. That removed a URL the example config was restating verbatim.

`type = "process"` with `command = "shepherd-media"` still works, and stays the escape hatch for the flags this kind doesn't expose.

**The video cache moves out of the player.** It lived inside the `shepherd-media` binary, which pulls libmpv, egui, and a gamepad stack, so shepherdd could not share it. It now lives in `shepherd-media-cache`, depending on `shepherd-media-core` with `default-features = false` so no player comes along. The `PlayerHandle` wrapper that substitutes cached files at play time stays behind as `caching_player.rs`, since a daemon has no player to wrap.

**shepherdd prefetches.** It fills the cache while nobody is watching, holding off during an activity, while the internet is down, and below a free-disk floor — where it warns, because the cache cap bounds the cache, not the volume it sits on. Availability windows are deliberately ignored: an activity outside its window today is exactly the one worth having ready tomorrow. Opt out with `service.media.prefetch` or per activity with `prefetch = false`.

It re-reads policy before every sweep, so a config reload reaches both `[service.media]` and the set of libraries within the hour — no restart. That's also why the task is started even on a device with no media entries configured: a prefetcher that only existed when the *startup* policy had work for it could never be handed any by a reload. `docs/shepherd-media.md` has the full list of what a reload does and doesn't reach.

**The Android app converges on the same cache policy.** Eviction scoring and cache-file naming moved into `shepherd-media-app`, which both front-ends already depend on. Only the *policy* is shared — each cache still walks its own directory with its own filters.

## How the cache decides what to throw away

What goes when the cache is full is the part of this PR that changed most since first review, so it's worth stating in full.

Every committed file gets one score on the time axis, and the lowest goes first:

```
watched    score = played_at  + watched_grace
unwatched  score = first_seen - min(ordinal, 168) * 1h
```

The cap is `service.media.cache_max_bytes`, 10 GiB by default. **Watching buys a grace, not a permanent claim.** `watched_grace` defaults to 30 days (`service.media.watched_grace_days`), and because it's a fixed head start on a moving axis it erodes at one day per day. Inside the window nothing speculative can touch the file. Past it, a film watched once last spring competes on age like anything else and loses to a video the parent added this week.

The first draft of this was a strict two-class ordering — every unwatched file below every watched one — which made that guarantee absolute. Absolute turned out to be too strong in two directions: a single play protected a file forever, and once every byte of a full cache had been watched at least once, prefetch had nothing left it was allowed to spend and went permanently inert. That second case was documented at the time as an acceptable edge; it's the same bug as the first, seen from the other end.

**Unwatched files are ordered by when the item entered the library**, with position in that library breaking ties. Those are two different questions and the old model had one axis serving both: it ordered guesses by download time, inverted (newest first) so prefetch wouldn't re-download the head of the list every sweep. The other question then came out backwards — the newest unwatched file is *exactly* the item a parent just added, and it was the first thing thrown away.

Position now lives in the `.done` sentinel as `ordinal=N`, because the shared directory has no idea which library a file came from, let alone where in it. The step is an hour and caps at 168, so a whole library spans at most a week of the scale while the ages it competes against run to months — position breaks ties, it never outweighs age.

**"Recently added" had to become something the device observes.** `Item` carries no date field and a library file no history, so there's a new `<ikey>.seen` marker: empty, keyed by interest (the URL), written the first time an item is queued and never updated. It can't live in the `.done` sentinel, which dies with the file — the whole point is that an item which has churned through the cache twice is not a new item. It's stamped for *every* item a prefetch pass walks, not only the ones it downloads, so an item the cache had no room for is still correctly aged when room appears.

**One eviction rule replaces two.** `evict_to`/`evict_unwatched_to` collapsed into `evict_for(target, incoming)`: a download may only evict what it outranks. The callers differ only in what the download is worth — a prefetch scores as a guess at its position, an after-play download as a play right now, which is the maximum. "Prefetch skips when the cache is full of watched content" falls out of that rather than being a special case, and now resolves itself as content ages. Equality deliberately doesn't displace, which is what stops a download evicting the file it just wrote.

No hysteresis deadband, and none is needed: nothing drifts. `first_seen` is write-once and `ordinal` comes from the library, so a file that loses a comparison today loses it again tomorrow rather than trading places with whatever replaced it. The only input that moves is `played_at`, and it moves because somebody watched something. (A one-day margin was tried first and removed — it swamped the hour-scale position step by 24×, so no guess could recycle another guess from the same sweep and the cache went inert again, which is the exact bug being fixed.)

**One behaviour change worth naming:** a library larger than the cache now holds a stable prefix rather than rotating, because a same-sweep guess is dropped rather than swapped for one nearer the head of the list. That head is what a browsing child reaches first, and it churns less than the old ordering did.

### Both knobs, both processes

The eviction policy has to match on both sides of the directory or the daemon and the player undo each other's trims. Two settings govern it, and shepherdd resolves both from policy and hands them to its own prefetcher *and* to each spawned activity, through new `SpawnOptions` fields:

| Setting | Default | Flag to the activity |
|---|---|---|
| `service.media.watched_grace_days` | 30 | `--watched-grace-days` |
| `service.media.cache_max_bytes` | 10 GiB | `--cache-max-bytes` |

Flags resolved by the caller rather than env vars or entry fields, following `connectivity_check` — an env var would have meant giving the lean host adapter a `shepherd-media-cache` dependency just to name a constant.

**The size was previously unreachable except by environment variable**, and that didn't work the way you'd expect: each process reads `SHEPHERD_MEDIA_VIDEO_CACHE_MAX_BYTES` from its own environment, `build_inherited_env` forwards a fixed allowlist that doesn't include it, and `type = "media"` has no `env` map to override with. Setting it on shepherdd raised the cap for the prefetcher alone while the player kept trimming the same directory to 10 GiB. The variable is kept and still wins, now documented for what it is — a local override for debugging and for `shepherd-media` run by hand, not the deployment mechanism.

Worth distinguishing from `free_space_floor_bytes`, which the docs now do explicitly: `cache_max_bytes` bounds the cache, `free_space_floor_bytes` bounds the volume the cache sits on. A 10 GiB cache on a 16 GiB device fills the disk long before it fills the cache.

"Resolves" means per sweep, not once at startup, and that turned out to matter — see the reload bullet below.

## Making YouTube prefetch actually work

Validating the branch on a real device with an 89-item playlist turned up a
separate failure that had nothing to do with the cache policy, and everything to do
with whether any of this works at all. The journal showed **87 of 89 downloads failing** in four minutes with `yt-dlp exited with exit status: 1`.

The two that got through were both DRM-protected "full episode" uploads, which resolve to the legacy progressive itag 18. That was the tell.

`YOUTUBE_EXTRACTOR_ARGS` was `player_client=android_vr,android`, which **replaces** yt-dlp's default client list. That was a strict improvement when it was written — `android_vr` served DASH without a PO token while the default clients were gating those — but YouTube now rejects `android_vr`'s media URLs with HTTP 403 partway through the transfer. So the setting had inverted: it preserved only the edge case it was added for and broke the ordinary case.

| Video | Client path | Old value | New value |
|---|---|---|---|
| ordinary upload | DASH (`137+251`) | **403 Forbidden** | 295 MB, exit 0 |
| DRM "full episode" | progressive (`18`) | works | 8.45 MB, exit 0 |

It's `player_client=default,android` now — yt-dlp's own list, plus `android` purely for the itag 18 the defaults report as unavailable. Format selection sorts it out per video. Both cases verified with real downloads, not just resolution.

**This is pre-existing on `main`, not introduced here**, and the constant is shared with mpv's `ytdl_hook` and the Android stream resolver — so it broke playback too, not just caching. It's in this PR because it makes the branch's central feature untestable otherwise. (Updating yt-dlp 2026.07.04 → 2026.08.19 was worth doing and was *not* the fix; the 403 reproduced on the new version.)

Playback is no longer a guess. Checked in the headless dev session against a fixture with `prefetch = false` and an empty cache, so the uncached streaming path runs rather than a cache hit: with the new value, `STARTED_PLAYBACK … source=youtube`, decoded frames on the virtual output, audio confirmed, and the cache directory still empty; with `android_vr,android` restored and the same fixture, `STARTED_PLAYBACK` followed immediately by `ERROR message=Raw(-16)` and `RETURNED_TO_MENU reason=error`. On a fresh device, where nothing is cached yet, **every ordinary YouTube video was unplayable**, not merely un-cacheable. The Android resolver is a third consumer of the same constant and was checked separately — see Verification.

### Four defects that made it hard to see what was happening

- **yt-dlp's stderr was discarded.** Everything that goes wrong goes wrong *inside* yt-dlp — a 403, a format matching nothing, an age gate — and all of it exits 1. 87 failures produced no information and the cause had to be found by reproducing invocations by hand. Captured now, last lines in the warning, bounded to 3 lines and 400 characters so a library that has entirely stopped working doesn't put a screenful in the journal per item.
- **A failed item was retried every sweep, forever, at full speed.** A `<key>.failed` marker records the last failure and suppresses a speculative retry for 6 hours — deliberately longer than the hourly sweep, since the failures worth pacing are the ones that don't fix themselves within an hour. Keyed by content: a rendition that won't download says nothing about the others. An earned download ignores it, because someone is waiting on that one.
- **Downloads were unpaced** — 89 back-to-back yt-dlp invocations from one address. Nothing observed was attributed to that rate, so this is hygiene rather than a diagnosed fix and is documented as such: 5s between attempts that reached the network, skipped items still draining instantly, configurable and zero in tests.
- **The sweep log couldn't tell "finished" from "broken".** `queued media items … items=92` counted items *offered* to `queue_prefetch`, not downloads started — and `enqueue` returns early on a cache hit. So it printed identically whether 92 downloads were about to begin or the library had been complete for a quarter of an hour, and since every skip logs at `debug!`, INFO went silent either way. A later test (download, log out mid-way, log back in) was read as a dead prefetcher by two people; the capture showed 92 sentinels, 92 files, 8.6 GiB, zero `.failed` markers and zero warnings, with the last file written fifteen minutes before the second login. It had simply finished. `queue_prefetch` now returns a `QueueOutcome` (`Queued` / `AlreadyCached` / `FailedRecently` / `NotCacheable`) and the sweep tallies them into one line per library, logged on every sweep including the empty ones — the empty case being exactly the one that was indistinguishable from broken:

  ```
  media prefetch sweep entry=youtube total=92 queued=0 cached=92 cooling=0
  ```

  The failure cooldown is now checked in `enqueue` as well, so a skipped item counts as skipped rather than as work that was started. The worker still re-checks it, since a cooldown can expire while a request waits in the queue.

### And one unrelated bug in the same log

```
failed to parse yt-dlp output (line 47):
invalid type: null, expected a string; using stale cache
```

`YtDlpEntry.title` was `String`, and yt-dlp emits `"title": null` for a video deleted or made private since it was added — so **one dead video failed the entire playlist**. It survived here only because a stale cache existed; on a fresh device that library wouldn't have loaded at all.

`title` is optional now, and `parse_flat_playlist` skips entries it can't use rather than aborting. A family playlist accumulates dead videos as a matter of course, and losing the other eighty-eight over one of them is the wrong trade; only a playlist with nothing usable left is still an error. Skips log at debug, not warn — videos disappearing is normal and nobody can act on it. Checked against the playlist from the report: 93 lines, one null title, **92 entries parsed** where before it was a hard failure.

## Bugs fixed along the way

Several of these were latent with one process and would not have been with two.

- **Cache files collided across libraries.** Files were named `<item_id>.<ext>` in one flat directory, and item ids are unique only within a library. Two libraries both defining `intro` shared a file, and whichever downloaded first was served to both. Files are now named by a truncated SHA-256 of the source URL, which also dedupes: one video referenced twice is downloaded once and hits for both.
- **Nothing arbitrated two writers.** The `.done` sentinel makes readers safe but does not stop two processes writing the same `.part`. Downloads now take a non-blocking `flock` on `<key>.lock`; the loser skips rather than waits, because a prefetch is speculative and the play path streams the remote source instead of parking a child in front of a progress bar they cannot see. `flock` specifically, because the kernel releases it when the holder dies — and activities are SIGTERM'd mid-download every time a session ends.
- **Two qualities of one video fought.** The yt-dlp format selector is now part of the content key. Two entries over one library at different `quality` settings each saw the other's file as the wrong codec, deleted it, and re-downloaded — a loop that never converged. This retires `CacheState::StaleSelector` and the compare-the-sentinel logic with it.
- **Eviction had recency backwards.** Plain mtime let a prefetch that landed a minute ago outrank a film watched last week. See the scoring section above for what replaced it. Interest is recorded per *video* rather than per rendition, so watching at 1080p protects the 480p copy.
- **A prefetch could never be displaced by newer content, and a play could never be superseded.** Both were consequences of the two-class ordering; the score fixes them together.
- **Evicting *to* the cap is a no-op**, so a full cache stayed full; prefetch now makes room to strictly below it.
- **An after-play download evicted itself** — it arrived scored as a guess and was the first thing its own trim discarded. It records interest on commit now, which is honest: that download exists because the child just watched the video.
- **A config reload reached the player but not the prefetcher.** `MediaPrefetcher` snapshotted policy at construction, for a good reason — the engine lock must not be held across a download — but the launch path reads policy live. So after a reload changing `watched_grace_days`, a spawned player used the new value while the prefetcher kept the startup one, and the two valued their shared cache directory by different rules until shepherdd restarted. That's the exact divergence the flag exists to prevent, arriving through a door the flag left open. Policy is now re-read under the lock at the top of each sweep and used after it's dropped, which keeps the property the snapshot existed to protect. Everything in `[service.media]` rides along — the grace, the cache size, the disk floor — so a reload reaches all of it within the hour. The library list is rebuilt from the same read, so adding or removing a `media` entry no longer needs a restart either, and switching `service.media.prefetch` off now stops a running prefetcher rather than only preventing the next one.
- **Android named cache files with `DefaultHasher`**, commented as a "stable hash". It is not — the standard library documents the output as unspecified across releases, so a toolchain bump would rename the whole cache at once, silently re-downloading everything while the orphans kept occupying the size cap. Now the same truncated SHA-256, pinned by a test so a change to it has to be deliberate.
- **Android's `cached_path` bumped the file's mtime**, so merely consulting the cache counted as using it. It is a pure lookup now, and the play site records interest explicitly.
- **A codegen bug this surfaced:** `constant_name` upcased wire values straight into Kotlin identifiers, so `MediaQuality`'s `1080p` became `enum class MediaQuality { 1080P }` — not valid Kotlin, and it would have broken the companion build. Leading digits take a `Q_` prefix now; the wire value is untouched in `@SerialName`.

## Upgrading an existing cache

Pre-existing cache files under the old naming are orphaned by the rename and left in place on both platforms: they carry valid sentinels, so they are ordinary eviction candidates that age out, and re-downloading them is exactly what the next toolchain bump would have cost anyway.

Files that predate the `.seen` marker get stamped on the first sweep that walks them. Taking that stamp at face value would present the entire existing cache as freshly added and scramble the ordering, so **the file's own mtime is a floor on `first_seen`** — whichever is older wins. Sentinels with no recorded ordinal read as the tail of a list nothing is walking; pre-hash leftovers, which have no interest key at all, read as never watched.

## Verification

Unit tests throughout, plus integration tests that drive the real cache worker against a loopback HTTP server, so the pieces are checked against each other rather than against a fixture — including two that drive the failure path against a server that returns 403, covering both the cooldown and an earned download's exemption from it. On the host: `shepherd-config` 74, `shepherd-media-core` 75, `shepherd-media-app` 94, `shepherd-media-cache` 52, `shepherd-media-android` 31, `shepherdd` 39, `shepherd-host-linux` 64. The reload path is covered by building policies from real TOML rather than hand-assembled structs, since the resolution reads fields (`disabled`, per-entry `prefetch`, `mode`) a hand-built value could quietly drift away from. The scoring policy has its own tests for each boundary it claims — that a recent play is untouchable, that a stale one isn't, that a fresh addition beats a month-old guess wherever it sits in the library, that a same-sweep tail item doesn't displace the head, and that the configured grace actually moves where the flip happens.

The Android half was checked on a **Pixel 10a** (arm64-v8a, SDK 37), re-run after the scoring change and again after `cache_max_bytes`:

- Both ABIs link (`arm64-v8a` and `armeabi-v7a` — the 32-bit one matters, the Fire TV stick is `armeabi-v7a` only), `cargo ndk clippy --all-targets -- -D warnings` is clean, and the APK carries the cdylib for both.
- The crates' own unit tests were run **on the phone**, off `/data/local/tmp`, not just on the host: `shepherd-media-app` **94/94**, `shepherd-media-android` **30/30**, `shepherd-media-core` **61/61**. That includes the digest-pinning test, which is what actually proves the cache naming is identical on bionic/aarch64 and on the host, and the two new scoring tests — that a play old enough to have lost its grace stops protecting the file, and that a re-download is not a fresh arrival. `shepherd-media-core` joined the on-device set because `parse_flat_playlist` changed and Android is its only caller.
- End-to-end in the app against a loopback library, the `.seen` marker behaves as the design requires on real app storage rather than in a `tempfile`: it is written under the same content key as the file, is **not** re-stamped on a replay, **survives the eviction** of the file it names, and is still the original timestamp after a re-download — which is the entire point of keying it to interest rather than to the file. Eviction picks the earliest-played file and lands within the cap. A replay is still a cache hit with **zero** further HTTP requests that leaves the file's mtime alone while moving the `.played` marker's.
- The **Android stream resolver** was checked too. It is an independent consumer of `YOUTUBE_EXTRACTOR_ARGS` — not mpv's `ytdl_hook`, not the host's yt-dlp, but youtubedl-android's own bundled copy, which the app refreshes from GitHub at startup. Both videos from the failure report resolve and play on the device, streaming rather than from cache: the ordinary upload that `android_vr` was 403ing, and the DRM "full episode" that only itag 18 reaches. The playlist fetch exercised `parse_flat_playlist` live, non-ASCII titles included.

The YouTube fixes were verified against the real playlist and the real videos from the failure report — both client paths downloaded end to end, and the playlist that previously failed to parse now yields 92 of its 93 entries.

⚠️ **The eroding grace cannot be reached through the Android app**, only through its unit tests. It needs an *unwatched* file to compete against a long-ago-watched one, and nothing on Android produces one until `CacheMode::QueueAll` prefetches — so every eviction the app can be driven into is watched-vs-watched, which the old two-class ordering would have decided the same way. Same gap as before, same cause; it closes when that mode is wired.

⚠️ **32-bit is build-checked only.** The Pixel is arm64-only and rejects a pushed `armeabi-v7a` binary outright, and the Fire TV stick was unreachable during the run. The `armeabi-v7a` cdylib links and packages from current sources; nothing has executed it.

A **full-library prefetch has since been run on the device**, and this is the clearest evidence the extractor-args fix holds at scale: **92 of 92 videos downloaded, 8.6 GiB, zero failures and zero warnings**, in about sixteen minutes across one login. The same library produced 87 failures out of 89 before the fix.

`docs/ai/history/2026-08-22 001 media-kind-scope.md` records the original design reasoning and the on-device workflow, including the non-obvious parts (`TMPDIR` must be set because `env::temp_dir()` falls back to a `/tmp` Android does not have; reading the app's own cache needs a debug build, whose signature will not match a release install). `docs/ai/history/2026-08-22 002 media-cache-eviction-weights-watched-against-age.md` records why the two-class ordering was replaced and what the alternatives cost, and `docs/ai/history/2026-08-22 004 android-on-device-validation-of-the-scored-cache.md` records the hardware pass above. The on-device test workflow now lives in `crates/shepherd-media-android/README.md` rather than only in a history note, since its three gotchas have cost time on two separate passes.

## Not in scope

Deliberately left for follow-ups:

- **The stdout protocol reader** for playback-only time accounting, which `docs/shepherd-media.md` has always tracked separately. It is harder than it looks: `ManagedProcess::spawn` never pipes stdout, and the firewall path wraps the activity in `pkexec systemd-run --scope`, putting a privilege boundary between shepherdd and the stream.
- **Readiness gating for the media kind** — hiding tiles until `shepherd-media` and `yt-dlp` are present. shepherdd warns at startup if a YouTube entry exists without yt-dlp, but nothing enforces it.
- **`CacheMode::QueueAll` on Android.** It appears in the settings picker but nothing acts on it, so that cache has no library ordinal to score with and every file reads as the tail of a list nothing is walking. The shared policy degrades cleanly to age-ordering there, but the position term only starts earning its keep once that mode is wired.
- **Reclaiming a removed entry's cache eagerly.** When a `media` entry is removed by reload, its cached files stop being refreshed and age out on their own rather than being deleted. That keeps a config edit non-destructive and makes re-adding the entry a week later cheap; deleting on removal would be defensible too, and is a one-liner if that's preferred.
- **Play count as a signal.** A video watched twenty times is a favourite and could earn a longer grace than one watched once. The score has room for it; recording it means the `.played` marker has to stop being an empty file.
