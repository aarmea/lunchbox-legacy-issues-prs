## Description

Closes [#154](https://github.com/aarmea/lunchbox/issues/154).

> One of the annoyances while setting up activities is the need to SSH in or
> temporarily switch to a non-shepherd DE (i.e. GNOME) to do things like: log
> into Steam and install games, set up RetroArch controls, install packages of
> any kind, manage local files.

A button in the web app or the companion relaxes the kiosk in place. The key
grabs go back to whatever is on screen, the launcher becomes a searchable
picker over every `.desktop` file on the machine, the HUD becomes a taskbar, and
the screen stops blanking. Leaving logs the session out, which is what makes it
a reset rather than a flag flip.

The scope decisions behind all of this are recorded in
[`docs/ai/history/2026-08-27 002 management-based-arbitrary-launcher (#154).md`](docs/ai/history/),
and the rebase and revalidation in
[`docs/ai/history/2026-09-07 007 admin-mode-rebase-and-logout-on-exit (#154).md`](docs/ai/history/).

## It is a mode, not an activity kind

Which is what makes it broad: nearly every kiosk invariant in this codebase is
written as an unconditional truth, and each one had to become conditional.

| Invariant | Where it is asserted | In the mode |
|---|---|---|
| One activity at a time | `CoreEngine` / `ActiveSession` | many windows, no session |
| No window switching, no keybinds | `sway.conf`, single workspace | `mode "admin"` + `WindowAction::Focus` |
| `Home`/`Ctrl+w`/`Alt+F4` end the session | `bindsym --locked` | keys reach the app |
| Screen blanks with no session | `swayidle` → `set_screen_power` | suppressed |
| A window with no session is an orphan | `WindowOwner::Unowned`, orphan banner | suppressed |
| Everything launchable comes from config | `launch(EntryId)` | `launch_desktop_app(id)` |
| Nothing floats, nothing goes fullscreen | `for_window` rules | **unchanged** — dialogs stack full-size |

The mode lives on `CoreEngine` as a **policy** state rather than a device flag,
which is what makes the mutual exclusion fall out of the existing launch gate:
every entry reports `ReasonCode::AdminMode`, so the child's grid greys itself out
without the launcher knowing the mode exists, and entering is refused while an
activity runs — naming it — rather than tearing a child's session down from a
button that does not say so.

## What is in it

| | |
|---|---|
| `WindowAction::Focus` | Useful on its own: both window panels can switch windows now, not just close and stash them. |
| `mode "admin"` in `sway.conf` | The kiosk grabs released, volume/brightness and the emergency exit kept. Contains no binding that *leaves* the mode, so shepherdd's idea of it and the compositor's cannot drift. |
| `enter_admin_mode` / `exit_admin_mode` / `admin_idle_timeout` | On `ManagementService`, so one implementation serves IPC, HTTP and BLE. `admin_mode` rides `ServiceStateSnapshot`; `AdminModeChanged` is the delta. |
| `shepherd_config::desktop` | A `.desktop` enumerator, hand-rolled — ~300 lines sharing `xdg_application_dirs()` with `icon.rs`, no new dependency. Honours `NoDisplay`, `Hidden`, `OnlyShowIn`/`NotShowIn`, `TryExec`, field codes and `Terminal=true`. |
| The picker | The launcher's own grid with a search bar over it, per the issue. In the mode the launcher *is* the picker, so the taskbar's "Start" button is `WindowAction::Focus` on the launcher's window rather than a new RPC. |
| The taskbar | An extra box in the HUD's `left_box`, shown on `admin_mode` while the kiosk's label and countdown hide. `build_hud_content` needed no refactor, so [#48](https://github.com/aarmea/lunchbox/issues/48) can still take one on its own terms. |
| `shepherd-lock` | A new crate: `ext-session-lock-v1`, `lock_device` / `unlock_device`. |
| Audit | `AdminModeEntered`, `AdminModeExited { timed_out }`, `ScreenLocked { timed_out }`, `ScreenUnlocked`, `AdminAppLaunched { id, name }`. |

The mode bills no time and creates no session, so **the audit log is the only
record the device was in use for that span** — which is why those variants are
load-bearing rather than nice-to-have. `AdminAppLaunched` stores the name beside
the id because a `.desktop` file can be uninstalled, and
`org.kde.krita.desktop` is a poor answer six months later to "what was run on
this device?".

## The "X" button, and the two ways out

The HUD's "X" closes the focused window and becomes "leave administrator mode
and log out" only once nothing the caregiver opened is left, exactly as the issue
describes. **That gate is a HUD affordance only.** `exit_admin_mode` over HTTP
and BLE is never refused, whatever is still on screen — so a window that refuses
to close is rescued from the phone in seconds rather than stranding the device.

The idle timeout (15 minutes, armed unconditionally in `sway.conf` and a no-op
outside the mode) splits on the same question:

| Seat idle 15 min | Result |
|---|---|
| Nothing open | leave the mode → log out → kiosk |
| Windows open | **lock**; the mode persists, nothing is closed |

Walking away is a legitimate workflow — waiting on a Steam download over a slow
connection is the motivating case — so a timeout that force-closed windows would
break the most valuable thing the mode does. The lock is the compensating
control instead.

## The lock is a real session lock

`ext-session-lock-v1`, not a `gtk4-layer-shell` overlay, and the reason is one
this repo already wrote down in another context: an activity that issued
`[app_id=org.shepherd.hud] kill` removed the HUD for the rest of the session.
That same command against a layer-shell lock surface would unlock the device. A
session lock is immune — killing the client leaves sway showing a blank locked
screen, which fails closed, and for a control whose whole job is keeping a
determined child out, fail-closed is the requirement.

The cost is a second rendering stack: a session-lock client is a raw
`wayland-client` surface, not GTK. `shepherd-pairing-display` is the precedent
for the shape (a small standalone binary shepherdd spawns for one purpose), and
the three crates it adds — `smithay-client-toolkit`, `wayland-client`,
`cairo-rs` — were already in `Cargo.lock` transitively, since gtk4 pulls cairo
and the wayland stack comes with it. No new dependency tree.

Unlocking is a protocol message, so **the unlock path cannot be "kill the
process"** — a `SIGKILL`ed lock client leaves the session locked permanently,
with nothing left to unlock it. The client subscribes to shepherdd's event
stream like the HUD and the launcher do, and calls `unlock_and_destroy` when it
sees the state clear; killing it is only the failure path, and that path fails
in the safe direction.

Locking is offered on the device, unlocking is not. That asymmetry is the
feature: the device itself has no way back in, which is what makes it safe to
walk away from mid-setup. Leaving the mode always clears the lock, because a lock
whose only exit is an administrator RPC reached *through* the mode must not
outlive it.

## Leaving the mode logs the session out

From the issue: *"exiting the admin mode should actually be a complete logout to
ensure that everything is properly reset"*.

Turning the flag off was never a reset, and the mode's own design is why.
Everything a caregiver starts here is started deliberately outside supervision —
`launch_unsupervised` `setsid`s it so a package install survives a daemon
restart — so nothing in the daemon can enumerate what is still running, let
alone reap it. A signed-in Steam client, a dbus-activated service that was not
there at boot, a package manager still holding its lock: each one changes how the
*child's* next activity behaves, and none of them appears in the window list the
"no windows left" gate reads. Ending the session is the only reset the daemon can
actually promise.

Both exits go through one `leave_admin_mode`, which asks for the same shutdown
`logout` has always asked for — so the ordering that makes `logout` work (stop
the session, drain the HTTP server, then tear sway down) carries the exit's own
RPC reply out ahead of the compositor going away.

Three decisions inside it:

- **Only when the engine really left the mode.** `exit_admin_mode` is idempotent
  and ungated on purpose, so the two clients and the timeout race each other.
  The one that arrives second must not tear down whatever session the device has
  moved on to.
- **The idle timeout's exit logs out too.** A mode nobody came back to leaves
  exactly the same processes behind as one somebody left on purpose.
- **The timeout's lock branch does not.** It can therefore only ever end a
  session from the empty case, where there is nothing on screen to lose.

Every button that leaves says so, since leaving closes whatever is open: "Turn
off and log out" on the phone, "Turn Off & Log Out" in the web app, "Leave
administrator mode and log out" on the HUD.

**Operational consequence.** On a device the session ends, logind stops
`user@<uid>.service` with it (the kiosk user is denied SSH and console login by
`shepherd harden apply`, so there is no second session holding it up), and the
`shepherd-admin-*.scope` units go with it. A device *without* getty auto-login
comes back to a greeter rather than to the kiosk — already true of the "Log Out"
button both management UIs have always had, and now true of a second button.

## Security

This branch waited on [#156](https://github.com/aarmea/lunchbox/issues/156) and [#161](./0161.md), and the release gate decision 4 named was
[#144](https://github.com/aarmea/lunchbox/issues/144). All three have landed, so the position is now:

- **The trigger is authenticated.** Every administrator RPC arrives through
  `POST /api/v1/rpc`, which [#156](https://github.com/aarmea/lunchbox/issues/156) put in the `guarded` half of the router behind
  `require_auth`. There is nothing per-method to remember: adding a route to
  `guarded` is automatically gated, and adding one to `open` is a visible act in
  a five-line list. Over BLE it is the existing claim (`AdminAuthority`).
- **What the mode could damage has moved.** [#157](https://github.com/aarmea/lunchbox/issues/157)/#161 put policy, the database
  and the audit log at `shepherd-state`'s uid, which nothing an administrator
  launches can read or write.
- **`launch_desktop_app` refuses when the mode is off**, asserted against the
  host rather than the return value — a refusal that still spawned would be the
  worst outcome, and the error alone cannot tell the two apart.
- **`unlock_device` is only reachable from a management client.** Under [#144](https://github.com/aarmea/lunchbox/issues/144) an
  activity cannot reach the daemon's socket at all.

### The one this branch had to fix

`launch_unsupervised` left the picker's applications as plain children of
`shepherdd`, in `shepherdd`'s own cgroup — which is exactly what [#144](https://github.com/aarmea/lunchbox/issues/144)'s peer
check trusts. Every other launch path respects that line, and
`shepherd-host-linux/README.md` states it as an invariant: *"nothing shepherd
starts for an activity is ever in shepherd's cgroup."*

The picker's launches had the weakest claim of any of them and were the only ones
inside. They are arbitrary third-party programs, chosen out of `.desktop` files
an activity can itself write into `~/.local/share/applications` — where XDG
precedence puts them *ahead* of the system copies. A terminal opened in
administrator mode was a peer the daemon believed, holding `unlock_device`,
`launch` and the rest; and because these launches are `setsid`, it kept them long
after the mode ended.

They now get the same `systemd-run --user --scope` wrapper an activity gets, and
the same fallback (run it bare when the user manager is unreachable, which the
existing `ipc_socket_not_hardened` diagnostic reports). Measured on the headless
stack, launching Calculator from the picker:

```
shepherdd 703633: /user.slice/…/tmux-spawn-….scope
calc      705036: /user.slice/…/user@1000.service/app.slice/
                  shepherd-admin-gnome-calculator-703633-0.scope
```

Two smaller ones from the same pass, both branch code that predated [#144](https://github.com/aarmea/lunchbox/issues/144)'s
`helpers` module: the picker's program name now resolves through
`helpers::tokio_command` — which narrows it to binaries in root-owned
directories, deliberately, since a bare name a bare `$PATH` could satisfy is a
name the kiosk uid can choose — and so does `shepherd-lock`, whose bare-name
fallback was a substitution primitive aimed at the one binary standing between a
child and a locked screen.

## Accepted as-is

- **Full-size stacked windows.** `for_window [floating] floating disable` and
  `workspace_layout stacking` stay exactly as they are, so dialogs and file
  choosers become full-size stacked siblings. This deletes the largest piece of
  risk in the feature (no imperative window-rule override, no fight with map-time
  rules) and is what makes the taskbar load-bearing rather than cosmetic: a modal
  that has stacked over its parent is only reachable by switching to it.
- **The whole `.desktop` set**, with no shepherd-specific allowlist or category
  filter. The search bar is how you find things in it.
- **The orphan banner is suppressed** while in the mode rather than adding a
  fifth `WindowOwner::Admin`, and `report_unowned_windows` stops logging for the
  same reason — everything on screen is deliberately outside supervision.

## Verification

`cargo build/test/clippy --workspace --all-targets` (69 suites, 0 failures),
`cargo fmt --all`, `shepherd build config-wasm`, `shepherd config validate`,
`npm run typecheck` / `test` (95) / `check:boundary` / `check:coverage`, and
`./gradlew :app:testDebugUnitTest`. Every commit checks green on its own
(`git rebase --exec 'cargo check --workspace --all-targets'`).

Driven end to end on the headless stack (`shepherd dev headless`):

- Administrator mode paints: taskbar with "Apps", lock button, and the launcher
  showing the searchable picker instead of the child's grid.
- `list_desktop_apps` returned 45 entries; `launch_desktop_app` on Calculator
  mapped its window and landed the process in its own scope (above).
- `exit_admin_mode` replied `{"ok":null}` and sway was gone within a second,
  with no survivors — `shepherdd`, the HUD, the launcher and the Calculator all
  down.
- The audit log carries the whole span and nothing else does:
  `admin_mode_entered` → `admin_app_launched{Calculator}` →
  `admin_mode_exited{timed_out:false}`.
- Rebooting comes up as an ordinary kiosk: `admin_mode=false`, `locked=false`,
  no session, the child's grid.

Two things that driving it found and no test would have:

- **The launcher needed a view of its own.** Because the mode disables every
  entry, the child's grid renders completely empty — a blank screen with no
  reason on it for the child and no reminder for the caregiver that the kiosk is
  unlocked. `LauncherState::AdminMode` is its own stack child now, which is both
  where the picker lives and what makes the picker non-interactive for the
  child's grid by construction: the grid is a different child, so nothing on
  screen in the mode can launch an activity.
- **The preloaded Steam client is reported `Unowned`.** `snap run` re-execs, so
  the pid the host recorded is not the pid that draws. Main never noticed because
  `report_unowned_windows` skips the scratchpad; `admin_windows` did not — so the
  taskbar carried a button for a hidden window and the "X" would never have
  become "leave administrator mode" on any device that preloads Steam. Which is
  every device that has it configured.

Pressing the HUD's exit button itself is not driveable headlessly (synthetic
pointer events do not fire GTK4 `connect_clicked` handlers there); the icon and
tooltip were confirmed in pixels, and the handler takes the same
`admin_windows(..).is_empty()` branch the icon does before calling the RPC that
*was* driven directly.

## Not in this PR

- **A virtual keyboard** ([#6](https://github.com/aarmea/lunchbox/issues/6)). The picker's search bar needs a physical keyboard
  on a touch-only device until that lands.
- **Per-activity filesystem separation** ([#105](https://github.com/aarmea/lunchbox/issues/105)), which would close the last of
  what the mode can reach.
- **The Waydroid app picker** ([#75](./0075.md)/#2) has its own "list what's installed and
  launch one of them" shape; worth a shared abstraction before a second one is
  written, but not here.
