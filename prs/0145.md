## Description

Closes [#143](https://github.com/aarmea/lunchbox/issues/143).

shepherdd notices roughly sixty conditions an administrator could act on — a missing dependency, a protection that is configured but not in effect — and every one of them goes to journald and nowhere else. A child hits the consequence; the parent has no way to see the cause.

This adds the structured channel the issue asks for: conditions **raised and cleared** rather than logged once, each with a severity, the entry or subsystem it concerns, and a suggested fix — surfaced in the web UI and the companion app.

## What changes

**A diagnostic channel on the wire.** `Diagnostic` / `DiagnosticCode` / `DiagnosticSubject` / `DiagnosticSeverity` / `DiagnosticSet` in `shepherd-api`, carried on `ServiceStateSnapshot` and as a `DiagnosticsChanged` event, plus a `list_diagnostics` RPC.

Deliberately **not** called a warning. That word already means the time-limit warning shown to the *child* before their session expires, in both `WarningSeverity` and `AuditEventType::WarningIssued`, and reusing it would collide in exactly the code that has to handle both. These are aimed at the person who configured the device, not the person using it.

**State, not events.** A diagnostic is a condition that is currently true and later stops being true, so the daemon holds a set and clients read it, rather than an append-only stream they would have to reconcile. Identity is `(code, subject)`, which is what lets one registry replace the four incompatible de-duplication mechanisms already in the tree — a `warned` bool, an `AtomicBool` swap, an `attempts % 10` throttle, a `reported` HashSet — and the per-launch warnings that had none at all.

**Nine conditions**, of two kinds, because the difference is whether the daemon can ask again:

- *Probed* — a pure function of the environment (firewall enforceable, `yt-dlp` present, cache disk above the floor, sound backend, readable input devices, browser policy applicable). The sweep recomputes the whole set and replaces it wholesale, so a condition that stops being true simply stops appearing.
- *Observed* — raised where it happens and cleared when the same site next succeeds (unreadable media library, BLE pairing agent unregistered).

**A configured protection that cannot be applied now blocks the launch.** An entry with `[entries.firewall]` on a host where enforcement is unavailable used to spawn *without* a filter and warn to the log — the config promised the activity was filtered and it was not. It no longer launches, and the child sees a bare `ProtectionUnavailable` reason with no detail, because nothing they can do changes it. Which protection and how to fix it is the administrator's diagnostic.

**Both UIs.** A dedicated page listing everything (web: "Health"; companion: "Device health"), a critical-only banner on each main screen linking through, and per-activity problems shown on the activity next to its availability reasons.

## The defect that shaped the design

The warnings being replaced were computed **once at daemon construction and never retracted**. The missing-`yt-dlp` check ran in `MediaPrefetcher::from_policy` and the firewall probe in `process::init`, neither re-run on config reload. So an admin who added a YouTube entry got no warning until they restarted, and one who then installed `yt-dlp` kept the warning forever.

Any design that did not fix this would make the feature actively misleading, so re-evaluation is core rather than a refinement: sweeps run hourly and on config reload, and `firewall_enforcement_status` had to stop being a `OnceLock`. It stays cached — the launch path consults it on every spawn and the probe execs `pkcheck` — but it is refreshable now, which matters much more once it also gates launches: otherwise an admin installs the helper and their child's activities stay gone.

## Notable decisions

**The gate copies [#96](https://github.com/aarmea/lunchbox/issues/96)'s required-input gating exactly**, including the part that matters most: `Option<bool>`, where `None` means "not yet probed" and **fails open**. [#96](https://github.com/aarmea/lunchbox/issues/96) wanted that so a detection failure would not hide activities; here it stops a probe that has not answered from blanking every firewalled tile during boot. There is a test asserting an unprobed host still shows them.

**A firewall on a Steam entry is now a config error, not a runtime diagnostic.** The adapter cannot filter a Steam-launched process whatever the host supports, so blocking it would remove the activity permanently for a mistake no host change could ever fix. That belongs in validation, which also fixes today's silent acceptance of a setting that is quietly ignored.

**`DiagnosticsChanged` carries the whole set rather than a delta.** For a payload this small, reconciliation logic in every client would be cost with no benefit — and it earns the payload a BLE coalesce key, since a newer set makes every queued older one redundant. Under its own key, not the snapshot's, so a diagnostics update cannot drop a queued state snapshot.

**The set is capped at 32 with a `truncated` flag.** `ServiceStateSnapshot` already carries every `EntryView` and is delivered over BLE, where a frame caps at 16 KiB, so this is the one field that could push it past the limit. Truncation spends the least severe first, because a set over the cap is exactly when the critical ones most need to survive.

**`list_diagnostics` exists because the web UI never fetches a snapshot.** The scope doc called it probably unnecessary; the UI queries per page, so the set would have been unreachable from a browser.

Two conditions took different routes than the scope doc planned, both flagged in their commits. A browser policy on a kind that cannot apply one turned out to be static, so it is probed — an admin learns their setting does nothing before their child opens the activity. An unreadable media library stayed observed, because probing it would mean invoking yt-dlp or fetching a URL on a timer to discover something the prefetch worker finds out anyway.

## Bugs found by actually running it

Four defects that neither the type checker nor the test suite could catch, each fixed in its own commit:

- **An activity gated by the new reason rendered `undefined`** in the web UI. `types.ts` is hand-written, so its `ReasonCode` union never learned about `protection_unavailable`, and `reasonLabel` is an exhaustive switch with no default. The Kotlin equivalent is generated, so the *same* omission broke the companion build instead — which is the argument for the generated mirror being the source of truth wherever a client can use one.
- **The per-activity diagnostic rendered inline** with the text after it ("…and that the file parses.Up to 1h"), because MUI's caption variant is a `<span>` and that card is not a flex column.
- **Its severity colour never applied** — `color={...}` produced the same emotion class as the plain grey captions, so a critical problem and an incidental note looked identical.
- **The companion's critical banner never appeared.** It read the diagnostic set but nothing on the home screen ever fetched one, so on a cold launch it stayed invisible until the caregiver navigated to the very thing it exists to tell them about. Nothing distinguishes "reads a flow that is populated" from "reads a flow nobody fills" except watching a cold launch.

A fifth, visible only in raw JSON: a remedy string reached the wire with a run of twenty-odd spaces from a Rust literal that lost its line continuation. HTML collapses whitespace, so no screenshot would ever have shown it.

## Verification

53 new tests. The probe rules are pure and take gathered facts, so each judgement is testable without a filesystem or a subprocess — including the two that are easy to get wrong and invisible when they are: a missing `yt-dlp` only matters if something references YouTube, and unreadable input devices only matter if some entry requires one. Both are pinned by tests asserting *silence* in the negative case.

Checked end-to-end against a live daemon, which raised three real conditions on the dev box with no fixture needed (`firewall_unenforceable`, `firewall_not_applied` on an entry, `media_library_unreadable` on another) — probed, observed, service-level and per-entry all at once:

- **Web UI**: dashboard banner with count and link, Health page in daemon order with entry chips resolved to labels, per-activity text in the right colours, and the gated entry reading "Unavailable until set up".
- **Companion, on a Pixel 10a over BLE**: cold-launch banner, Device health screen, correct severity colours and chips.
- **Launcher**: the gate fires — the firewalled entry carries `ProtectionUnavailable`.

Also `cargo fmt --check`, `clippy --all-targets -D warnings`, `cargo test --all-targets`, `validate-config config.example.toml`, wire codegen drift, `tsc --noEmit` + web build, and the companion's Kotlin compile and unit tests.

## Not in scope

- **The remaining ~50 log sites.** Most are transient per-operation failures that belong in the log. The line drawn is "a condition an administrator can fix"; the obvious next tier is `brightnessctl` missing, the config watcher failing, and BLE bearer pinning unavailable.
- **Notifying a parent when a protection stops working.** The companion has no notification infrastructure at all — no `NotificationManager` use and no `POST_NOTIFICATIONS` in the manifest — so Critical is an in-app banner in both UIs. Interrupting is its own issue with its own transport question, since BLE only reaches the phone while it is connected.
- **Audit-log entries for Critical conditions.** A protection silently not applied seems worth an audit row distinct from the current-state registry, but it is a second write path and can wait.
