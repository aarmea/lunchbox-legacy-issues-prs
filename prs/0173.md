## Description


Closes [#155](https://github.com/aarmea/lunchbox/issues/155).

The premise in the issue is half right, and the half that is wrong is the
interesting part: **the enforcement clock already paused.** `MonotonicInstant`
is `CLOCK_MONOTONIC`, which stops while the machine is asleep, so `deadline_mono`
and `billable_duration` have always excluded the time a lid was shut. The
journal has it — session `23e1d56a` ran 92.72 s of wall clock across two
suspends and was billed 85.78 s, the 6.95 s shortfall falling inside the 10.07 s
the machine spent in the suspend path.

What does *not* pause is `ActiveSession::deadline`, the wall-clock copy set
beside it at launch and never reconciled. Every countdown a human sees is
derived from that one:

| Consumer | Reads |
|---|---|
| HUD (`SessionStarted` and the state snapshot) | `shepherd-hud/src/state.rs:371`, `:487` |
| Launcher cover | `shepherd-launcher-ui/src/state.rs:94`, `:187` |
| Admin dashboard | `DashboardPage.tsx:173`, `useCountdown(deadline)` |

So after a sleep they all read low by however long the machine was out, and can
sit at 0:00 while the session runs happily on — which is exactly the report:
the time asleep counted as activity time (in the display), and the countdown
crossing zero without the activity exiting. `SessionInfo` already carries the
*correct* monotonic `time_remaining` on the wire; nothing reads it.

## The larger hole underneath

`compute_max_duration` clamps a session to what is left of its window **at
launch**, and nothing re-checks it afterwards — `tick` re-evaluates entries only
to update the launcher grid. Because the monotonic clock stops, an N-second
sleep moves the real end of the session N seconds past the window that bounded
it. That is unbounded for an overnight sleep: an activity started at 19:55
against a 20:00 bedtime, slept through the night, resumes the next morning with
its budget intact, inside a window that is closed.

This half is the one with supervision consequences, and it was reproduced on
hardware before it was fixed (see below).

## What this adds

`CoreEngine::notify_resumed(now, now_mono)`, called from the `resume_rx` arm of
shepherdd's main loop — the arm that already existed for the suspend cover
([#73](https://github.com/aarmea/lunchbox/issues/73)). It does two things:

1. **`ActiveSession::resync_deadline`** re-derives the wall deadline from the
   monotonic one. Since all four consumers read `deadline` out of the state
   snapshot shepherdd was *already* broadcasting on resume, correcting the
   session before that broadcast fixes every countdown at once — no wire change,
   no client change.
2. **`outside_allowed_hours`** re-asks the schedule question (entry window,
   group window, force-enable override) at the post-resume wall clock. On a
   failure the session is clamped to the entry's save-progress grace and a
   `Critical` `WarningIssued` goes out.

The snapshot is broadcast *before* the warning: clients rebuild their countdown
from the snapshot, so a warning sent first would be overwritten by the state
that followed.

```toml
[service]
save_grace_seconds = 120   # the default; 0 closes the activity on wake

[groups.limits]
save_grace_seconds = 300   # members fall back to this

[entries.limits]
save_grace_seconds = 45    # unless they set their own
```

It is wired into the config editor (service field, per-subject slider) so it is
not a key reachable only by hand-editing TOML.

## Judgement calls

**Only the schedule is re-checked**, not all of `evaluate_entry`. A daily quota
resets at midnight, so a long sleep can only leave *more* of it; a cooldown is
not a reason to stop an activity that is already running. Widening this would
end sessions for reasons the issue did not ask for.

**The grace latches** (`ActiveSession::save_grace_started`). Suspend/resume is a
loop a child can drive from the lid switch, and the monotonic clock does not
burn the grace down while the machine is asleep — without the latch, closing the
lid whenever the warning appeared would extend the session forever. With it,
each wake returns only the grace that is left, so total awake grace is bounded
by the configured value.

**Warning thresholds at or beyond the grace are retired** when the clamp
applies. Otherwise a default 300 s threshold fires on the very next tick, and
the HUD's last-writer-wins rendering replaces "you have 2 minutes to save" with
a bare "only 120 seconds remaining". Thresholds *inside* the grace still fire
and still escalate.

**`save_grace` cascades service → group → entry**, unlike every other limit,
which is evaluated at both levels independently. One session has one answer, and
"strictest wins" is the wrong rule for a kindness. The entry's resolved value is
used even when it was the *group's* window that closed — the child is saving the
activity in front of them either way. Without the cascade the key would have
been silently dead under `[groups.limits]`, since `RawLimits` is shared.

**`LimitDefaults`** replaces the loose `Duration` parameters threaded through
`Group::from_raw` / `Entry::from_raw` / `convert_limits`. Adding a third
same-typed positional would mis-resolve every entry if a pair were swapped, with
nothing to catch it.

## Verification

Ten new tests (eight engine, two config) cover the display correction, the
clamp, the latch, the force-enable bypass, a group window, a session already
ending inside the grace, `save_grace = 0`, a resume with no session, and the
config cascade. `cargo test --workspace --all-targets` is green (62 suites) and
`cargo clippy --workspace --all-targets -- -D warnings` is clean.

**Confirmed against a real suspend**, driven from the headless dev session. The
fixture's entry sets no grace of its own and the service default is 120 s, so a
correct run has to resolve 30 s through its group — the cascade, exercised for
real rather than in a unit test. Launched inside a 19:00–19:30 window, then
suspended across the end of it through logind:

```
20:55:46  Session started    deadline=2026-04-27 19:30:44.765
20:58:28  Resumed; corrected the displayed deadline for time spent asleep
          slept_secs=146  deadline=Some(2026-04-27T19:33:11.142)
20:58:28  Resumed outside allowed hours; granting save-progress grace
          entry_id=bedtime-game  grace_secs=30
20:58:48  Warning issued     threshold_seconds=10  remaining_secs=9
20:58:58  Session ended      reason=Expired
```

- `slept_secs=146` — the drift between the two clocks *is* the suspended time.
  The stale deadline `19:30:44` was **40 s in the past** at resume, so the HUD
  would have shown 0:00 with ~106 s of budget still to run.
- `grace_secs=30` — resolved through the group, not the service's 120 s.
- Only the **10 s** threshold fired; the 300 s and 60 s defaults were retired
  rather than firing at once and overwriting the explanation.
- Ended `reason=Expired` exactly 30 s after resume.

Twelve seconds into the grace the HUD showed `00:18` in critical red beside
**"Time is up for now. You have 30s to save."**, over a mock clock reading
7:31 PM — visibly past the window it launched under. Thirty seconds later, "No
session" and an empty grid.

One trap for the next person: **`rtcwake -m mem` cannot test this.** It writes
`/sys/power/state` directly, so logind never emits `PrepareForSleep` and
`notify_resumed` never runs. That mistake cost a run — and the run was worth
keeping, because it reproduced the untreated bug on hardware: after a 151 s
suspend the session was still running at mock 19:31:25, **85 seconds past the
19:30 window end**, and kept going until its monotonic budget ran out. Arm the
alarm with `rtcwake -m no -s 150` and suspend with `systemctl suspend`.

## Out of scope

Usage is billed to the day a session *ends*, so a session from 23:50 to 00:10
charges all twenty minutes to the second day. Agreed as a real defect and split
out as [#170](https://github.com/aarmea/lunchbox/issues/170); it cannot produce "the activity never exits", which the display
drift can. Note for whoever takes it that `settle_session_end` passes the same
`today` to `settle_tokens`, so token balances land on the same wrong day —
cooldowns are safe, being stored as `now + delta` timestamps.

`reduce_current` drifts the same way this bug did: its new wall deadline comes
from the old one minus the reduction rather than from `now + new_remaining`.
Left alone here to keep the diff to the resume path.

the reasoning behind each decision above — is in
