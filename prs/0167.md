## Description

Cross-compile, package and release `arm64` from the `amd64` runner, so an arm64
device can be installed from the apt repo instead of built by hand. Closes [#166](https://github.com/aarmea/lunchbox/issues/166).

## What this adds

**A target architecture for the build and packaging path.**

```sh
./scripts/shepherd deps install cross --arch arm64   # toolchain + sysroot
./scripts/shepherd build --arch arm64                # → target/<triple>/
./scripts/shepherd package deb --arch arm64          # → Architecture: arm64
```

`--arch` takes a Debian architecture and derives the Rust triple with
`dpkg-architecture`; `--target` takes a triple directly. An `--arch` naming the
host stays a native build — it leaves the triple unset, so output paths and cargo
fingerprints are the ones every other build on the machine already uses. That is
what lets a CI matrix pass `--arch` on every leg at no cost.

Everything downstream follows without knowing a cross build is happening:
`get_target_dir` is the single place that knows about `target/<triple>/`, and
`SHEPHERD_BINARIES` stays the one list `binaries_exist`, `install_bins`,
`uninstall_bins` and the `.deb` staging all read.

**A cross dependency set**, `scripts/deps/cross.pkgs` — the host toolchain plus
the target half of every development library the native build links against.
`scripts/ci/check-cross-pkgs.sh` fails the build when it drifts from
`build.pkgs`, because the failure it prevents is quiet and remote: someone adds a
dependency, every native build goes green, and the cross job breaks much later
with a pkg-config error naming a library nobody connected to the commit.

**CI and release legs.** A separate `cross` CI image (`.ci/Dockerfile.cross`)
layers the toolchain and sysroot onto the base image — kept separate because it
is 1.5–2.5 GB larger and every other job pulls the base on every run. `Build
(arm64 cross)` builds the workspace; `release.yml` gains an `arch: [amd64,
arm64]` matrix with `fail-fast: false`, so whichever architecture succeeds still
publishes. Forgejo reads `Architecture:` out of the control file and serves both
from one distribution/component, so no per-arch handling is needed downstream.

Both CI and release assert what would otherwise fail silently: that the binaries
really are `ARM aarch64`, that the `.deb` is labelled for the architecture it
contains, and that the eBPF object stayed on `bpfel-unknown-none`. Every arm64
job also starts by checking that it actually got the cross image — see *The
cross image ref could arrive empty* below for why that is not a given.

**A test for the path CI never runs.** Every CI and release job passes `--arch`,
on an amd64 runner, so a plain `shepherd package deb` — the command a developer
or a device runs — is exercised nowhere. A hardcoded `amd64` default would pass
every job, and on an arm64 host it turns `package deb` into a cross build that
emits a *consistent* `_amd64.deb` of x86-64 binaries (demonstrated on the M1
VM), which no label-vs-contents assertion would flag even if the path ran.
`scripts/ci/check-default-arch.sh` covers it: a stub `dpkg` reports a host the
runner is not (arm64, and ppc64el so that hardcoding `arm64` instead does not
pass), and the real `package_deb` runs end to end with only the Rust build,
binary staging and root check stubbed. The real `dpkg-deb` builds a small
package whose `Architecture:`, file name and requested target triple are
checked. It needs no Rust toolchain, runs in the existing *Arch neutrality* job,
and fails on each of five regressions it was mutation-tested against (the
default hardcoded to `amd64`, to `arm64`, the host comparison in
`build_set_target`, the control file's `Architecture:`, the `.deb` file name).
`scripts/shepherd` now runs `main` only when executed, so the test can source
the real entrypoint.

**`check-arch-neutral.sh`, narrowed rather than removed.** With arm64 built for
real, its old purpose — "this repo can build for non-amd64" — is proven by the
build and package jobs. What it still uniquely covers is the scripts the `.deb`
installs (`scripts/lib/*.sh`, `shepherd-admin`), which run on the device and are
only ever staged in CI; a `/usr/lib/x86_64-linux-gnu/…` path in `admin.sh` would
otherwise ship green. Its header, messages and CI step now say that, and say
plainly that it is lexical and what that misses.

## What this does not do

**A cross build buys no test coverage.** Nothing in `cargo test`, `shepherd-e2e`,
the firewall BPF suites or the headless session runs on the target architecture.
The BPF path is the most exposed, because the verifier runs on the *target*
kernel ([#151](https://github.com/aarmea/lunchbox/issues/151)). Correctness on arm64 is covered separately, on a native aarch64
machine — CONTRIBUTING gains a section on running the suites there, and the
results are in `docs/ai/history/2026-09-04 002` and `2026-09-13 002`.

The arm64 cross job is a required check only because it runs on always-up
hardware. What it catches is what actually recurs: a new dependency that does not
cross, an arch-specific compile error, and packaging breakage.

There is no arm64 clippy leg. Running `clippy --workspace --all-targets -D
warnings` natively on aarch64 produced zero findings — no integer-width or
`c_char`-signedness lints — and the workspace has no `cfg(target_arch)` gates
outside the wasm crate, so a second target would cost minutes per PR to
re-report what the amd64 `lint` job already says.

## One real bug in the product code

`crates/shepherd-firewall-helper/build.rs` now strips `CARGO_BUILD_TARGET` before
shelling out to build the sibling eBPF crate. An exported one beats that crate's
own `.cargo/config.toml` `[build] target` and compiles the eBPF program for
whatever the parent is targeting. This is also why `shepherd build` passes
`--target` on the command line rather than exporting the variable — the command
line never reaches the child at all; the `env_remove` is the belt to that
braces.

Confirmed load-bearing rather than assumed: with the line removed and
`CARGO_BUILD_TARGET` exported, the BPF build fails at link —
`rust-lld: error: undefined symbol: __libc_start_main` against `Scrt1.o`. With it
restored, the object stays eBPF. (The host triple is enough to show this; no
cross toolchain is involved.)

## Verification

### Cross-compiled in both directions, on real hardware

No source changes were needed either time.

* **amd64 → arm64** on the amd64 workstation, the direction CI takes. All 12
  binaries are `ARM aarch64`, interpreter `/lib/ld-linux-aarch64.so.1`; **every**
  ELF in the `.deb` is aarch64 with no x86-64 file anywhere, and its file set is
  identical to the amd64 package's, so label and contents agree.
* **arm64 → amd64** on the aarch64 host, re-run at `0.5.1` with all 12 binaries
  (the first pass, in `docs/ai/history/2026-09-04 002`, predated three of them).
  Every binary links as x86-64 against the amd64 sysroot, the `.deb` is
  `Architecture: amd64` with zero aarch64 files inside, and its file set is
  identical to the native arm64 package's.

In both, the eBPF object stayed `ELF … eBPF` with no host-triple directory beside
it in the BPF crate's `target/`, and a plain `shepherd build` afterwards still
produces native binaries — the cross build stays entirely inside
`target/<triple>/`.

Host-architecture packaging is unchanged: `package deb` with no `--arch` still
produces the same `.deb`, and `package deb --arch <host>` produces byte-identical
contents.

### The activity backends, natively on arm64

None of this is reachable from a cross build, and none of it had been exercised
on arm64 before.

**RetroArch.** All 14 cores in `RETROARCH_CORES` have arm64 candidates in
`resolute/universe`, so the table needs no per-architecture handling.
`apps install retroarch` installs aarch64 packages; the core resolves through
`/usr/lib/aarch64-linux-gnu/libretro/` because `core_search_dirs()` reads
`/usr/lib` rather than guessing a triple. Launched end to end from the grid with
the MIT-licensed `jsmolka/gba-tests` ROM the docs recommend: RetroArch mapped as
`com.libretro.RetroArch`, drew its result on screen, and wrote
`states/mGBA/…state.auto` on close.

**The libretro PPA works on arm64 too.** All three channels advertise
`Architectures: … arm64 …` with `Components: main`. `apps install retroarch --ppa
mupen64plus-next` takes visible `libretro-*` packages from **16 to 102**, every
one with an arm64 candidate — so the "the PPA is the only source that adds cores"
claim in `docs/emulators.md` holds here, not just on amd64. That core is also the
naming-mismatch case: `core = "mupen64plus-next"` resolves against the real file
to `mupen64plus_next_libretro.so`, with no diagnostic.

**Okular.** `okularGenerator_epub.so` — the backend people miss, and the reason
`apps install okular` installs `okular-extra-backends` — is present for arm64.
The `ebook` kind launched `org.kde.okular` rendering a real EPUB under shepherd's
generated kiosk configuration, with the HUD's page-turn controls.

**shepherd-media.** `va-api detect` takes the branch written for ARM boards —
machines with no PCI display controller of a known vendor — and correctly names
no package rather than guessing one. Playback decoded and displayed H.264, the
browse view rendered a library, and `yt-dlp` runs. **Hardware video decode on
real ARM silicon remains untested**: this machine has no VA-API driver and the
headless session forces software rendering either way.

## Defects found while verifying, all fixed here

### The cross image ref could arrive empty

A CI run of the new jobs failed on a commit that changed nothing but a history
note, one run after the same jobs had passed. The job logs show why: `Build
(arm64 cross)` started `image=node:20-bookworm` — the runner default, because
its `container.image`
was empty — and failed with `rustc: command not found`, while the arm64
`Package` leg started the **base** image and failed with E0463 *can't find crate
for `core`*, because `arm64 && cross-ref || base-ref` falls through on an empty
string. The published cross image itself was correct.

`needs.images.outputs.cross-ref` was empty, and stayed empty — the Package leg
read it five minutes after the image jobs finished. Forgejo resolves a reusable
workflow's outputs once, when the caller completes. In the failing run
`CI image (arm64 cross)` finished in the same second as `CI images`; the Android
image, a second earlier, got its ref through, as did the cross image in the
previous run with a one-second gap. That mechanism is inferred from the timing
and the stored value, not observed inside Forgejo.

Fixed at both ends:

* **`images.yml` ends on a `settle` job** that needs all three image jobs and has
  no outputs, so the job finishing alongside the caller is one nobody reads. It
  prints the three refs, which will distinguish "never landed" from "landed but
  was not propagated" if this recurs. It applies to `release.yml` too.
* **Every arm64 job fails first, and says why** (both in `ci.yml`, and the
  release `.deb` leg): before checkout it prints `cross-ref` and exits with a
  message naming an empty ref, or an environment without the aarch64 std,
  instead of a compiler error that points nowhere near the cause.
* **`arch_to_triple` requires `rustc` up front.** Under `pipefail` a missing
  `rustc` failed the target-list check exactly like an unknown target, so it
  reported *"No Rust target for Debian architecture 'arm64'"* — blaming the
  architecture for a job with no toolchain at all.

The first run with these in place (463) was green throughout, and its timing is
the intended one: `CI image (arm64 cross)` finished three seconds before the
snapshot, and it is `settle` that completed in the same second as `CI images`.
The failure was intermittent, so one green run shows the ordering works, not
that the race is gone.

### Found on the native arm64 machine

**The apt mirror probe could not answer for a PPA.** `deps install cross` decided
whether "the configured mirror" served the target architecture by reading the
first `URIs:`/`Suites:` line across `/etc/apt/sources.list.d/*.sources` —
whichever file sorts first — and probing it for `main` *and* `universe`. A
Launchpad PPA only ever publishes `main`, so the probe 404ed on a component the
stanza never claimed and reported "does not serve this architecture" for a PPA
that does. The fallback then pinned **every** source to `Architectures: <native>`.

On a machine whose first source is `ppa:libretro/testing` — Libretro's own PPA —
that would have made every one of its emulation cores invisible to apt, on a
device whose primary use is supervised emulation, while the real archive served
the architecture the whole time. Now probed per stanza against the components
that stanza declares, with pinning decided per source and the ports fallback
keyed off the Ubuntu-archive-shaped stanza.

Verified on a host that actually has the PPA installed, which reproduces both
halves of the bug: the PPA file sorts before `ubuntu.sources` in the glob, and
probing the live PPA by hand gives `main universe` → *does not serve*, `main` →
*serves*. The fixed parser yields three stanzas (PPA, archive, security) and
probes each against its own components.

**The ports fallback then ran for real** — the branch previously recorded as
exercised nowhere, not locally and not in CI. For an architecture the archive
genuinely lacks, the PPA was left byte-identical, `ubuntu.sources` was pinned
once per stanza, the ports entry was added, `apt-get update` succeeded, and all
102 libretro packages stayed resolvable. Restoring from the `.pre-cross` backup
returned `/etc/apt/sources.list.d/` to its pre-run md5sums exactly. For an
architecture the archive does serve, nothing under `/etc/apt` changed at all.

**`--arch armhf` derived the ARMv6 triple, and so did `--arch armel`.**
`dpkg-architecture` reports `arm-linux-gnueabihf` and `arm-linux-gnueabi`, which
became `arm-unknown-linux-gnueabihf` and `arm-unknown-linux-gnueabi` — both real
Rust targets, so the target-list guard accepted them, and both the wrong one.
Rust's bare `arm-*` triples are the ARMv6 baseline (`+strict-align,+v6`), while
Debian defines armhf as ARMv7-A hard-float and armel as ARMv5TE soft-float.

The two fail differently and both badly. armhf fails *quietly*: ARMv6 code runs
on an ARMv7 machine, so the result is a package labelled armhf whose contents
target an older ISA than the label promises. armel fails *loudly but late*:
ARMv6 instructions fault on ARMv5TE hardware, long after the package looked fine
on the build host. Corrected with a two-entry override applied before the
target-list check. Every other architecture derives as before, and `riscv64`
still fails loudly and correctly.

Neither architecture is one this PR claims to support; both are fixed because an
answer that passes the guard and is wrong is worse than a refusal.

**A flaky e2e test.** `firewall_supported_path_invokes_helper_with_expected_argv`
failed once and then passed 21 consecutive re-runs, 15 of them under full CPU
load. Its helper stub records argv to a log, and `wait_for_file` waits for that
log to *exist* — but a shell redirection creates the file before a byte is in it,
and `/bin/sh` flushes after each command, so the log grows a few lines at a time
and a reader can catch a prefix. The assertion then blames a flag that is merely
not written yet. Both argv-recording stubs now write to `<log>.partial` and
rename it into place, so "exists" and "is complete" become the same statement.
Test-only, unrelated to this issue, and riding along because a gate that fails
occasionally is not a gate.

## Known gaps and loose ends

* `_deps_enable_foreign_arch` only parses deb822 `*.sources`. A one-line `.list`
  source that cannot serve the new architecture would not be pinned.
* Hardware video decode is unverified on any real ARM GPU (see above).
* The uninstall guard on `deps install cross` answers "what would this remove",
  not "will this resolve at all" — an unsatisfiable multiarch set still reaches
  apt and fails there.
* Pinning a source reflows its stanza's comments: a commented-out alternate
  `# URIs:` ends up after `Signed-By:` rather than beside the line it annotates.
  Semantically identical, cosmetically worse.
* Noted for separate issues, both outside this PR's surface:
  `browser::write_policy_file` uses `std::fs::write`, so a reader — Chrome
  included — can observe a partial managed-policy JSON; and
  `VA_DRIVER_DIRS`' `/usr/lib/*/dri` glob is architecture-blind, so on a
  multiarch host `va-api detect` can report a foreign-architecture driver as
  present.
