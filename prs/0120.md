## Description

Off by default on both front-ends: `--resume` on the Linux binary (global,
so it covers `browse` and `play`), and a per-library "Resume playback"
checkbox on Android (`LibraryEntry.resume`, serde-defaulted so existing
settings files parse unchanged). With the option off nothing is recorded
and no state file is ever written.

With it on, per library: a position for every item plus the id of the one
watched most recently. Re-opening an item resumes it; re-opening the
library shows a "Continue watching" card offering that item.

The state model lives in `shepherd-media-app::resume` rather than in each
binary. That crate's premise was "the Linux binary is stateless", and this
is the exception — putting it there is what lets both front-ends share one
policy for the parts that are easy to get subtly wrong:

- An item stopped within 30s of a known end (or within its first 20s) has
  its entry *removed*, so the next play starts over instead of at the
  credits. The natural EOF path needs no special casing as a result.
- The player's position is ignored for the first 2s of a playback. A load
  carrying a start offset does not report that offset instantly — mpv
  still answers with the previous file's position, or zero — and
  recording that would erase the position just resumed from.
- Writes are batched to one per 10s while playing and forced when
  playback ends, including on SIGTERM: shepherdd ending an activity
  mid-film (a time limit, a bedtime window) is a normal way to stop
  watching here, not an edge case.

Resuming is a start offset on the load, not a seek after it:
`PlayerHandle::set_start_position` becomes a `start=` per-file option on
libmpv's `loadfile`, so nothing before the resume point is decoded or
shown. `Session::set_start_position` deliberately re-applies to every load
of the current item, so the existing `RetryBudget` restart after a
transient stream error comes back to where it dropped rather than to the
opening titles.

Positions go to `$XDG_STATE_HOME/shepherd/media/resume/<library_id>.toml`
(new `paths::media_state_dir`) and, on Android, beside `settings.toml` —
not the cache dirs, which are defined by being safe to delete and
re-download.

The card is shared UI (`shepherd-media-ui::prompt`), following the poster
grid's convention: custom-painted, focus by index, caller-supplied theme,
because both front-ends drive it from a D-pad or gamepad. It is modal only
while drawn; on Linux the offer waits up to 10s for its item to appear
(the `--connectivity-check` grid starts pessimistically empty) and then
lapses rather than popping up over a grid already in use.

Verified end-to-end in the headless dev session: a clip played ~35s then
SIGTERMed recorded 36.56s; relaunching opened at 0:38; browse mode then
offered "Left off at 0:50 of 3:00" and accepting started playback at
exactly 0:50; Escape dismissed the card without leaving the library; and
the same clip played without `--resume` left the state file byte-identical.
The Android front-end is covered by the shared tests and compiles, but is
not yet exercised on hardware.
