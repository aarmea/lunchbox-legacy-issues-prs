## Description

Closes [#193](https://github.com/aarmea/lunchbox/issues/193).

## What

A token-gated activity or category is now unavailable whenever its banked balance is below `minimum_seconds`, not only once the balance reaches zero.

Previously the gate *ratcheted*: once the balance reached the minimum it stayed open until the balance was spent out. A partial spend could therefore leave a 40-second balance behind a 10-minute minimum and still offer the activity. That is the too-short session the minimum exists to prevent (an unfinished Pokémon battle, half an Outer Wilds loop).

## Behaviour

- **The minimum applies every time**, not just the first time the balance reaches it.
- **Nothing is cut off at the threshold.** A session that does start is still capped by the *whole* balance, not `balance - minimum`.
- **The remainder is kept.** What a session leaves below the minimum stays banked and counts toward reopening; a little more source time opens the gate again onto the full balance. With `carry_over = false`, a remainder that is never topped up expires at midnight like any other balance.
- **Equality still opens the gate.** The issue says "exceeds", but the gate has always opened at exactly the minimum, and the docs and both apps say "needs 10m". I left that as it was.

Example with `minimum_seconds = 600` and 700 s banked: a 5-minute session leaves 400 s, so the activity locks. The 400 s stays banked, and another 200 s earned reopens it with 600 s available.

## Changes

- **Gate:** `TokensPolicy::unlocked(balance)` is now `balance > 0 && balance >= minimum`. The engine no longer records a ratchet after earning or after an `adjust_tokens` grant.
- **Store:** `TokenState.ratcheted` and `Store::set_token_ratchet` are removed. A new `drop_obsolete_column` migration drops `token_balances.ratcheted` from existing databases, and it replaces `add_missing_column`, which only that column used. Downgrading is safe: the previous release adds the column back with its default.
- **State custodian protocol:** `SetTokenRatchet` is removed and `PROTO_VERSION` goes from 2 to 3. Unlike adding a variant, removing a field is not harmless: an older client would fail to decode a `TokenState` without `ratcheted` and treat every gate as locked, so a half-finished upgrade should be refused at the handshake.
- **Docs and UI text:**
  - `config.example.toml` and `crates/shepherd-config/README.md`
  - `crates/shepherd-store/README.md`
  - the config editor's caption under a token gate
  - the `TokenStatus.unlocked` doc comment, with the generated TypeScript and Kotlin mirrors regenerated (that comment is the only change in them)
- **Apps:** neither the web UI nor the companion needs a code change. Both already show progress toward the minimum whenever `unlocked` is false, so a partly spent balance now reads as e.g. "7m of 10m needed · locked".

## Tests

- `test_token_gate_relocks_when_a_spend_leaves_less_than_the_minimum` replaces the ratchet test. It checks that:
  - the gate opens onto the whole balance;
  - a spend leaving 400 s of 600 s locks it with `TokensInsufficient { balance: 400s, required: 600s }`;
  - `request_launch` is refused;
  - the 400 s stays banked;
  - topping up reopens the gate with a 600 s cap.
- `test_group_token_gate_relocks_every_member_below_the_minimum` covers the category case the issue describes: one member's spend locks both members.
- `test_manual_grant_banks_time_and_opens_at_the_minimum` (renamed) also checks that granted time spent below the minimum locks the gate.
- `test_obsolete_ratchet_column_is_dropped` opens a ratchet-era table holding a `ratcheted = 1` row. It asserts that the column is dropped, the balance survives, writes work, and re-opening is a no-op.
